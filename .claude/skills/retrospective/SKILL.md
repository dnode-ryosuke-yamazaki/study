> ワークフロー上の位置: 定期作業(開発ループ外)。Skillの更新はfeatureブランチ + [/pr](../pr/SKILL.md)で行う

# 実行タイミング

月1回〜四半期に1回。ワークフローに従っていて「毎回この手順を飛ばしている/毎回手順にない作業をしている」と気づいたときは待たずに実行してよい。

# Step1 直近の実績を集める

`gh pr list`はGitHubへの通信を要するため、サンドボックスから直接実行できないことが多い([doc/claude-code-sandbox-limitations.md](../../../doc/claude-code-sandbox-limitations.md)参照)。ネットワーク制限のない環境ではこちらで直接実行し、失敗する場合はユーザーに以下のコマンドを手元のターミナルで実行してもらい、出力を貼ってもらう:

```bash
gh pr list --state merged --limit 10 --json number,title,mergedAt,url
```

直近のマージ済みPRを5〜10本見返し、それぞれについて「どの工程(/requirement〜/pr)をどう通ったか」を確認する。会話ログは残っていないため、PRの本文・コミット構成・レビューコメント・specの差分から読み取る。PR一覧が取得できない場合は`git log main --oneline -20`などローカルで追える範囲の情報で代替する(レビュー記録まではPRの本文を見ないと追えない点に留意する)。

# Step2 ずれを洗い出す

観点:

- **飛ばされた工程**: 仕様承認PRなしで実装に入っていないか、レビュー(spec-review/implementation-review)の記録がPRに残っているか
- **毎回発生する手順外の作業**: どのPRでも同じ追加作業をしているなら、それはSkillに手順として書くべきもの
- **使われていないテンプレート・チェック項目**: PR本文がテンプレートと乖離している、チェックリストの特定項目が常に空振りしている
- **Skill間の案内切れ**: 完了時の次ステップ案内どおりに遷移しているか。案内先が実態と違うなら修正する
- **CLAUDE.md・[README](../README.md)との整合**: ワークフロー図・まとめ表・遷移図がSkillの現状と一致しているか
- **Skillの固定コスト**: 全Skillのfrontmatter(name・description)は毎セッション必ずコンテキストに載るため、Skillを増やすほど固定トークン費が増える。descriptionが長文化していないか(発火条件が伝わる1〜2文に収まっているか)、一度も使われていない・役割が重複しているSkillが残っていないかを確認し、不要なら統合・削除する

# Step3 ずれの扱いを決める

ずれごとに「手順が過剰(形骸化)」か「実態が手抜き」かを判定し、ユーザーに一覧で提示して方針を確認する:

- 手順が過剰 → Skillを実態に合わせて簡素化する(使われないチェック項目・テンプレ項目は消す)
- 実態が手抜きで手順が正しい → Skillは変えず、次回から手順に従う(必要ならSkillに注意書きを足す)
- 新しい定常作業が見つかった → 該当Skillに手順を追記する、または新しいSkillとして切り出す

# Step4 Skillを更新する

`feature/<変更内容>`ブランチを切り、Skill・CLAUDE.mdを更新して[/pr](../pr/SKILL.md)で実装PRとして出す(仕様承認ゲートの対象外。specs/には触れないため)。

# 完了時の次ステップ案内

振り返り結果(ずれの一覧・対応方針・更新したSkill)をユーザーに報告する。PRを出した場合はマージ後に不要になったブランチ・worktreeを掃除すればよい(`git worktree remove`・`git branch -d`)。
