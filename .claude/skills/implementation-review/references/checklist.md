# コードレビューのチェックリスト

code-reviewerエージェント(またはエージェントを使えない状況で直接レビューするメインスレッド)が読むファイル。レビュー実施者以外はこのファイルを読まない(トークン節約のため[SKILL.md](../SKILL.md)本体から分離している)。

# レビューの注意事項

- **レビュー中はコードを修正しない。** 指摘の報告に徹する(修正は[/resolve](../../resolve/SKILL.md)の仕事)
- **好みの問題は指摘しない。** 指摘には必ず根拠(承認済み仕様との不一致、CLAUDE.mdの規約、テスト・CIの失敗、[/implementation](../../implementation/SKILL.md)の命名ルールなど)を添える。根拠を示せない指摘は出さない
- **良い点も必ず1つ以上挙げる**
- **レビュー結果に応じて次のステップを案内する**(テンプレート末尾の案内を必ず含める)

# チェックリスト

## 仕様との整合
- [ ] 実装がrequirements.mdのビジネスルール・design.mdの処理フローと一致しているか(境界値・エラー時の振る舞いを含む)
- [ ] 承認された仕様にない機能・挙動を勝手に追加していないか
- [ ] requirements.md先頭の`> ステータス: 仕様確認中(未実装)`行が削除されているか
- [ ] 実装中に仕様を変更した場合、3点セットが同じ変更で更新されているか

## テスト
- [ ] 該当アプリのテストコマンドが全て通るか
- [ ] requirements.md/design.mdの仕様項目に対応するテストが揃っているか(仕様コメントの見出し・`[n]`表記が仕様書と完全一致するか、[/implementation](../../implementation/SKILL.md)参照)。対応するテストがない項目がある場合、意図的な省略かどうかを確認する
- [ ] 境界値・特殊ケース・エラーケースのテストがあるか

## 動作確認
- [ ] UIに変更がある場合、`run`Skill等でアプリを起動・操作し、変更箇所の表示を実際に確認したか
- [ ] UIを持たないAPI・バッチ処理の変更の場合、curl・統合テスト等でエンドポイントや処理を直接呼び出して確認したか

## コード品質
- [ ] CLAUDE.mdの規約に沿っているか(コメントは日本語、関数・型に役割と非自明な計算式・定数の根拠をコメント、過剰な抽象化をしない)
- [ ] 該当アプリのlint・buildコマンドが定義されている場合、それらが通るか
- [ ] デバッグコード・不要なファイル・未使用のimportが残っていないか

## 設定・ドキュメント
- [ ] specフォルダの増減・依存関係の変化がある場合、`apps/<アプリ名>/specs/architecture.md`の機能マップが追随しているか

# 指摘の重要度

| 重要度 | 意味 | 扱い |
|---|---|---|
| 🔴 must | マージできない問題(仕様との不一致、テストの欠落・失敗、CI失敗の原因) | 修正するまで/prに進まない |
| 🟡 should | 修正が望ましい問題(規約逸脱、テスト命名ルール違反、可読性) | 原則今回対応する |
| 🟢 info | 参考情報・質問・提案 | 対応は任意 |

# フィードバックのテンプレート

```markdown
## コードレビュー結果: <承認(指摘なし) / 要修正(🔴n件・🟡n件・🟢n件)>

### 対象
feature/<機能名> の変更差分

### 良い点
- (必ず1つ以上)

### 指摘事項
| # | 重要度 | 対象 | 指摘内容 | 根拠 |
|---|---|---|---|---|
| 1 | 🔴 must | apps/notes-api/application/xxx.py:42 | ... | ... |

### 動作確認(UI変更がある場合は必須。ない場合はこの欄ごと省略)
- 確認したフロー: (例: DELETE /notes/{id} を呼び出し204が返ることを確認)
- 結果: 想定どおり / 問題あり(→指摘事項の#nを参照)

### 次のステップ
- 🔴/🟡あり → /resolve で修正し、再レビューを受ける
- 指摘なし(🟢のみ) → /pr で実装PRを作成する
```
