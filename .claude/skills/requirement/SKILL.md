> ワークフロー上の位置: [/consult](../consult/SKILL.md)(任意) → **/requirement(本Skill)** → [/design](../design/SKILL.md)

> **次フェーズのモデル(/design):** requirements.mdのビジネスルール複雑度に基づいて選ぶ
> - 複数の条件・計算ロジック・外部仕様が複雑に絡む場合: **Opus** (複数ルール間の関連性・矛盾検出・落ちがある要件の発見が重要)
> - 標準的な要件(条件は3〜5個程度、ロジックは単純): **Sonnet**
> - シンプルな要件(ルーティング変更・文言修正など): **Sonnet**

> 別の機能の作業(承認待ちを含む)が進行中のまま本Skillを始める場合は、先に[parallel-work](../parallel-work/SKILL.md)(worktreeによる並行作業)を確認する。

# 開始時: JIRAチケットの確認

Step0より前に、`~/.claude/jira-ticket-check.md`(グローバル方針)を読み、その手順に従って対応するJIRAチケットの有無を確認する(studyでの詳細な背景は`specs/jira-automation/requirements.md`参照)。[/fix](../fix/SKILL.md)でも同様にこの節を維持する。

# Step0 入口の判断: 新規spec作成 vs 既存spec更新

機能に着手する前に、新しい`apps/<アプリ名>/specs/<機能名>/`フォルダを作るか、既存specを更新するかをまず判断する。ここを誤ると、既存機能の修正が別機能のspecとして切り出され、同じビジネスルールが複数のrequirements.mdに分散してしまう。

新規specフォルダを作る前に、他のworktree・他のセッションで同じ/重複する機能が既に進行中でないかを確認する(手順は[parallel-work](../parallel-work/SKILL.md)の「他セッションとの重複を避ける」を参照。worktreeを使っていない・並行作業の予定がない場合でも、他セッションの存在に心当たりがなければこの確認は省略してよい)。

**既存specを更新すべきサイン**(いずれか1つでも該当したら新規フォルダを作らず[/fix](../fix/SKILL.md)のフローへ切り替える):
- 既存のユーザーストーリー・機能要件・ビジネスルールの一部を書き換える/追記するだけで説明が済む
- 実装が既存specの対象ファイル・関数を修正するものである(新しいファイルの追加だけで完結しないなら既存spec寄り)
- 機能名が「〜への〜追加」「〜の修正」のように既存機能名や既存の入出力を前提にしている(強いシグナル)
- 既存specの「スコープ外」にあった項目に今回対応する、または既存の不具合を直す

**新規specを作るべきサイン**(本Skillで進める):
- 新しいエンドポイント・新しい画面・独立してリリース/ロールバックできる機能である
- 既存のユーザーストーリーでは説明できない、新しい利用者視点の目的がある
- 別のドメイン・別のデータストアなど、技術的に独立した関心事である

> 「新規specを作るべきサイン」の3項目は[/fix](../fix/SKILL.md)のStep1に要約が転記されている(/fix単体で判断を完結させ、本Skillの読み込みを省くため)。変更時は両方を更新する。

# 新規アプリ立ち上げ時のspec分割

新しいアプリに着手するときは、要件を1つの巨大なspecフォルダにまとめない。まず利用者視点のユーザーストーリー(「〜としては、〜したい」)を洗い出し、**1ストーリー=1specフォルダ**を原則に`apps/<アプリ名>/specs/<機能名>/`を縦に分割して作る。

- 洗い出したストーリーの数だけ`apps/<アプリ名>/specs/<ストーリーを表す機能名>/`を並べて作る(例: 注文管理APIなら`order-creation`(注文作成)、`order-cancellation`(注文キャンセル)、`order-history`(注文履歴)のように分ける)
- 複数のストーリーの結果を1つのレスポンス・画面にまとめる統合ロジックが必要な場合は、新たに統合専用specを作らず、その統合先(最終的に呼び出し元が使うエンドポイント・画面)を担当するstory specに書く。他のstory specの機能要件には「この結果は`<まとめ先の機能名>`で使われる」と一言添えて依存関係を明示する
- アプリ立ち上げ時は`apps/<アプリ名>/specs/architecture.md`も最初から作成する(作成基準・書き方は[architecture-workflow](../architecture-workflow/SKILL.md)を参照)。機能一覧表(機能マップ)の状態列は全spec「仕様のみ(未実装)」で初期化する
- あわせてリポジトリ直下[README.md](../../../README.md)の「アプリ一覧」テーブルに1行追加する(アプリ名・パス・概要・architecture.mdへのリンク)
- 各specが育ってきて「既存機能の修正・拡張」に該当する変更が発生したら、以降は上記Step0の判断に従う

# 要件ヒアリング

requirements.mdを書き始める前に、以下の4項目が**すべて**確認できているかを確認し、足りないものはユーザーに質問して埋める。

- 誰・何のための機能か(ユーザーストーリーの主語、または呼び出し元システム)
- 何ができればよいか(入出力・レスポンス・画面の完成イメージ)
- ビジネスルールと根拠(数値・条件は法令・公式資料・既存の意思決定などの出典とセットで確認する)
- 今回やらないこと(スコープ外)

**聞き方**: 一度に全部聞かず、重要な順に1〜2項目ずつ質問する。回答を受け取ったら、残りの項目がまだ埋まっていないか都度確認し、埋まっていなければ続けて質問する(往復して構わない)。ユーザーの最初のメッセージだけで書き始めず、4項目が出揃うまでrequirements.mdの作成に進まない(未確認のまま推測で埋めてよいのは[/autopilot](../autopilot/SKILL.md)の推測マーカー運用が対象とする設計の細部のみで、この4項目は対象外)。

**新しい画面を追加する場合**: 「何ができればよいか」の確認で新しい画面・表示の追加が分かったら、文章だけで質問を返さない。ラフなワイヤーフレーム(テキスト/ASCIIで十分、Figma等の外部ツールは使わない)を、レイアウトの方向性が異なる**3パターン**のレイアウト案として作成し、AskUserQuestionの`preview`機能で並べて提示してから選んでもらう。画面イメージのすり合わせは文言だけのやり取りよりユーザーとの認識のズレを防げる。`/consult`で機能全体を壁打ち済みで、その中で画面イメージに触れていた場合でも、この工程は省略しない(会話ベースの合意はワイヤーフレーム+AskUserQuestionでの選定の代わりにならない)。

# 仕様書は「最新仕様のみ」を書く(恒久ルール)

requirements.md / design.md / architecture.md には、**常に今の正しい仕様だけを現在形で書く**。仕様を書き換えるときは差分として追記せず、**あたかも最初からその仕様だったかのように書き直す**(仕様書を読む人が知りたいのは「今どうなっているか」だけで、そこに至る経緯ではない。差分の痕跡が残るほど、後任・第三者が現状を読み取るコストが上がる)。

**書かないもの**:

- 変更の経緯・履歴 —「〜から〜に変更した」「旧〜」「移設した」「廃止した」「撤去」などの差分ナラティブ
- 移設・変更を示すマーカー — 例:「【〜で移設】」
- 内輪のコードネーム・呼称 — 第三者・後任が読んで意味が分からない語。例:「方向B」
- 合意日付などセッション固有の言い回し — 例:「2026-08-19合意」

**経緯・決定理由が必要な場合はADRに分離する。** 仕様書には書かず、ADR(Architecture Decision Record)にまとめ、仕様書からは必要ならリンクだけを張る。置き場所と採番は[architecture-workflow](../architecture-workflow/SKILL.md)の「ADRの置き場所」を参照する。

# requirements.mdの書き方

「何を作るか(WHAT)」「なぜその仕様にしたか(根拠)」を言語化する。数式・変数名は使わず日本語の言葉で書く(正確な計算式・スキーマはコードとテストに委ねる)。技術的な実装方法(HOW)はここでは書かない。

タイトル直下に `> ステータス: 仕様確認中(未実装)` という行を入れる(この行の意味と削除タイミングは[/pr](../pr/SKILL.md)の仕様承認ゲートを参照)。

以下の見出しをテンプレートとして使う(サマリ・ユースケース図の扱いは各見出しの説明を参照。それ以外で該当しないものは省略してよい)。

0. **サマリ(必須)** — 時間がない人がこの章だけで概略をつかめるようにする短い要約。`##`見出しでファイル先頭(タイトル・ステータス行の直後)に置く。3〜5行程度で「誰の何を解決するか・今回の主要なビジネスルール1〜2点・スコープ外の要点」を書き、下の「ユースケース図」へのリンクを添える。下の「概要」(機能名・目的・優先度)とは役割が違う(概要はメタ情報、サマリは中身のTL;DR)。物量が増えても、まずここだけ読めば判断できる状態を保つ
1. **概要** — 機能名・目的・優先度
2. **ユーザーストーリー** — 「〜としては、〜したい」という利用者視点の要求
3. **ユースケース図(必須相当)** — このspecの利用者(アクター。人だけでなく呼び出し元システム・定期実行トリガーなども含む)と、その人/システムができること(ユースケース)をMermaidで俯瞰する。ユーザーストーリー・機能要件が文章としての正であり、図はその俯瞰(下記「ユースケース図の書き方」参照)。単一のアクターが1つの自明なユースケースを行うだけ(図にする意味がない)と検討の上で判断した場合のみ、その理由を一言添えて省略してよい(安易に省略しない)
4. **機能要件** — 実装する機能と入出力を言葉で説明する
5. **ビジネスルール・制約** — 数値・条件などのルールと、その根拠(法令・公式資料・既存の意思決定など)を必ずセットで書く。特殊な入力やエラー時にどう振る舞うべきかも、条件付きのルールとしてこの見出しの中に書く(例:「該当データが存在しない場合、404を返す」)。項目が複数ある場合は`###`見出しで分ける(テストとの対応付けがしやすくなる)
6. (任意)**非機能要件・依存関係・制約条件・UI/UX要件** — 関係する場合のみ書く。無理に埋めない。
   依存関係を書く際、他specの機能要件・ビジネスルールの入出力をそのまま使う場合は内容を書き写さず、`<spec名>/requirements.md#見出し-n`の形で参照する(書き写すと元specが変更されたときに追随できなくなる)

## 会話ドリブン原則(推測で埋めない)

requirements.mdに書く方針は、サマリ・任意項目(非機能要件・UI/UX要件など)も含め、**要件ヒアリングまたは[/consult](../consult/SKILL.md)の会話の中で確認したもの・こちらから提案して合意したものだけを書く**。会話に出ていない方針を推測で埋めない。判断に迷う点が残ったら、書き切る前にユーザーに確認するか、少なくとも提案の形で認識合わせをしてから記載する。つまりrequirements.mdは「会話で合意したことがドキュメントになっているだけ」の状態を目指す(未確認のまま推測で埋めてよいのは[/autopilot](../autopilot/SKILL.md)の推測マーカー運用が対象とする設計の細部のみで、要件の方針はその対象外)。

## ユースケース図の書き方(Mermaid)

- 図はMermaidコードブロックとして「ユースケース図」見出しに直接埋め込む(専用ファイル・画像は作らない)。アクター(利用者・呼び出し元システム・定期実行トリガー)とユースケースの関係を描く(`flowchart LR`でアクター→ユースケースを線でつなぐ形で十分。厳密なUML記法にこだわらない)
- **図は文章を置き換えない。** ユーザーストーリー・機能要件が正、図は俯瞰用の補助。`[n]`採番・テストとの対応付けの対象は従来どおり文章側
- ノード名・ラベルは業務的な言葉にする/1行1エッジ/図の直後に正となる文章(ユーザーストーリー・機能要件)へのリンクを置く/**エッジラベルに半角括弧を書かない**([architecture-workflow](../architecture-workflow/SKILL.md)の「Mermaidの書き方ルール」に従う)

## [n]採番ルール

機能要件・ビジネスルール・制約など、個別にテストを対応させたい箇条書きには見出し内で連番の`[n]`を振る(見出しが変わればまた`[1]`から振り直してよい、グローバルな採番ではない)。

```markdown
### ノート削除API
- [1] 対象: 自分が作成したノートのみ
- [2] 挙動: 対象ノートが存在しない場合は404を返す
- [3] 挙動: 削除に成功した場合は204を返す
```

概要・ユーザーストーリー・スコープ外など、そもそもテスト対象にならない見出しには`[n]`を振らなくてよい(見出し単位でスキップ登録の対象になる)。

箇条書きは「〜の場合、〜になること」という文体に揃えておくと、そのままテストの`it()`に転記しやすい。

# 完了時の次ステップ案内

requirements.mdをユーザーに提示し、[/design](../design/SKILL.md)(設計・タスク分解)へ進むことを案内する。仕様が承認されるまでコード(テストを含む)は書き始めない。

既存アプリに新規specを追加した場合(アプリ立ち上げ時の一括作成ではない)も、そのアプリが`apps/<アプリ名>/specs/architecture.md`を持っていれば、機能一覧表に新しいspec行を状態「仕様のみ(未実装)」で追加し([architecture-workflow](../architecture-workflow/SKILL.md)の「更新タイミング」参照)、更新後の機能一覧表をこの完了報告に貼って提示する。

requirements.mdをコミットした時点で、compactや新しいセッションへの切り替えを行っても支障はない。新しいセッションの名称と、次のセッションにそのまま貼り付けられるプロンプトを、1行目=名称・2行目=プロンプトの単一のコードブロックとして毎回提示してから終える(名称とプロンプトを分けて提示しない。「セッションを閉じても大丈夫」とだけ述べて済ませない。名称は<機能名>に次工程名を()で添えた形):

```
<機能名>(設計)
/design を実行してください。対象は apps/<アプリ名>/specs/<機能名>/、ブランチ feature/<機能名> です。
```
