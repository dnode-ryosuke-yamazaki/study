# architecture.mdとは何か

`apps/<アプリ名>/specs/architecture.md` は、そのアプリ配下の複数specにまたがる全体像を1箇所に集約するドキュメント。以下と役割分担する(重複させない)。

| ドキュメント | 担当範囲 |
|---|---|
| CLAUDE.md | プロジェクト全体で共通のフォルダ規約・コーディング規約 |
| `doc/adr/` | 複数アプリにまたがる技術選定とその理由(DB・ホスティング・認証基盤など) |
| `apps/<アプリ名>/specs/adr/` | そのアプリ内だけで完結する設計判断とその理由・経緯(後述「ADRの置き場所」) |
| `doc/architecture/` | リポジトリ共通のクラウド・インフラ系の図(インフラ構成図・デプロイメント図など。後述) |
| `apps/<アプリ名>/specs/<機能名>/requirements.md`・`design.md` | 1つの機能(spec)固有の要件・処理フロー・DB項目・セキュリティ |
| `apps/<アプリ名>/specs/architecture.md` | このアプリ配下の複数specをまたぐ全体像(機能マップ・依存関係・このアプリが使うADR/外部サービスの一覧) |

architecture.mdは**参照のハブ**であり、他ドキュメントの内容を転記する場所ではない。技術選定の理由はADRへ、機能ごとの詳細はrequirements.md/design.mdへリンクするだけに留める。「architecture.mdだけ読めばそのアプリの全体を把握できる」ことを目標とする。このためアプリ単位のREADMEとは役割を分け、アプリ概要・構成図・機能マップ・関連設計書リンクはarchitecture.mdが担い、`apps/<アプリ名>/README.md`はセットアップ方法・開発コマンド(テスト・lint・build)に絞る(両方に構成図を置くと二重管理になり「図だけが古くなる」事故の温床になる)。

# いつ作る/更新するか

- 新しいアプリに着手するタイミングで、[/requirement](../requirement/SKILL.md)の「新規アプリ立ち上げ時のspec分割」と合わせて最初から作成する(具体的なspecが1つしかない段階でも作ってよい。後から待つ必要はない)
- 既存アプリでarchitecture.mdがまだない場合、2つ目以降のspecに着手するタイミングで作成する
- 新規specフォルダの作成・廃止、既存specの依存関係の変化があったときは、[/fix](../fix/SKILL.md)の「仕様(3点セット)への影響を洗い出す」の一環として、機能マップを更新する
- アプリ固有の採用技術・外部サービス・ディレクトリ構成が変わったときも同様に更新する

# 仕様書は「最新仕様のみ」を書く(恒久ルール)

requirements.md / design.md / architecture.md には、**常に今の正しい仕様だけを現在形で書く**。仕様を書き換えるときは差分として追記せず、**あたかも最初からその仕様だったかのように書き直す**(仕様書を読む人が知りたいのは「今どうなっているか」だけで、そこに至る経緯ではない。差分の痕跡が残るほど、後任・第三者が現状を読み取るコストが上がる)。

**書かないもの**:

- 変更の経緯・履歴 —「〜から〜に変更した」「旧〜」「移設した」「廃止した」「撤去」などの差分ナラティブ
- 移設・変更を示すマーカー — 例:「【〜で移設】」
- 内輪のコードネーム・呼称 — 第三者・後任が読んで意味が分からない語。例:「方向B」
- 合意日付などセッション固有の言い回し — 例:「2026-08-19合意」

**経緯・決定理由が必要な場合はADRに分離する。** 仕様書には書かず、ADRにまとめ、仕様書からは必要ならリンクだけを張る(architecture.mdなら「12. 関連ADR」、design.mdなら該当見出しから)。

# ADRの置き場所(判断の範囲で使い分ける)

ADR(Architecture Decision Record)は、決定に至った背景・理由・トレードオフを残す場所。仕様書から追い出した経緯はここに集める。

| 判断の範囲 | 置き場所 | 採番 |
|---|---|---|
| 複数アプリにまたがる技術選定・方針(DB・ホスティング・認証基盤・CI基盤・リポジトリ構成など) | `doc/adr/` | リポジトリ全体で連番(既存の最大値+1、4桁) |
| 特定のアプリ内だけで完結する判断 | `apps/<アプリ名>/specs/adr/`(そのアプリのarchitecture.mdと同じ階層) | **アプリごとに`0001`から**独立採番 |

- 迷ったら「他のアプリがこの判断を参照しうるか」で決める。参照しうるなら`doc/adr/`
- ファイル名は`NNNN-短いタイトル.md`。構成は`ステータス` / `コンテキスト` / `決定` / `影響`(`doc/adr/README.md`の書き方に揃える)
- 決定を覆す場合も既存ファイルを書き換えず、新しいADRを追加して旧ADRのステータスを`Superseded by NNNN`に更新する(**ADRだけは履歴を残す場所**。仕様書と役割が逆である点に注意)
- `doc/adr/`に追加したら`doc/adr/README.md`の一覧に、アプリ配下に追加したらそのアプリのarchitecture.md「12. 関連ADR」に、それぞれ行を足す

# 図の運用方針(AI駆動開発向け)

設計図は「人が理解するため」だけでなく「AIが理解・保守しやすいこと」を最優先する。

- 論理構造の図はMermaidコードブロックとして`specs/`配下の既存Markdownに直接埋め込む(専用ファイル・画像は作らない)。Git差分・レビュー・AIによる更新と親和させるため
- **図は日本語の文章を置き換えない。** 処理フロー等の文章が正であり、図は俯瞰用の補助。`[n]`採番・テストとの対応付けの対象は従来どおり文章側
- **各図種は必須相当**(design.mdの必須見出しと同じ運用)。下表の作成条件に該当する箇所が一つでもあれば、原則その図を描く。該当する箇所が一つもない、と一旦立ち止まって検討した上で判断した場合のみ、その理由を一言添えて省略してよい(安易に省略しない)。一方で、条件に該当しない箇所へ無理に図を足す必要はない(全処理・全画面への一律付与は求めない)

## 論理構造の図の一覧(Mermaid・specs/配下に埋め込み)

これらは要件定義〜設計〜アーキテクチャを通じて、時間がない人でも全体像を図で追えるようにするための図。作成条件を満たす箇所があれば必須相当で描く。

| 図 | 記載先 | 作成条件(満たす箇所があれば必須相当) |
|---|---|---|
| ユースケース図 | requirements.md「ユースケース図」([/requirement](../requirement/SKILL.md)参照) | 利用者(アクター)とできること(ユースケース)がある機能。単一アクター×自明な1ユースケースのみなら省略可 |
| コンテキスト図 | architecture.md「4. コンテキスト図」 | 全アプリ(テンプレどおり必須)。本アプリ・利用者・外部サービスの境界を1枚で |
| システム構成図 | architecture.md「5. システム構成図」 | 全アプリ(テンプレどおり必須) |
| コンポーネント図 | architecture.md「9. コンポーネント図」(機能一覧表の直後) | 複数specにまたがるモジュール・共通ライブラリ間の依存があるとき |
| ER図 | architecture.md「11. 外部サービス」内(アプリ横断)。spec単位のカラム/属性表(design.md)は現行どおり | アプリの使用テーブルが2つ以上、またはリレーションが生まれたとき |
| シーケンス図 | design.md「処理フロー」配下([/design](../design/SKILL.md)参照) | 呼び出し元・API・DB・外部サービスなど複数アクター間のやり取りがある処理があるとき |
| 画面遷移図 | design.md「画面設計」配下([/design](../design/SKILL.md)参照) | 画面が複数、または画面内で表示が大きく切り替わる(入力→確認→完了など)とき |
| 状態遷移図 | design.md「状態管理」([/design](../design/SKILL.md)参照) | 状態が3つ以上、または遷移に条件分岐があるとき |

## Mermaidの書き方ルール

- ノード名・ラベルは業務的な言葉にする([/design](../design/SKILL.md)の処理の呼び名の規則と同じ。関数名を図に書かない)
- 差分レビューしやすく書く: 1行1エッジ、ノード定義とエッジ定義を分ける、意味のないリネームをしない
- 図の直後に、その図が表す内容の正となる文章・specへのリンクを置く
- **1図の可読サイズを超えたら分割する**: 1つの図は**ノード10個・エッジ12本以内**を目安にする(人が一目で追える「7±2」の上限側)。これを超えるシステム構成図は、1枚に詰め込まず、まず全体像の**俯瞰図**を1枚置き、続けて**利用シーン/フロー単位**の詳細図に分ける(各見出しは`### 4.1 …`のように節番号配下のサブ見出しにする)。各詳細図も同じ上限に収める。レイヤ(クライアント/API/データ/外部)での分割は、フローがレイヤを縦断するアプリでは各図の意味が薄くなるため、フロー単位を第一候補とする
  - **このサイズ上限は構成/構造図(システム構成図・コンポーネント図・コンテキスト図・ER図)に適用する。** 開発工程の端から端までを1枚で見せる**プロセス/ワークフロー遷移図**(例: [.claude/skills/README.md](../README.md)のSkill遷移図)は、パイプライン全体を一望できること自体が価値なので、ノード10を超えても機械的に分割しない(分割するとかえって流れが追えなくなる)。プロセス図はサイズ上限の対象外とする
- **エッジラベルに半角の括弧類 `()[]{}<>` を書かない**: Mermaidがノード形状の開始と誤認して描画エラー(`Parse error … got 'PS'`等)になり、図全体が表示されなくなる。全角 `()` を使うか、ノードラベルと同様に `"…"` で括る(ノードラベルは `["…"]`・`[("…")]` で括られているため半角括弧でも壊れない)
  - **このリポジトリには図の描画をCIで検査する仕組みが無い**(ルートに`package.json`が無く、lintジョブも持たない)。したがって半角括弧の混入は自動では検出されない。図を書いた後は、**GitHub上でその図が実際に描画されるか(赤いParse errorが出ないか)を必ず目視で確認する**。PRを出す前にVSCodeのMarkdownプレビューで確認しておくとやり直しが減る

# 見出しテンプレート

`apps/<アプリ名>/specs/architecture.md` は以下の見出しで構成する。サマリ・機能一覧表・コンテキスト図・システム構成図は必須(それ以外で該当しない見出しは省略してよい。無理に埋めない)。

0. **サマリ(必須)** — 時間がない人がこの章だけでアプリの全体像をつかめる短い要約。`##`見出しでファイル先頭に置く。アプリが何をするか1行・主要技術・機能一覧表の規模(specがいくつ・何ができるアプリか)・下の「コンテキスト図」「システム構成図」へのリンクを短くまとめる。下の「概要」(1〜2行のメタ情報)とは役割が違う(サマリは中身のTL;DR)
1. **概要** — アプリが何をするアプリか、1〜2行で
2. **アーキテクチャの目的** — このアプリ固有の目的のみ(プロジェクト全体の一般論はCLAUDE.mdの担当)
3. **設計方針** — このアプリだからこそ追加で効いてくる方針のみ(CLAUDE.mdの共通方針は書かない)
4. **コンテキスト図(必須)** — Mermaidコードブロックで書く。本アプリを中心に、利用者(アクター)・依存する外部サービス・他アプリとの境界を1枚で俯瞰する(システムの内部構造は描かず、外との関係に絞る)。下の「システム構成図」が内部構成、この図が外部境界、という役割分担
5. **システム構成図(必須)** — Mermaidコードブロックで書く(既存のASCIIアートは触るタイミングでMermaidに置換する)。このアプリから見た構成のみを描き、リポジトリ共通インフラの詳細は`doc/architecture/`へリンクする(汎用テンプレートをそのまま貼らない)
6. **アーキテクチャ概要** — 上の図を文章で説明(この文章が正、図は補助)
7. **採用技術** — このアプリが実際に使っている技術のみ。選定理由はADRへのリンクで済ませ再掲しない
   ```markdown
   | 技術 | 用途 |
   |---|---|
   ```
8. **機能一覧表(機能マップ)(必須)** — このアプリ配下のspecフォルダ一覧と、利用者から見た機能名・役割・依存関係・進捗状態。「このアプリで何ができるか」と「今どこまで進んでいるか」を一覧できる中核の必須見出しで、全specを漏れなく載せる(新規specの追加・廃止時は必ずここを更新する)。architecture.mdをまだ持たない単一specアプリの段階では、requirements.mdのサマリ章の機能要点がこれを兼ねる
   ```markdown
   | spec | 機能(利用者から見て) | 役割 | 依存 | 状態 |
   |---|---|---|---|---|
   | note-creation | ノートを作成する | ノートをDBに登録する | - | リリース済み |
   | note-deletion | ノートを削除する | 自分のノートを削除する | note-creationで作られたノートを参照 | 実装中 |
   ```
   **状態列の値(3段階)**: 「仕様のみ(未実装)」→「実装中」→「リリース済み」。リリース済みのspecにバグ修正・改修で再度手が入ったら「実装中」に戻し、本番反映の確認が済んだ時点で「リリース済み」に戻す。

   **更新タイミング**(複数specにまたがる開発で、1セッション単位の作業が終わるたびに全体進捗を追えるようにするための仕組み):

   | タイミング | 更新後の状態 | 担当Skill |
   |---|---|---|
   | 新規specフォルダ作成(requirements.md新規作成)時 | 仕様のみ(未実装) | [/requirement](../requirement/SKILL.md) |
   | 仕様承認PRのマージ済みを確認して実装に着手する時 | 実装中 | [/implementation](../implementation/SKILL.md) |
   | 実装PRのマージ後、本番反映の確認が済んだ時 | リリース済み | [/pr](../pr/SKILL.md)の完了時案内 |

   architecture.mdを持つアプリ(複数specにまたがる規模と判断済み)でこれらのタイミングを迎えたら、機能マップの該当spec行の状態を更新してコミットに含めるだけでなく、**更新後の機能マップ全体(表)をその工程の完了報告にそのまま貼って提示する**(ファイルを直すだけで済ませない。セッションを閉じる前にユーザーがチャット上で全体進捗を把握できることが目的)。architecture.mdを持たないアプリ(単一spec)ではこの運用自体が不要。
9. **コンポーネント図**(複数specにまたがるモジュール・共通ライブラリ間の依存があるときのみ) — Mermaidで、spec横断で共有されるモジュールの依存関係を描く。機能一覧表の「依存」列が文章としての正であり、図はその俯瞰
10. **ディレクトリ構成** — `apps/<アプリ名>/`配下がCLAUDE.mdの一般規約(infra/application)から逸脱・追加している部分のみ。逸脱がなければ「CLAUDE.mdの規約通り」の一言で済ませる
11. **外部サービス** — このアプリが実際に依存する外部サービス(使用テーブル名など)。選定理由は書かず関連ADRへリンクする。使用テーブルが2つ以上、またはリレーションが生まれたら、この見出しにアプリ横断のER図(Mermaid `erDiagram`)を置く(spec単位の属性表はdesign.mdの現行どおりで、そちらが正)
    ```markdown
    | サービス | 用途 |
    |---|---|
    ```
12. **関連ADR** — このアプリが依存するADRのリンクのみ列挙する(内容は転記しない)。リポジトリ共通の`doc/adr/`と、このアプリ配下の`adr/`の両方を載せる
    ```markdown
    - [0001-multi-app-monorepo-layout.md](../../../doc/adr/0001-multi-app-monorepo-layout.md) — モノレポ構成の方針
    - [adr/0001-dynamodb-key-design.md](adr/0001-dynamodb-key-design.md) — このアプリのキー設計を単一テーブルにした理由
    ```
13. **セキュリティ** — このアプリ固有のリスクのみ(IAM等の横断的な仕組み自体はADR参照)
14. **技術的制約** — このアプリ固有の制約のみ(プロジェクト全体の制約はADR/CLAUDE.mdの担当)
15. **用語集** — このアプリのドメイン特有の用語のみ(汎用IT用語は書かない)

## 会話ドリブン原則(推測で埋めない)

architecture.mdに書く方針(アーキテクチャの目的・設計方針・採用技術・外部サービス・機能一覧表の役割/依存など)も、[/consult](../consult/SKILL.md)・[/requirement](../requirement/SKILL.md)・[/design](../design/SKILL.md)の会話の中で確認したもの・こちらから提案して合意したものだけを書く。会話に出ていない技術選定・構成方針を推測で埋めない(新規アプリ立ち上げ時に一気に作る場合も、主要な採用技術・外部サービスは提案の形で認識合わせしてから記載する)。

# クラウド・インフラ系の図(doc/architecture/)

クラウドサービスを1つでも使っている場合、以下をリポジトリ共通ドキュメントとして`doc/architecture/`に作成する(アプリ単位ではなくリポジトリ単位。ルートREADMEからリンクする)。

| 図 | 内容 | 記載先 | 作成条件 |
|---|---|---|---|
| インフラ構成図 | 使用している全クラウドサービスと役割・データの流れ・課金/無料枠の境界 | `doc/architecture/infrastructure.md` | クラウドサービスを使っていれば必須 |
| デプロイメント図 | mainマージから本番反映までの経路(CI・ビルド・デプロイ先) | `doc/architecture/deployment.md` | デプロイパイプラインがあれば必須 |
| ネットワーク構成図 | VPC・サブネット・通信経路・境界 | `doc/architecture/network.md` | ネットワーク境界を自分で設計している場合のみ(VPC、プライベート接続、独自DNS/CDN経路の制御など)。フルマネージドサービスの利用だけなら不要(インフラ構成図が兼ねる) |

## 形式の選択

- 構成が単純なうち(サービス数が少なく、配置・アイコンに意味がない)はMermaidで上記.mdに埋め込む
- AWS/GCP等でアイコン・レイアウト・境界の表現に意味が出てきたらDraw.ioへ昇格する:
  - `doc/architecture/<名前>.drawio` を正本とし、README掲載用SVG・資料用PNGを同名で出力する
  - drawio CLIのセットアップと出力手順をADRとして残す(このサンドボックスではCLIの追加インストールにネットワークが必要で実行できないため、手順の実行はユーザーの手元で行う)
  - README・architecture.mdにはSVGを掲載する(PNGは資料・プレゼン用)
- 昇格の要否は[/retrospective](../retrospective/SKILL.md)の図のスポットチェックで見直す

# 更新ルール(図だけが古くなることの禁止)

設計変更時は、要件定義・設計書・Mermaid図・(あれば)Draw.io図・READMEを**同じPRで同期する**。同期の確認ポイントは各工程Skillに組み込まれている:

- [/design](../design/SKILL.md)「architecture.mdへの反映」: 機能一覧表(機能マップ)に加え、コンテキスト図・システム構成図・コンポーネント図・ER図への影響も確認する
- [/fix](../fix/SKILL.md)「仕様(3点セット)への影響を洗い出す」: 図の同期チェックを含む
- [/spec-review](../spec-review/SKILL.md)チェックリスト: 図が本文・コードと矛盾していないかを確認する
- [/retrospective](../retrospective/SKILL.md): 直近のPRで触ったアプリの図と実態の乖離をスポットチェックする(`doc/architecture/`含む)
- インフラ・デプロイ構成を変えるPR(Terraform変更・CI変更・外部サービス追加)では、`doc/architecture/`の該当図を同じPRで更新する

# 書く際の注意

- 各見出しは「このアプリに関連するものだけ」を書く。プロジェクト全体・複数アプリ共通の内容を見つけたら、architecture.mdに書かずCLAUDE.mdまたは`doc/adr/`側の更新を検討する
- 機能マップの「依存」列と、依存元specのrequirements.mdの依存関係見出しが矛盾しないか確認する(architecture.mdは索引であり、依存の詳細はspec側の`[n]`参照が正)
- architecture.mdはrequirements.mdのような`[n]`採番・仕様承認ゲートの対象外
