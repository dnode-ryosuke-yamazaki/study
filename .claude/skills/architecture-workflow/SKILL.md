# architecture.mdとは何か

`apps/<アプリ名>/specs/architecture.md` は、そのアプリ配下の複数specにまたがる全体像を1箇所に集約するドキュメント。以下と役割分担する(重複させない)。

| ドキュメント | 担当範囲 |
|---|---|
| CLAUDE.md | プロジェクト全体で共通のフォルダ規約・コーディング規約 |
| `doc/adr/` | 複数アプリにまたがる技術選定とその理由(DB・ホスティング・認証基盤など) |
| `apps/<アプリ名>/specs/<機能名>/requirements.md`・`design.md` | 1つの機能(spec)固有の要件・処理フロー・DB項目・セキュリティ |
| `apps/<アプリ名>/specs/architecture.md` | このアプリ配下の複数specをまたぐ全体像(機能マップ・依存関係・このアプリが使うADR/外部サービスの一覧) |

architecture.mdは**参照のハブ**であり、他ドキュメントの内容を転記する場所ではない。技術選定の理由はADRへ、機能ごとの詳細はrequirements.md/design.mdへリンクするだけに留める。

# いつ作る/更新するか

- 新しいアプリに着手するタイミングで、[/requirement](../requirement/SKILL.md)の「新規アプリ立ち上げ時のspec分割」と合わせて最初から作成する(具体的なspecが1つしかない段階でも作ってよい。後から待つ必要はない)
- 既存アプリでarchitecture.mdがまだない場合、2つ目以降のspecに着手するタイミングで作成する
- 新規specフォルダの作成・廃止、既存specの依存関係の変化があったときは、[/fix](../fix/SKILL.md)の「仕様(3点セット)への影響を洗い出す」の一環として、機能マップを更新する
- アプリ固有の採用技術・外部サービス・ディレクトリ構成が変わったときも同様に更新する

# 見出しテンプレート

`apps/<アプリ名>/specs/architecture.md` は以下の見出しで構成する。該当しない見出しは省略してよい(無理に埋めない)。

1. **概要** — アプリが何をするアプリか、1〜2行で
2. **アーキテクチャの目的** — このアプリ固有の目的のみ(プロジェクト全体の一般論はCLAUDE.mdの担当)
3. **設計方針** — このアプリだからこそ追加で効いてくる方針のみ(CLAUDE.mdの共通方針は書かない)
4. **システム構成図** — このアプリが実際に使うコンポーネントのみの図。プロジェクト共通のインフラも含めてよいが、実際の構成に合わせる(汎用テンプレートをそのまま貼らない)
5. **アーキテクチャ概要** — 上の図を文章で説明
6. **採用技術** — このアプリが実際に使っている技術のみ。選定理由はADRへのリンクで済ませ再掲しない
   ```markdown
   | 技術 | 用途 |
   |---|---|
   ```
7. **機能マップ** — このアプリ配下のspecフォルダ一覧と役割・依存関係。architecture.mdの中核であり必須見出し
   ```markdown
   | spec | 役割 | 依存 |
   |---|---|---|
   | note-creation | ノートを作成する | - |
   | note-deletion | ノートを削除する | note-creationで作られたノートを参照 |
   ```
8. **ディレクトリ構成** — `apps/<アプリ名>/`配下がCLAUDE.mdの一般規約(infra/application)から逸脱・追加している部分のみ。逸脱がなければ「CLAUDE.mdの規約通り」の一言で済ませる
9. **外部サービス** — このアプリが実際に依存する外部サービス(使用テーブル名など)。選定理由は書かず関連ADRへリンクする
   ```markdown
   | サービス | 用途 |
   |---|---|
   ```
10. **関連ADR** — このアプリが依存する`doc/adr/`のリンクのみ列挙(内容は転記しない)
    ```markdown
    - [0001-multi-app-monorepo-layout.md](../../../doc/adr/0001-multi-app-monorepo-layout.md) — モノレポ構成の方針
    ```
11. **セキュリティ** — このアプリ固有のリスクのみ(IAM等の横断的な仕組み自体はADR参照)
12. **技術的制約** — このアプリ固有の制約のみ(プロジェクト全体の制約はADR/CLAUDE.mdの担当)
13. **用語集** — このアプリのドメイン特有の用語のみ(汎用IT用語は書かない)

# 書く際の注意

- 各見出しは「このアプリに関連するものだけ」を書く。プロジェクト全体・複数アプリ共通の内容を見つけたら、architecture.mdに書かずCLAUDE.mdまたは`doc/adr/`側の更新を検討する
- 機能マップの「依存」列と、依存元specのrequirements.mdの依存関係見出しが矛盾しないか確認する(architecture.mdは索引であり、依存の詳細はspec側の`[n]`参照が正)
- architecture.mdはrequirements.mdのような`[n]`採番・仕様承認ゲートの対象外
