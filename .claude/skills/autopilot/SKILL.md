> ワークフロー上の位置: [README.md](../README.md)の遷移図1(新機能開発)・遷移図2(バグ修正・既存機能改修)全体を貫く**モードSkill**。各工程の手順はすべて既存の工程Skillに従い、本Skillは「どこで止まり、どこを自走するか」だけを定める(手順の二重メンテをしない)

# このリポジトリでの前提(移植元との違い)

本Skillは別プロジェクト(benriyatool)の自動運転モードを、この環境の制約に合わせて縮小移植したもの。次の3点が移植元と異なる。

- **push・PR作成・CI確認・マージは自走の対象外。** このサンドボックスからGitHubへの通信は遮断されている(`~/.claude/sandbox-limitations.md`)。該当箇所ではコマンド一式をまとめて提示し、ユーザーの手元ターミナルでの実行結果の報告を待つ(下記「引き継ぎポイント」)。移植元にあった`gh pr merge`による自動マージは**採用しない**
- **委譲先のAgentは既存の4つのみ**(spec-reviewer / code-reviewer / implementer / impl-pr-reviewer)。移植元が使うdesigner・resolver・release-checkerはこのリポジトリに存在しないため、**設計([/design](~/.claude/skills/design/SKILL.md))とレビュー指摘対応([/resolve](~/.claude/skills/resolve/SKILL.md))はメインスレッドが自分で行う**
- **リリース確認工程(release-check)は無い。** 実装PRのマージ後は[/pr](~/.claude/skills/pr/SKILL.md)の完了時案内(本番反映の確認・ブランチ/worktreeの掃除)で終える

# 前提条件

- **小規模・低リスクの変更にだけ使う。** 課金・請求に関わる計算、個人情報の扱いが変わる変更、本番インフラ(Terraform)の破壊的変更、影響範囲の読めない変更には使わない(通常フローで工程ごとに確認する)。対象として適切か迷ったら、自走を始める前にユーザーに確認する
- **対象範囲**: 新機能([/requirement](~/.claude/skills/requirement/SKILL.md)起点)、または小規模なバグ修正・既存機能改修([/fix](~/.claude/skills/fix/SKILL.md)起点)。[/fix](~/.claude/skills/fix/SKILL.md)のStep1で「新規spec作成が必要」と判定された場合は、以降「フロー(新機能起点)」に合流する
- **JIRAチケットの確認は省略しない。** 起点の工程Skill(/requirement・/fix)が定めるJIRAチケット確認(`~/.claude/jira-ticket-check.md`)は対話①の中で通常どおり行う
- **推奨モデル: Sonnet。** メインスレッドのモデルはフロー途中で自動では切り替えられず、既存Skillの「次フェーズのモデル」運用(工程ごとに人が切り替える)がこのモードでは使えない。対象が小規模である前提なので、発動時(遅くとも自動運転宣言の時点)に`/model`でSonnetへ切り替えることを案内する

# 対話ポイントと引き継ぎポイント

自走を止める箇所は2種類ある。混同しないよう区別して扱う。

**対話ポイント(判断を仰ぐ・ユーザーの承認が要る)**

1. [/requirement](~/.claude/skills/requirement/SKILL.md)の要件ヒアリング、または[/fix](~/.claude/skills/fix/SKILL.md)の入口確認(設計の分かれ道になる事項の確認もここに含める。下記「ヒアリングの範囲」)
2. 仕様承認PRでの一括レビューと承認(複数回のやりとり可)

fix起点で仕様変更・スコープ判断のいずれも伴わない純粋なバグ・軽微な変更は、**対話なしで完走することがある**。

**引き継ぎポイント(環境制約。判断ではなく実行の代行を頼む)**

- `git push` / PR作成 / CI結果の確認 / マージ / マージ後の`git pull`
- 該当箇所では[/pr](~/.claude/skills/pr/SKILL.md)の共通ルールに従い、コピペ可能なコマンドブロック1つにまとめて提示し、実行結果(PRのURL・CI結果)の報告を待つ。**待っている間は「完了」と報告しない**(セッションを閉じてよいとも書かない)
- 報告を受けたら、そこから先の工程は再び自走する

# 任意の工程からの起動(途中からの自走)

[/requirement](~/.claude/skills/requirement/SKILL.md)・[/fix](~/.claude/skills/fix/SKILL.md)からの起動(下記「フロー」の最初から)が最も安全だが、それ以外の工程からも起動できる。「ここから自走して」のように、一部の工程が既に完了した状態で指示された場合がこれにあたる。

**起動前監査(必須)**: 起点より前のステップを飛ばして自走を始める前に、それらのステップが実際に満たされているかを、会話の記憶ではなく確認可能な証跡(gitコマンド・ファイル内容)で確認する。証跡で確認できない、または満たされていない項目があれば、**どの前提が欠けているためどんなリスクがあるかを具体的に列挙してから**、その項目だけユーザーに確認するか、通常ルール(このSkillの自動化を使わず都度人が確認する運用)にフォールバックする。「確認できないが恐らく大丈夫」で自走を始めない。

なお`gh pr list`・`git fetch`はこの環境では実行できないため、監査はローカルで完結する手段(`git log --all --oneline -- <パス>`・`git branch -a`・`git worktree list`・ファイルの内容確認)で行い、それで判断がつかない項目はユーザーに直接確認する。

| 起動する工程 | 確認する前提 | 満たされない場合のリスクと対応 |
|---|---|---|
| [/design](~/.claude/skills/design/SKILL.md) | 対象specの要件ヒアリング4項目(誰の・何ができる・ビジネスルール根拠・スコープ外)が会話で確認済みか。requirements.mdの記述だけでは、それが実際の会話に基づくか判別できない場合がある | [/requirementの会話ドリブン原則](~/.claude/skills/requirement/SKILL.md)に反したまま設計が進むリスク。確証が持てなければ4項目が埋まっているか確認し、埋まっていなければヒアリングからやり直す(対話①に合流) |
| [/spec-review](~/.claude/skills/spec-review/SKILL.md) | 3点セットが揃っているか。design.mdの必須見出し・必須相当の図が埋まっているか | 未完成の仕様をレビューに掛け、指摘なしのまま承認PRへ進むリスク。欠けていれば先に[/design](~/.claude/skills/design/SKILL.md)へ戻る |
| [/pr](~/.claude/skills/pr/SKILL.md)(仕様承認PR) | spec-reviewが🟢のみで通っているか | 指摘未対応のままPRを出すリスク。通っていなければ先に[/resolve](~/.claude/skills/resolve/SKILL.md)で対応する |
| [/implementation](~/.claude/skills/implementation/SKILL.md) | 仕様承認PRがユーザーの明示的なOKでマージ済みか(ユーザーからのマージ報告、または`git log origin/main`での確認) | 未承認のままコードを書き始めるリスク。未マージなら例外停止し承認を待つ(通常の前提条件どおり) |
| [/implementation-review](~/.claude/skills/implementation-review/SKILL.md) | 対象アプリのテストが通っているか(コマンドは`apps/<アプリ名>/README.md`で確認する) | 壊れた状態のままレビューに進むリスク。通っていなければ先に直す |
| [/pr](~/.claude/skills/pr/SKILL.md)(実装PR) | [/implementation-review](~/.claude/skills/implementation-review/SKILL.md)が🟢のみか、impl-pr-reviewerが❌なしか | 指摘を残したままPRを出すリスク。満たしていなければ先に[/resolve](~/.claude/skills/resolve/SKILL.md)で対応する |

上記いずれの工程から始める場合も、起動前監査を通過した後は「フロー(新機能起点)」または「フロー(fix起点)」の該当ステップ番号以降をそのまま踏襲する(対話ポイント・引き継ぎポイント・例外停止の基準は変わらない。新しい判断基準を都度作らない)。

# フロー(新機能起点)

各ステップの手順・テンプレートはリンク先の工程Skillに従う。

1. **要件定義(対話①)**: [/requirement](~/.claude/skills/requirement/SKILL.md)をそのまま実施する(JIRAチケット確認・Step0の入口判断・ヒアリングも通常どおり)。ヒアリングは要件に閉じず、設計の分かれ道になる事項もここで合わせて確認する(下記「ヒアリングの範囲」)
2. **自動運転宣言**: ヒアリング完了後、「ここから仕様承認PRの提示まで自走する」と宣言し、以降はユーザー確認なしで進む
3. **設計**: [/design](~/.claude/skills/design/SKILL.md)に従いメインスレッドがdesign.md・tasks.mdを作成する。ヒアリングで確認できていない細部は質問せず妥当な推測で補い、推測で決めた箇所には推測マーカーを付ける(下記「推測マーカー」)
4. **仕様レビュー**: [/spec-review](~/.claude/skills/spec-review/SKILL.md)(spec-reviewerエージェント)。🔴/🟡は[/resolve](~/.claude/skills/resolve/SKILL.md)で対応し再レビューする。ただし対応に要件・ビジネスルールの変更が必要な指摘は例外停止(下記)
5. **仕様承認PR(対話②+引き継ぎ)**: [/pr](~/.claude/skills/pr/SKILL.md)で仕様承認PRの本文を用意し、push〜PR作成のコマンドブロックを提示してユーザーに実行を依頼する。PR本文の「判断に迷った点・レビューしてほしい点」に**推測箇所の一覧**を明記し、一括レビューを依頼する。指摘はセッション上・PRコメントのどちらで受けてもよく、[/resolve](~/.claude/skills/resolve/SKILL.md)で修正して再提示する(何往復してもよい)
6. **承認処理(引き継ぎ)**: ユーザーの明示的なOKを得たら、残っている推測マーカーを全て削除するコミットを作り(`grep -rn '【推測】' apps/*/specs/` で残りゼロを確認する)、push・マージのコマンドをまとめて提示する。マージ完了の報告を受けてから次へ進む
7. **実装**: マージ後、新しいfeatureブランチを切り([/pr](~/.claude/skills/pr/SKILL.md)共通ルール)、[/implementation](~/.claude/skills/implementation/SKILL.md)に従いTDDで実装する。並行作業中など委譲したい事情があればimplementerエージェントに委譲してよい。architecture.mdを持つアプリでは、実装に着手する前に機能一覧表の状態列を「実装中」に更新し表を提示する(下記「機能一覧表(状態列)の更新」)
8. **実装レビュー**: [/implementation-review](~/.claude/skills/implementation-review/SKILL.md)(code-reviewerエージェント)。🔴/🟡は[/resolve](~/.claude/skills/resolve/SKILL.md)で対応し再レビューする。仕様の変更が必要な指摘は例外停止
9. **実装PR(引き継ぎ)**: [/pr](~/.claude/skills/pr/SKILL.md)(impl-pr-reviewerチェック→PR本文作成)。push〜PR作成〜CI確認のコマンドブロックを提示し、ユーザーの実行結果の報告を待つ。CIが失敗した場合は原因の修正を1回だけ自動で試み、それでも失敗するなら例外停止する
10. **完了報告**: マージ済みの報告を受けたら、[/pr](~/.claude/skills/pr/SKILL.md)の完了時案内に従って本番反映の確認手順とブランチ/worktreeの掃除を案内し、全工程のサマリをまとめて報告する — 作成したspec、PRのURL2件、テスト件数、自動対応したレビュー指摘の一覧、更新後の機能一覧表(architecture.mdを持つアプリの場合)、例外停止の有無

# ヒアリングの範囲

対話①では/requirementの要件ヒアリングに加えて、**設計(design.md)の分かれ道になる事項**も先に確認する。ここで聞いておくほど推測マーカーが減り、仕様承認PRでの一括レビューが軽くなる。

- **聞くもの**(設計への影響が大きい事項):
  - 分岐パターンが多く、どのパターンを扱うかで処理フローが大きく変わる事項
  - パターンの切り替えによって提供する機能・エンドポイント・画面が大きく変わる事項(新しい画面が増える場合は[/requirementの要件ヒアリング](~/.claude/skills/requirement/SKILL.md)のワイヤーフレーム3案の提示ルールに従う)
  - 誤った推測のまま進むと手戻りが大きい事項(データの保存有無・既存機能への影響範囲・インフラ構成の変更有無など)
- **聞かないもの**(推測で進めてマーカーを付ける): メッセージ文言・ログの粒度・表示順など、PRレビューで軽く直せる細部
- 聞き方は[/requirementの要件ヒアリング](~/.claude/skills/requirement/SKILL.md)と同じく一度に全部聞かず重要な順に、回答を受けたら残りが埋まっているか確認して往復する。**今回の機能に「聞くもの」に該当する事項がある限り、それらが確認できるまでステップ2(自動運転宣言)に進まない**(見切り発車で自走を始めない)。確認した内容は要件ならrequirements.mdへ、設計判断ならdesign.mdへ反映する(確認済みなのでマーカーは付けない)

# フロー(fix起点)

各ステップの手順・テンプレートはリンク先の工程Skillに従う。新機能起点との違いは、design.md/tasks.mdを作る独立した設計工程がなく、[/fix](~/.claude/skills/fix/SKILL.md)のStep2(3点セットへの影響洗い出し)がその役割を兼ねる点。

1. **入口確認・影響洗い出し(対話①)**: [/fix](~/.claude/skills/fix/SKILL.md)のStep1(JIRAチケット確認・新規spec vs 既存spec更新の判定)・Step2(3点セットへの影響洗い出し・承認要否判定)を実施する。ユーザーの依頼内容だけで判断できない曖昧な点(再現条件・期待する挙動の絞り込みなど)があればここで確認する。判断できる場合は対話なしで次に進めてよい。Step1で新規spec相当と判定した場合は「フロー(新機能起点)」の対話①(要件ヒアリング)に合流する
2. **自動運転宣言**: Step2完了後、「ここから自走する」と宣言し、以降はユーザー確認なしで進む
3. **分岐(仕様承認ゲート)**:
   - **仕様変更あり**(ビジネスルール変更・スコープ外だった項目への対応など): 3点セットを更新し、[/pr](~/.claude/skills/pr/SKILL.md)の仕様承認PRの手順で本文とコマンドブロックを提示する。PR本文の「判断に迷った点・レビューしてほしい点」に**推測箇所の一覧**を明記し、一括レビューを依頼する(**対話②**、新機能起点と同じ運用)。ユーザーの明示的なOK+推測マーカー残りゼロを確認してからマージのコマンドを提示する
   - **仕様変更なし**(純粋なバグ・軽微な変更): 対話②は発生させず、そのまま次のステップへ進む
4. **TDD修正**: [/fix](~/.claude/skills/fix/SKILL.md) Step3(再現テスト→修正)を実施する。architecture.mdを持つアプリで対象specがリリース済みなら、着手前に機能一覧表の状態列を「実装中」に戻し表を提示する。ヒアリングで確認できていない実装上の判断(文言・ログ粒度など)は質問せず妥当な推測で補ってよいが、合理的な選択肢が複数あり自信を持って決められない場合は例外停止する
5. **実装レビュー**: [/implementation-review](~/.claude/skills/implementation-review/SKILL.md)(code-reviewerエージェント)。🔴/🟡は[/resolve](~/.claude/skills/resolve/SKILL.md)で対応し再レビューする。仕様の変更が必要な指摘は例外停止
6. **実装PR(引き継ぎ)**: [/pr](~/.claude/skills/pr/SKILL.md)(impl-pr-reviewerチェック→PR本文作成)。ステップ4で確認なしに決めた判断があれば、PR本文の「判断に迷った点」に明記する。push〜PR作成〜CI確認のコマンドブロックを提示し、実行結果の報告を待つ
7. **完了報告**: マージ済みの報告を受けたら、[/pr](~/.claude/skills/pr/SKILL.md)の完了時案内に従って本番反映の確認手順とブランチ/worktreeの掃除を案内し、全工程のサマリをまとめて報告する — 修正内容、PRのURL(仕様変更ありの場合2件・なしの場合1件)、テスト件数、自動対応したレビュー指摘の一覧、更新後の機能一覧表(architecture.mdを持つアプリの場合)、確認なしで決めた判断点の一覧、例外停止の有無

# 機能一覧表(状態列)の更新 — 委譲してもメインスレッドが必ず行う

対象アプリが`apps/<アプリ名>/specs/architecture.md`を持つ場合、[architecture-workflow](~/.claude/skills/architecture-workflow/SKILL.md)の「更新タイミング」で定める機能一覧表の状態列更新を、実装をimplementerエージェントに委譲しても**委譲対象から外し、メインスレッドが自分の責務として実行する**(implementerは仕様外の変更をしない設計のため、構造上メインスレッドの仕事になる)。architecture.mdを持たない単一specアプリではこの節は不要。

自走中に見落としやすいポイントなので、フロー中の該当ステップ(新機能起点ステップ7・10、fix起点ステップ4・7)で省略しない。いずれのタイミングでも「ファイルを直すだけ」で終わらせず、**更新後の機能一覧表全体を該当工程の報告にチャット上で貼る**(セッションを閉じる前にユーザーが全体進捗を1画面で把握できることが目的)。

# 推測マーカー

- **対象**: ヒアリング・入口確認で確認していないのに設計判断(fix起点では実装判断を含む)として決めた事項(メッセージ文言・ログ粒度・エラー時の扱い・スコープの線引きなど)。design.mdだけでなく、requirements.mdに要件として書き足す場合も同様。fix起点で仕様変更を伴わない場合はrequirements.md/design.mdへの書き足しがないため、実装PR本文の「判断に迷った点」への記載で代替する
- **書き方**: その箇条書き・文の末尾に `【推測】` を付ける
- **削除**: 仕様承認PRでユーザーのOKが出たら、マージ前に全マーカーを削除する(`grep -rn '【推測】' apps/*/specs/` で残りゼロを確認してからマージを依頼する)。レビュー往復の中でユーザーが確認・修正した箇所は、その時点でマーカーを外してよい

# 例外停止

次のいずれかに当たったら自走をやめ、状況と選択肢をまとめて報告してユーザーの指示を待つ(勝手に要件・仕様を書き換えて進まない)。正常系では発動しない安全弁であり、対話ポイントを増やすものではない。

- 要件・仕様どおりに実装できない事情が判明した(implementerの中断報告、仕様の矛盾・不足の発見を含む)
- レビュー指摘への対応が要件・ビジネスルールの変更を要する
- 着手前チェック([parallel-work](../parallel-work/SKILL.md)の重複検出)で同じspecを扱う進行中ブランチ・worktreeを検知した
- CIの失敗が自動対応(1回)で解消しない
- 本番インフラ(Terraform)の破壊的変更・データ移行が必要と分かった
- (fix起点)実装上の判断に合理的な選択肢が複数あり、確信を持って決められない
