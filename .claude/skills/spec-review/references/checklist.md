# 仕様レビューのチェックリスト

spec-reviewerエージェント(またはエージェントを使えない状況で直接レビューするメインスレッド)が読むファイル。レビュー実施者以外はこのファイルを読まない(トークン節約のため[SKILL.md](../SKILL.md)本体から分離している)。

# レビューの注意事項

- **レビュー中は対象を修正しない。** 指摘の報告に徹する(修正は[/resolve](../../resolve/SKILL.md)の仕事)
- **好みの問題は指摘しない。** 指摘には必ずルール上の根拠([/requirement](../../requirement/SKILL.md)・[/design](../../design/SKILL.md)のテンプレート、CLAUDE.mdの規約、既存specとの整合性など)を添える。根拠を示せない指摘は出さない
- **良い点も必ず1つ以上挙げる**
- **レビュー結果に応じて次のステップを案内する**(テンプレート末尾の案内を必ず含める)

# チェックリスト

## requirements.md
- [ ] ユーザーストーリーが利用者視点(「〜としては、〜したい」)で書かれているか
- [ ] ビジネスルールの数値・条件に根拠(法令・公式資料・過去の意思決定)が添えられているか
- [ ] テストを対応させたい箇条書きに`[n]`が振られているか。「〜の場合、〜になること」の文体になっているか
- [ ] 数式・変数名・実装方法(HOW)が混ざっていないか
- [ ] スコープ外(今回やらないこと)が明記されているか
- [ ] タイトル直下に`> ステータス: 仕様確認中(未実装)`の行があるか(新規specの場合)
- [ ] 他specへの依存が内容の書き写しでなく`<spec名>/requirements.md#見出し-n`の参照形式になっているか
- [ ] ユーザー入力・リクエストの極端なパターン(未入力・境界値・想定外の値)に対する挙動がビジネスルールとして決まっているか
- [ ] 先頭に**サマリ**章があり、この章だけで概略(誰の何を解決するか・主要ルール・スコープ外の要点)がつかめるか
- [ ] **ユースケース図**があるか。無い場合、省略した理由が一言添えられているか([architecture-workflow](../../architecture-workflow/SKILL.md)の「図の運用方針」)
- [ ] 会話で確認していない方針が推測で書かれていないか(会話ドリブン原則)

## design.md(作成している場合)

形式:
- [ ] 必須5見出し(処理フロー・エラーハンドリング・関連するファイル・セキュリティ・ログ)が検討されているか。安易な「特になし」で済ませていないか
- [ ] 処理の呼び名が業務的な言葉になっているか(関数名・ファイル名などの実装詳細が混ざっていないか)
- [ ] 手順が日本語の文章で書かれ、分岐が「〜の場合は…、そうでない場合は…」の形で網羅されているか
- [ ] 先頭に**サマリ**章があり、処理の全体像・主要な設計判断・主要図へのリンクがまとまっているか
- [ ] 作成条件を満たす**Mermaid図**(シーケンス図・画面遷移図・状態遷移図)が描かれているか。無い場合、省略した理由が一言添えられているか

中身:
- [ ] requirements.mdの全ビジネスルールが処理フローのいずれかでカバーされているか(設計漏れがないか)
- [ ] 境界値・特殊ケース(空・NULL・上限値ちょうど、想定外の入力など)が分岐として現れているか
- [ ] エラーハンドリングが起こりうる失敗ごとに具体的か(何が失敗したら・呼び出し元に何を返し・処理を継続するか中断するかまで決まっているか)
- [ ] セキュリティがこの機能固有のリスクを検討しているか(保存する個人情報が必要最小限か、外部からの入力をどこまで信頼するかを考えたか)
- [ ] データベース設計がある場合、型・キー設計に根拠があるか。既存の属性・テーブルと重複していないか
- [ ] 画面設計がある場合、正常表示以外の状態(ローディング・エラー・空・未入力)が考慮され、既存画面と用語・操作感が一貫しているか
- [ ] 省略された任意見出し(バリデーション・パフォーマンスなど)が本当に該当しないか。逆に、書かれている見出しで実装に委ねてよい詳細まで書き込んでいないか
- [ ] 設計がプロジェクト構成・`doc/adr/`の決定と矛盾なく実現可能か

## tasks.md(作成している場合)
- [ ] 各タスクが🔴Red→🟢Green→🔵Refactorで完結できる粒度か
- [ ] 冒頭にTDD宣言文があるか
- [ ] design.mdの全処理がいずれかのタスクでカバーされているか
- [ ] タスクの並び順が依存関係の順(先に必要なものが先)になっているか

## 最新仕様のみが書かれているか(requirements.md / design.md / architecture.md 共通)
- [ ] 変更の経緯・履歴が混ざっていないか(「〜から〜に変更した」「旧〜」「移設した」「廃止した」「撤去」などの差分ナラティブ)
- [ ] 移設・変更を示すマーカー(「【〜で移設】」など)が残っていないか
- [ ] 内輪のコードネーム・呼称(第三者・後任が読んで意味が分からない語。例:「方向B」)が使われていないか
- [ ] 合意日付などセッション固有の言い回し(例:「2026-08-19合意」)が残っていないか
- [ ] 残すべき経緯・決定理由がADRに分離され、仕様書からはリンクだけになっているか(ADRの置き場所は[architecture-workflow](../../architecture-workflow/SKILL.md))

## 3点セットの整合性
- [ ] requirements↔design↔tasksの間で矛盾(designにだけある処理、requirementsにだけあるルール)がないか
- [ ] 新規spec作成 vs 既存spec更新の判断([/requirement](../../requirement/SKILL.md)のStep0)が正しいか
- [ ] `apps/<アプリ名>/specs/architecture.md`がある場合、機能一覧表(spec一覧・依存関係・状態列)と矛盾しないか
- [ ] 各Markdownに埋め込まれたMermaid図が本文・実装と矛盾していないか。**エッジラベルに半角括弧が混入していないか**(このリポジトリにはCIの描画検査が無いため、ここが最後の砦)

# 指摘の重要度

| 重要度 | 意味 | 扱い |
|---|---|---|
| 🔴 must | 承認できない問題(要件の欠落・矛盾、根拠のないビジネスルール、テンプレート必須項目の欠落) | 修正するまで/prに進まない |
| 🟡 should | 修正が望ましい問題(表現の曖昧さ、`[n]`の振り忘れ、文体の不統一) | 原則今回対応する |
| 🟢 info | 参考情報・質問・提案 | 対応は任意 |

# フィードバックのテンプレート

```markdown
## 仕様レビュー結果: <承認(指摘なし) / 要修正(🔴n件・🟡n件・🟢n件)>

### 対象
apps/<アプリ名>/specs/<機能名>/

### 良い点
- (必ず1つ以上)

### 指摘事項
| # | 重要度 | 対象 | 指摘内容 | 根拠 |
|---|---|---|---|---|
| 1 | 🔴 must | requirements.md#ビジネスルール | ... | ... |

### 次のステップ
- 🔴/🟡あり → /resolve で修正し、再レビューを受ける
- 指摘なし(🟢のみ) → /pr で仕様承認PRを作成する
```
