> **次フェーズのモデル(/spec-review):** 基本は **Sonnet**(トークン消費を抑えるため下流工程は原則Sonnetで運用する)。複雑なロジックが絡み、見落としのコストが大きい設計に限り **Opus** を検討する

# 前提条件

- 対象の`apps/<アプリ名>/specs/<機能名>/requirements.md`が存在すること。なければ[/requirement](../requirement/SKILL.md)(要件定義)から始める(要件ヒアリングを飛ばして設計に入らない)

# 仕様書は「最新仕様のみ」を書く(恒久ルール)

requirements.md / design.md / architecture.md には、**常に今の正しい仕様だけを現在形で書く**。仕様を書き換えるときは差分として追記せず、**あたかも最初からその仕様だったかのように書き直す**(仕様書を読む人が知りたいのは「今どうなっているか」だけで、そこに至る経緯ではない。差分の痕跡が残るほど、後任・第三者が現状を読み取るコストが上がる)。

**書かないもの**:

- 変更の経緯・履歴 —「〜から〜に変更した」「旧〜」「移設した」「廃止した」「撤去」などの差分ナラティブ
- 移設・変更を示すマーカー — 例:「【〜で移設】」
- 内輪のコードネーム・呼称 — 第三者・後任が読んで意味が分からない語。例:「方向B」
- 合意日付などセッション固有の言い回し — 例:「2026-08-19合意」

**経緯・決定理由が必要な場合はADRに分離する。** 仕様書には書かず、ADR(Architecture Decision Record)にまとめ、仕様書からは必要ならリンクだけを張る。置き場所と採番は[architecture-workflow](../architecture-workflow/SKILL.md)の「ADRの置き場所」を参照する。

# design.mdの書き方

requirements.mdのビジネスルールを「どんな手順・分岐で処理するか」を日本語の文章(変数名・数式なし)で書く**処理フロー**を中心に、この機能が実際に関わるファイル・DB・エンドポイント・画面などを確認用に書き足す。フォルダ構成の一般ルールや、プロジェクト全体の非機能要件・設計方針はCLAUDE.md/requirements.mdの領分のためここには書かない。分岐・複数ステップのロジックが1つもない機能(例: 純粋なルーティング変更)は、design.md自体を作らずrequirements.mdのみで完結してよい。

**会話ドリブン原則(推測で埋めない):** design.mdに書く設計方針は、データベース設計・エラーハンドリング方針・セキュリティ・任意見出しも含め、ユーザーとの会話の中で確認したもの・こちらから提案して合意したものだけを書く。要件ヒアリング・[/consult](../consult/SKILL.md)で既に合意済みの点はそれを反映し、設計段階で新たに決めるべき方針が出てきたら、書き切る前にユーザーに提案・確認してから記載する(design.mdは「会話で合意した設計がドキュメントになっているだけ」の状態を目指す)。ただし[/autopilot](../autopilot/SKILL.md)モードでは、推測した箇所を`【推測】`マーカーで明示する運用が例外として認められる(それ以外は推測で埋めない)。

**サマリ(必須):** design.mdの先頭(見出しの一番上)に`##`の**サマリ**章を必ず置く。時間がない人がこの章だけで設計の概略をつかめるよう、処理の全体像を1〜2行・今回の主要な設計判断(DB/エラー方針/セキュリティの勘所)・下記の主要図(シーケンス図・画面遷移図・状態遷移図)へのリンクを短くまとめる。物量が増えても、まずここだけ読めば方針が分かる状態を保つ。

以下の見出しのうち**処理フロー・エラーハンドリング・関連するファイル(抜粋)・セキュリティ・ログの5つは必須**(上記サマリと合わせて必須)。この5つは、該当しないと思っても一旦立ち止まって深く検討し、対策として実装できることは極力実装する方針で臨む(考えた末に本当に不要と判断した場合のみ、その理由を一言書く。安易に「特になし」で済ませない)。残りの見出しはこの機能が実際に関わる場合だけ書き、関わらないものは見出しごと省略する(「該当なし」とは書かない)。

1. **処理フロー**(必須) — `##`見出し。個々の処理はこの下に`###`見出しで並べる
   - **処理の呼び名**(`###`見出し) — 業務的な言葉にする(実装詳細(関数名・ファイル名)はtasks.mdに書く)
   - **対象** — この処理が何に対して行われるか
   - **手順** — 日本語の文章で書く番号付きステップ(変数名・数式は使わない)。分岐がある場合は「〜の場合は…、そうでない場合は…」と書く。単純な1つの計算のようにビジネスルールの文章だけで手順が自明なものは書かない。その処理固有のエラー時の振る舞い(例:「対象が存在しない場合は404を返す」)はここに書く。複数の処理にまたがる方針がある場合のみ、下記のエラーハンドリング見出しにまとめる
   - **シーケンス図**(呼び出し元・API・DB・外部サービスなど複数アクター間のやり取りがある処理のみ) — 該当する処理の配下にMermaidコードブロック(`sequenceDiagram`)を埋め込む。手順の文章が正であり、図は俯瞰用の補助(後述「Mermaid図の埋め込みルール」参照)
   - **関連するビジネスルール** — `requirements.md#見出し`

2. **バリデーション**(入力値に対する検証ロジックが必要な場合のみ) — 検証する項目・条件と、NGの場合の扱いを簡潔に書く。単純な必須入力チェックなど自明なものは省略してよい。

3. **エラーハンドリング**(必須) — 通信エラー・想定外の例外など、複数の処理にまたがる共通のエラー処理方針を積極的に検討して書く。個々の処理固有のエラー時の振る舞いは処理フローの手順に直接書けば足りるため、ここでは機能全体を通じた方針に絞る。

4. **関連するファイル(抜粋)**(必須) — フォルダ構成のルール自体はCLAUDE.mdにあるため、ここでは「新規に追加するファイル」「既存でこの機能から使う共通処理(DBクライアント・共通モジュールなど)」だけを列挙する。
   ```
   apps/notes-api/application/lambda/handlers/deleteNote.py (新規)
   apps/notes-api/application/lambda/lib/dynamoClient.py (既存の共通クライアントを利用)
   ```

5. **データベース設計**(DBのテーブルに保存・参照する場合のみ) — テーブル名(DynamoDBならパーティションキー・ソートキーを含む)と、この機能で追加・使用する属性のみを書く。アクセス制御やテーブル運用方針などアプリ横断の決定は`doc/adr/`を参照し重複させない。
   ```
   ### notes テーブル
   | 属性 | 型 | 補足 |
   |---|---|---|
   | noteId (PK) | string | UUID |
   | ownerId (SK) | string | 所有者ユーザーID |
   ```

6. **API設計**(このアプリがAPIエンドポイントを新設・変更する場合) — エンドポイント・リクエスト/レスポンス・ステータスコードを書く。API Gateway + Lambdaのようにアプリ自体がAPIである場合はこの見出しが中核になる。フロントエンドのみで完結し独自APIを持たないアプリでは不要。

7. **画面設計**(新しい画面・表示項目・操作を追加する場合のみ) — 表示項目と操作を箇条書きで。レイアウトの詳細・型定義は実装に委ねる(非自明なUI仕様はrequirements.mdのUI/UX要件に書く)。
   - **画面遷移図(必須相当)** — 画面が複数ある、または画面内で表示が大きく切り替わる(入力→確認→完了など)機能では、画面間・表示状態間の遷移をMermaid(`flowchart`。分岐条件が主役なら`stateDiagram-v2`でもよい)でこの見出しに埋め込む。箇条書きの表示項目・操作が正であり、図は遷移の俯瞰(後述「Mermaid図の埋め込みルール」に従う)。単一画面で完結し遷移がない、と検討の上で判断した場合のみ、その理由を一言添えて省略してよい(安易に省略しない)

8. **コンポーネント設計**(再利用可能な新しいコンポーネントを追加する場合のみ) — Propsの型と役割だけを簡潔な表にする。

9. **状態管理**(複数の処理・画面にまたがって共有する状態がある場合のみ) — 何を・どこで保持するか(useState/Context/URLパラメータなど)を一言で書く。状態が3つ以上、または遷移に条件分岐があるときは、状態遷移図(Mermaid `stateDiagram-v2`)をこの見出しに埋め込む(文章が正、図は補助)。処理の状態遷移(ジョブの実行状態・リソースのライフサイクルなど)を持つバックエンド機能もこの見出しの対象とする。

10. **セキュリティ**(必須) — 入力値のサニタイズ、個人情報・機微情報の扱い方など、この機能固有のリスクを積極的に洗い出し、対策できることは設計に盛り込む。IAMポリシー・API認可の方針などアプリ横断の決定は`doc/adr/`を参照し重複させない。

11. **パフォーマンス**(この機能で特別な考慮が必要な場合のみ) — 例: 大量データのページネーション、重い計算のメモ化・非同期化など。

12. **ログ**(必須) — この機能で出力すべきログ(処理の開始・終了・失敗など)を積極的に検討して書く。出力するログはタイミング・内容・ログレベルを簡潔に書く。

# Mermaid図の埋め込みルール

design.mdに入れる図(シーケンス図・画面遷移図・状態遷移図)は以下に従う:

- 図はMermaidコードブロックとして該当見出しに直接埋め込む(専用ファイル・画像は作らない)
- **図は日本語の文章を置き換えない。** 処理フロー等の文章が正であり、図は俯瞰用の補助。`[n]`採番・テストとの対応付けの対象は従来どおり文章側
- **各図種は必須相当**(design.mdの必須見出しと同じ運用)。その図種の作成条件に該当する箇所(複数アクター間のやり取り・複数画面/表示の切り替え・複数状態の遷移)が一つでもあれば、原則その図を描く。作成条件に該当する箇所が一つもない、と一旦立ち止まって検討した上で判断した場合のみ、その理由を一言添えて省略してよい(安易に省略しない)。一方で、条件に該当しない処理へ無理に図を足す必要はない(全処理への一律付与は求めない)
- ノード名・ラベルは業務的な言葉/1行1エッジ/図の直後に正となる文章へのリンク、**エッジラベルに半角括弧を書かない**などの書き方ルールは[architecture-workflow](../architecture-workflow/SKILL.md)の「Mermaidの書き方ルール」に従う。このリポジトリには図の描画をCIで検査する仕組みが無いため、書いた図は自分でプレビュー・GitHub上で描画を確認する

# tasks.mdの書き方

設計をもとに実装可能な最小単位に分解する。対象の関数名・ファイル名などの実装詳細はここに書いてよい。タスクを細かく分けるほどAIの生成精度が上がりレビューもしやすくなる。

タスクの並び順・粒度は、各タスクを🔴Red(失敗するテストを書く)→🟢Green(最小実装)→🔵Refactorの順で完結できる単位にする(TDDサイクルの進め方・詳細は[/implementation](../implementation/SKILL.md)を参照)。冒頭に`> TDDで進める。各タスクは 🔴 Red(失敗するテストを書く) → 🟢 Green(最小実装) → 🔵 Refactor の順で進める。`という一文を入れる。

- 変更頻度が低く設計が単純な機能は requirements.md のみで可

# architecture.mdへの反映

新規specフォルダの作成・廃止や、spec間の依存関係の変化がある場合、`apps/<アプリ名>/specs/architecture.md`が存在すれば機能一覧表(機能マップ)も合わせて更新する(存在しなければこの手順は不要。作成基準・書き方は[architecture-workflow](../architecture-workflow/SKILL.md)を参照)。あわせて、architecture.md内の図への影響も確認する: コンテキスト図(利用者・外部サービス・他アプリとの境界の増減)、システム構成図(使うコンポーネント・外部サービスの増減)、コンポーネント図(spec横断の依存の変化)、ER図(使用テーブルの追加・リレーションの発生)に変化があれば同じ変更で図も更新する(図だけが古くなることの禁止。[architecture-workflow](../architecture-workflow/SKILL.md)の「更新ルール」参照)。

# 完了時の次ステップ案内

3点セット(requirements.md/design.md/tasks.md)が揃ったら、[/spec-review](../spec-review/SKILL.md)(仕様レビュー)へ進むことを案内する。この時点ではまだコード(テストを含む)を書かない。

design.md/tasks.mdをコミットした時点で、compactや新しいセッションへの切り替えを行っても支障はない。新しいセッションの名称と、次のセッションにそのまま貼り付けられるプロンプトを、1行目=名称・2行目=プロンプトの単一のコードブロックとして毎回提示してから終える(名称とプロンプトを分けて提示しない。「セッションを閉じても大丈夫」とだけ述べて済ませない。名称は前のセッションと同じ<機能名>に次工程名を()で添えた形):

```
<機能名>(仕様レビュー)
/spec-review を実行してください。対象は apps/<アプリ名>/specs/<機能名>/、ブランチ feature/<機能名> です。
```
