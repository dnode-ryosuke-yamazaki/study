> ワークフロー上の位置: **/fix(本Skill)** → [/implementation-review](../implementation-review/SKILL.md) → [/pr](../pr/SKILL.md)(実装PR)

> **次フェーズのモデル:** 基本は **Sonnet**(トークン消費を抑えるため下流工程は原則Sonnetで運用する)
> - Step2で仕様変更が必要と判定した場合: 複数のビジネスルール変更・外部仕様への適合など影響範囲の特定が重要な場合のみ **Opus** を検討する
> - 純粋なバグ修正の場合: 複雑なバグ・複数箇所の修正が必要な場合のみ **Opus** を検討する

# 開始時: JIRAチケットの確認

Step1より前に、`~/.claude/jira-ticket-check.md`(グローバル方針)を読み、その手順に従って対応するJIRAチケットの有無を確認する(studyでの詳細な背景は`specs/jira-automation/requirements.md`参照)。[/requirement](../requirement/SKILL.md)でも同様にこの節を維持する。

# Step1 入口の確認

今回の変更が**既存spec更新**(本Skillの対象)であることを確認する。以下の**新規specを作るべきサイン**に1つでも該当したら、本Skillではなく[/requirement](../requirement/SKILL.md)のフローへ切り替える:

- 新しいエンドポイント・新しい画面・独立してリリース/ロールバックできる機能である
- 既存のユーザーストーリーでは説明できない、新しい利用者視点の目的がある
- 別のドメイン・別のデータストアなど、技術的に独立した関心事である

いずれにも該当しなければそのままStep2へ進む。判断に迷う場合のみ、/requirementのStep0「新規spec作成 vs 既存spec更新の判断」を読んで判断する(上記3項目はStep0の要約。Step0側を変更したらここも追随する)。

既存specを更新する場合も、他のworktree・他のセッションが同じspecに対して並行して作業していないかを確認する(手順は[parallel-work](../parallel-work/SKILL.md)の「他セッションとの重複を避ける」を参照)。同じrequirements.mdを2つのセッションが同時に書き換えるとマージ時に衝突・矛盾が生じる。

# Step2 仕様(3点セット)への影響を洗い出す

既存specを更新する場合、3点セットすべてへの影響を洗い出す。1つのファイルだけ直して終わりにしない。

**書き換えは差分の追記ではなく上書き。** 更新後の仕様書は、あたかも最初からその仕様だったかのように読める状態にする。「〜から〜に変更した」「旧〜」「移設した」といった経緯・履歴や、内輪の呼称・合意日付を仕様書に残さない([/requirement](../requirement/SKILL.md)の「仕様書は『最新仕様のみ』を書く」)。今回の変更理由を残す必要がある場合は、仕様書ではなくADRに書く(置き場所は[architecture-workflow](../architecture-workflow/SKILL.md)の「ADRの置き場所」)。変更の経緯そのものはコミット履歴とPR本文に残るため、仕様書に書き写す必要はない。

- **requirements.md**: 該当する見出しの`[n]`を書き換える、または新しい`[n]`を追記する(既存の連番は崩さない)。エッジケース・スコープ外に古い記述が残っていないか確認する
- **design.md**: 処理フローの該当する処理を更新する。処理の呼び名・手順が変わった場合は書き直す。埋め込まれているMermaid図(シーケンス図・画面遷移図・状態遷移図)が変更後の文章とずれる場合は、同じ変更で図も更新する(図だけが古くなることの禁止)
- **tasks.md**: 新しいタスクとして追記する(過去タスクの完了チェックは履歴として残し、変更しない)

さらに、仕様書だけでなく実装・テストへの影響も必ず洗い出す:

- 実装コード(該当する`apps/<アプリ名>/application/`配下のファイル)のどこを変更する必要があるか
- 既存テストの仕様コメントが指す見出し・`[n]`がずれないか(見出し名や番号を変更したら、対応するテストコメントも合わせて書き換える)
- 仕様項目とテストの対応関係が壊れていないか目視で確認する
- `apps/<アプリ名>/specs/architecture.md`があれば、機能一覧表(機能マップ)・関連ADR等に加え、図(コンテキスト図・システム構成図・コンポーネント図・ER図)に影響がないか確認する(外部サービス・使用テーブル・spec間依存が変わる修正では図も同じ変更で更新する)。リリース済みのspecに手が入る場合は状態列を「実装中」に戻す
- Terraform・CI・外部サービスの追加/変更などインフラ・デプロイ構成に触れる修正では、`doc/architecture/`の該当図(インフラ構成図・デプロイメント図など)も同じ変更で更新する([architecture-workflow](../architecture-workflow/SKILL.md)の「更新ルール」参照)

## 仕様承認の要否

修正の種類によって承認ゲートの扱いが分かれる:

- **仕様そのものを変える場合**(ビジネスルールの変更、スコープ外だった項目への対応など): 先に3点セットを更新して仕様承認PR([/pr](../pr/SKILL.md))を出し、ユーザーの承認を得てから実装に入る
- **仕様は正しく実装が誤っている場合**(純粋なバグ)や、仕様に影響しない軽微な変更(typo・文言修正): 承認ゲートは不要。そのままStep3へ進む

# Step3 修正(TDD)

`feature/<機能名>`ブランチを切り、まずバグ・問題を再現する失敗テスト(🔴Red)を書いてから修正する。別の機能開発に割り込む形で修正する場合は、ブランチを切り替えず[parallel-work](../parallel-work/SKILL.md)(worktree)で作業ディレクトリを分ける(テストの命名・仕様コメントのルールは[/implementation](../implementation/SKILL.md)を参照)。Step2で洗い出した仕様書・テストコメントの追随も同じ変更の中で行う。

# 完了時の次ステップ案内

修正・テスト・動作確認が済んだら、[/implementation-review](../implementation-review/SKILL.md)(コードレビュー)→[/pr](../pr/SKILL.md)(実装PR)へ進むことを案内する。

修正とテストをコミットした時点で、compactや新しいセッションへの切り替えを行っても支障はない。新しいセッションの名称と、次のセッションにそのまま貼り付けられるプロンプトを、1行目=名称・2行目=プロンプトの単一のコードブロックとして毎回提示してから終える(名称とプロンプトを分けて提示しない。「セッションを閉じても大丈夫」とだけ述べて済ませない):

```
<機能名>(コードレビュー)
/implementation-review を実行してください。対象ブランチは feature/<機能名> です。
```
