> ワークフロー上の位置: **/fix(本Skill)** → [/implementation-review](../implementation-review/SKILL.md) → [/pr](../pr/SKILL.md)(実装PR)。仕様変更を伴う場合は実装前に仕様の承認を挟む(判断は「仕様承認の要否」)。全体フロー・モデル対応表は[dev-flow.md](../../dev-flow.md)を参照

# 開始時: JIRAチケットの確認

Step1より前に、`.claude/jira-ticket-check.md`(グローバル方針)を読み、その手順に従って対応するJIRAチケットの有無を確認する。プロジェクトが独自の`fix/SKILL.md`を持つ場合は、そちらでも同様にこの節を維持する。

# Step1 入口の確認

今回の変更が**既存spec更新**(本Skillの対象)であることを確認する。[dev-flow.mdの「新規spec vs 既存specの判断基準」](../../dev-flow.md#新規spec-vs-既存specの判断基準)の**新規specを作るべきサイン**に1つでも該当したら、本Skillではなく[/requirement](../requirement/SKILL.md)のフローへ切り替える。いずれにも該当しなければそのままStep2へ進む。

既存specを更新する場合も、他のworktree・他のセッションが同じspecに対して並行して作業していないかを確認する(手順は[parallel-work](../parallel-work/SKILL.md)の「他セッションとの重複を避ける」を参照)。同じrequirements.mdを2つのセッションが同時に書き換えるとマージ時に衝突・矛盾が生じる。

# Step2 既存コードを確認し、仕様(3点セット)への影響を洗い出す

## 既存コードの確認(洗い出しの前に)

仕様書に手を付ける前に、今のコードがどう動いているかを読んで確かめる。この段階ではコード・テスト・仕様書を書き換えない(読むだけ)。「仕様は正しく実装が誤っているのか、仕様そのものを変えるのか」(下記「仕様承認の要否」)は、コードを読まないと判断できない。

1. **症状の出る箇所から呼び出し経路をたどる**: 入口(エンドポイント・コマンド・画面操作・launchdジョブ等)から、症状が出る箇所・変更したい箇所までを読む。対象の見当が付かない、または読む範囲が広い(複数のディレクトリにまたがる・1万字を超えるファイルを含む)場合はExploreサブエージェントに探させ、結論(該当箇所の`ファイル:行`と根拠)だけを受け取る
2. **関連するテストと仕様項目を読む**: 該当箇所を覆う既存テストと、その仕様コメントが指す requirements.md の`[n]`を読み、仕様・テスト・コードの3つのうちどれが食い違っているかを特定する
3. **最近の変更を見る**: 該当ファイルの`git log`(必要なら`git blame`)で、その処理がいつ・なぜ入ったかを確かめる。不要に見える処理を消す・変える修正では、入った理由を確認してから判断する(理由が分からないまま消さない)
4. **再現を確かめる(バグの場合)**: 既存テスト・コマンドの実行やログで、報告された症状が実際に起きることを確認する。再現できない場合は推測で直さず、再現条件をユーザーに確認する
5. **結果をまとめる**: 原因または変更箇所(`ファイル:行`)・その処理の呼び出し元など影響を受ける箇所・関連するテストを短くまとめ、以降の洗い出し(下記)と承認要否の判断の根拠にする。確認の途中で今回の依頼と別の不具合に気づいた場合は、範囲を広げずに別件としてユーザーに報告する

## 仕様・実装・テストへの影響の洗い出し

既存specを更新する場合、3点セットすべてへの影響を洗い出す。1つのファイルだけ直して終わりにしない。

**書き換えは差分の追記ではなく上書き。** 更新後の仕様書は、あたかも最初からその仕様だったかのように読める状態にする。「〜から〜に変更した」「旧〜」「移設した」といった経緯・履歴や、内輪の呼称・合意日付を仕様書に残さない([dev-flow.mdの「仕様書は『最新仕様のみ』を書く」](../../dev-flow.md#仕様書は最新仕様のみを書く恒久ルール))。今回の変更理由を残す必要がある場合は、仕様書ではなくADRに書く(置き場所は[architecture-workflow](../architecture-workflow/SKILL.md)の「ADRの置き場所」)。変更の経緯そのものはコミット履歴とPR本文に残るため、仕様書に書き写す必要はない。

- **requirements.md**: 該当する見出しの`[n]`を書き換える、または新しい`[n]`を追記する(既存の連番は崩さない)。エッジケース・スコープ外に古い記述が残っていないか確認する
- **design.md**: 処理フローの該当する処理を更新する。処理の呼び名・手順が変わった場合は書き直す。埋め込まれているMermaid図(シーケンス図・画面遷移図・状態遷移図)が変更後の文章とずれる場合は、同じ変更で図も更新する(図だけが古くなることの禁止)。specフォルダに画面モック`mock.html`がある場合、画面の配置・表示・状態が変わる修正ではモックも同じ変更で直し、プレビューのArtifactも再発行する(正本はモック。[/requirement](../requirement/SKILL.md)の「画面モックの作り方」)
- **tasks.md**: 新しいタスクとして追記する(過去タスクの完了チェックは履歴として残し、変更しない)

さらに、仕様書だけでなく実装・テストへの影響も必ず洗い出す:

- 実装コードのどこを変更する必要があるか(上記「既存コードの確認」で特定した箇所と、その呼び出し元)
- 既存テストの仕様コメントが指す見出し・`[n]`がずれないか(見出し名や番号を変更したら、対応するテストコメントも合わせて書き換える)
- 仕様項目とテストの対応関係が壊れていないか目視で確認する
- `architecture.md`を採用しているプロジェクトの場合、機能マップ・関連ADR等に加え、図(コンテキスト図・システム構成図・コンポーネント図・ER図)に影響がないか確認する(外部サービス・使用テーブル・spec間依存が変わる修正では図も同じ変更で更新する)。リリース済みのspecに手が入る場合は、機能マップの状態列と対象specの requirements.md のステータスのラベルの両方を「実装中」に戻す(片方だけにしない)
- インフラ・デプロイ構成(ホスティング・CI・外部サービスの追加/変更)に触れる修正では、該当のインフラ系図も同じ変更で更新する([architecture-workflow](../architecture-workflow/SKILL.md)の「更新ルール」参照)

## 承認済みのspecに手を入れるとき(フロントマター)

仕様書を1文字でも直す前に、直すファイル(requirements.md / design.md / tasks.md)の先頭のフロントマターを見る。

- **`status: approved` なら、この修正の最初の変更で** `draft` に戻し、`approved_date` を消し、`version` の小数点以下を1つ上げる(`"1.0"` → `"1.1"`)。誤字・表記の修正だけでも同じ(承認済みの内容が黙って変わるのを防ぐため)。再承認までに同じファイルを重ねて直しても上げ直さない。**直さないファイルは `approved` のまま**残す
- tasks.md へのタスクの追記も tasks.md の変更として扱う。一方、ステータスのラベルの値の書き換え(下の「リリース済みのspecに手が入る場合」)と tasks.md の `> 実装中: session ...` マーカーは承認状態に数えない
- `draft` に戻したファイルは、下の「仕様承認の要否」に従い承認を得て `approved` に戻す(値の遷移の正は[dev-flow.mdの「承認状態のフロントマター」](../../dev-flow.md#承認状態のフロントマター))
- **フロントマターが無い**(検査で種別 `フロントマター無し` が出る)既存specは、直す前に[dev-flow.mdの移行手順](../../dev-flow.md#フロントマターを持たない既存specの移行)で付ける。承認の有無が読めない spec はユーザーに確かめてから付ける
- 純粋なバグ修正で仕様書に触れない場合は、フロントマターも変えない

## 旧形式のspecに手を入れるとき(新形式化)

対象specが**旧形式**(畳みが1つも無く・畳むべきAIの見出しが1つ以上あり・出所の目印も1つも無い)なら、既存specを一括改稿する代わりに、**この修正と同じ変更で requirements.md と design.md を新形式へ直す**(片方だけにしない。部分適用の状態で残さない)。見出し名では判定しない(「概要」は新形式でも必須の見出し)。判定は検査スクリプトに任せてよい。

```
python3 .claude/lib/spec_layout_check/scripts/check_spec_layout.py <specフォルダの絶対パス>
```

終了コード2で種別 `旧形式` の行が出たら、次をまとめて行う(種別 `フロントマター無し` の行だけなら層分けは新形式なので、上の移行だけを行う)(書式の正は[区分け表のファイル](../../quality-standards/base/spec-layout.md)、骨格は[/requirement](../requirement/SKILL.md)・[/design](../design/SKILL.md)):

1. 「サマリ」の見出しを削り、中身を `## 概要`(誰の何を解決するか1〜3行・作るものと何のために要るか・進め方)と各見出しの要点行へ移す。「概要」が無ければ先頭に立てる。requirements.md のタイトル直下にはステータスと優先度のラベル1行を置く
2. 読み手がAIの見出しを「見出し → 要点1〜2行 → `<details><summary>詳細を開く</summary>`で畳んだ本文」に組み替える。`###`を持つ見出しは`###`ごとに畳み、図とその直後の説明1行は畳みの外に出す
3. design.md に「決定事項」の表(論点 / 選んだ案 / 採らなかった案 / 理由 / 影響範囲 / 出所 の6列)が無ければ、本文の選択・却下の記述から起こす
4. 設定・キャッシュ・コマンド・ログの書式を同じspecフォルダの appendix.md へ移し、design.md にはリンクを1行残す
5. 承認者が読む行に出所の目印を付ける。**承認済みだった内容の行は`〔合意〕`、この改修で追加・変更した行は`〔提案〕`**(承認は会話での合意と同じ重みを持つ)。迷ったら`〔提案〕`
6. 直したあと検査スクリプトを再実行し、違反0(終了コード0)になったことを確認する
7. 新形式に直したことを完了報告に書く

## 仕様承認の要否

修正の種類によって承認ゲートの扱いが分かれる:

- **仕様そのものを変える場合**(ビジネスルールの変更、スコープ外だった項目への対応など): 先に3点セットの該当箇所を更新し、内容をユーザーに提示してチャット上で明示的な承認を得てから実装に入る(承認ゲートの考え方は[/spec-review](../spec-review/SKILL.md)を参照)。仕様承認PR方式のプロジェクトでは、チャット承認の代わりに仕様承認PR([/pr](../pr/SKILL.md))を出し、マージを確認してから実装に入る。提示する時点で直したファイルのフロントマターを `in-review` にし、承認を得たら `approved` と承認日に書き換える(version は上げたまま)
- **仕様は正しく実装が誤っている場合**(純粋なバグ)や、仕様に影響しない軽微な変更(コード・画面のtypo・文言修正): 承認ゲートは不要。そのままStep3へ進む。ただし**仕様書そのものの誤字・表記を直す場合は、文言だけでも上の「承認済みのspecに手を入れるとき」に従って `draft` に戻し、再承認を得る**

# Step3 修正(TDD)

`feature/<機能名>`ブランチを切り、まずバグ・問題を再現する失敗テスト(🔴Red)を書いてから修正する。別の作業に割り込む形で修正する場合は、ブランチを切り替えず[parallel-work](../parallel-work/SKILL.md)(worktree)で作業ディレクトリを分ける(テストの命名・仕様コメントのルールは[/implementation](../implementation/SKILL.md)を参照)。Step2で洗い出した仕様書・テストコメントの追随も同じ変更の中で行う。

# 完了時の振り返り(3問)

修正・テスト・動作確認が済んだら、次に進む前にユーザーへ次の3問を確認する。仕様レビュー・コードレビューを通過したはずのバグがなぜ発生・混入したかを振り返り、チェックリストを経験から育てるための工程。

1. このバグ・問題はどの工程(要件定義・設計・仕様レビュー・実装・コードレビュー)で防げたか
2. [quality-standards](../../quality-standards/README.md)のチェックリストに追加すべき観点はあるか
3. 仕様の書き方(requirements.md/design.mdのテンプレート・記述粒度)自体に問題があったか

2.で「追加すべき観点がある」との回答を得た場合、その場で該当する層(base/company/project。使い分けは[quality-standards/README.md](../../quality-standards/README.md)参照)のチェックリストファイルへの追記を提案し、ユーザーの合意が得られれば追記する。個人の開発フロー(このSkill群自体)に起因する観点はbase、会社標準はcompany、対象プロジェクト固有の観点はプロジェクト側`.claude/quality-standards/`に追記する。

# 完了時の次ステップ案内

修正・テスト・動作確認・上記振り返りが済んだら、[/implementation-review](../implementation-review/SKILL.md)(コードレビュー)→[/pr](../pr/SKILL.md)(実装PR)へ進むことを案内する。

修正とテストをコミットした時点で、compactや新しいセッションへの切り替えを行っても支障はない。セッション終了時の出力形式は `~/.claude/session-handoff.md` に、プロンプト例は[dev-flow.md](../../dev-flow.md)の「次セッションへの引き継ぎプロンプト例」に従う。
