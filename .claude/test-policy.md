# テスト方針

開発フロー(`/requirement`〜`/pr`・`/fix`)で作る成果物(Skill・共有ライブラリ・アプリ・バッチ)に対する、テストの種類・置き場所・量・完了条件の正はこのファイル。各工程のSKILL.mdと品質基準(`quality-standards/`)は自工程で行う操作だけを持ち、判断基準はここへの参照で済ませる(同じ内容を複数箇所にコピーしない)。`~/.claude/CLAUDE.md`の「場面ごとに読む資料」から参照される。

商用案件でspec横断の総合試験・受入の根拠が要る場合は、この方針の外側を[/test-design](skills/test-design/SKILL.md)の`system-test.md`が担う。

# 基本原則

AIが仕様・実装・テストを書く開発では、テストを書く費用がほぼゼロになる一方で、仕様の思い込みが実装とテストに同時に写る(役割を別のAgentに分けても、全員が同じ仕様書を根拠にする限り同じ誤りを通す)。そのためテストの役割は「実装が仕様どおりか」の確認に加えて、**思い込みを外から破る仕組み**を持つことにある。次の4原則で判断する。

1. **量ではなく、対応の網羅と「落ちること」で判定する** — テスト件数・カバレッジ率を目標にしない。仕様項目`[n]`との対応が埋まっていること、実装を壊したときにテストが落ちることの2つで十分性を判定する
2. **検証の独立性は情報で確保する** — レビュー役を分けるだけでなく、検証側に作る側と違う情報(外部サービスの実応答・本番の実行環境)を渡す。レビュー役は実装を読む前に仕様だけから反例を出す
3. **成果物が動く環境で1回通す** — AIがテストを回すサンドボックスと、成果物が動く環境(launchd・`claude -p`・手元のシェル)は違う。無人実行・定期実行するものは本番と同じ起動経路で1回成果物が出るまで完了にしない
4. **出荷後は「成果物が出たこと」で受け入れる** — 終了コード0・ログにERRORなしは成功の証拠にならない。初回の実データ実行で成果物が出たことを受け入れ条件とし、外部が律速の非機能要件は本番の実測で合否を出す

# リスク種別

requirements.mdの`[n]`採番された仕様項目には、次の6種のうち最も当てはまるリスク種別を1つ付ける。テストの種類・量はこの種別で決める。

| リスク種別 | その項目が関わるもの | 担保するテスト種別 |
|---|---|---|
| **論理** | 自分のコードだけで閉じる計算・分岐・整形 | 単体テスト。パーサ・日時変換・集計には性質テストを足す |
| **境界** | 外部サービス・ファイル形式・他Skillの出力を読む/書く箇所 | 契約テスト(実応答由来のfixture)+ 失敗形(空・欠損・型違い・タイムアウト) |
| **生成物** | HTML・JavaScript・Markdown・plist・JSONなど、別の処理系が読むものを生成する箇所 | 生成物の構造検証 + 否定確認 |
| **環境** | launchd・`claude -p`・シェル・ネットワーク・認証に依存する起動と入出力 | 環境スモーク(本番経路で1回起動し成果物が出る) |
| **並行** | ロック・再試行・二重実行・時刻境界 | 競合を再現する単体テスト |
| **非機能** | 所要時間・呼び出し回数・トークン消費・到達率など数値で約束するもの | 自分のコードで閉じるものは性能テスト。外部が律速のものは出荷後の実測 |

テスト戦略表の「テスト種別」に書ける名前は、下記で定義する**単体 / 性質 / 契約 / 構造検証 / 環境スモーク / 性能 / evals**と、テストを置かない場合の**なし**(備考に理由を書く)だけ。「結合」「統合」のような一般的な呼び名は使わない(DB・外部APIを相手にする箇所は境界のリスクなので**契約**と書く)。

「手動確認」もテスト種別ではない。人が目で見る確認は、環境スモークか実データE2E(下記)のどちらかに言い換えて表に書く。

この禁止語の適用範囲は**spec単位のテスト**(design.mdのテスト戦略表・テストファイル名・describe/it名)に限る。spec横断の試験工程の呼び名には適用しない。[/test-design](skills/test-design/SKILL.md)の`system-test.md`は「総合試験」、社内標準のAI駆動開発ハーネスを採用したプロジェクトの試験フェーズは「結合試験」「総合試験」とそのまま呼ぶ(対応は下記「社内標準ハーネスの試験フェーズとの対応」)。

# テスト種別の定義

## 単体テスト

関数・モジュール単位の入出力を確かめる。既定の種別で、論理の項目の大半はここに入る。1つの`[n]`につき正常1件 + 分岐・境界値・エラー経路を分岐の数だけ(目安2〜4件)。テストの命名・仕様コメントは[/implementation](skills/implementation/SKILL.md)の「テストのコメント・命名ルール」に従う。

## 性質テスト

入力をランダムに大量生成し、どんな入力でも成り立つはずの性質(変換して戻すと元に戻る・件数が保存される・順序に依存しない)を確かめる。パーサ・日時変換・集計に限って使い、1つの処理につき1件。ライブラリ(hypothesis)は候補段階のため、導入前は境界値を列挙した単体テストで代替する。

## 契約テスト

外部サービス(JIRA・Confluence・Power Automate・OneDrive・Teams)やファイル形式との境界で、**実際に届いた応答**をfixtureとして保存し、こちらの読み取り処理がその形を正しく扱えるかを外部を呼ばずに確かめる。fixture 1種類につき正常1件 + 失敗形(空・欠損・型違い・タイムアウト)各1件。fixtureの扱いは下記「fixture」節。

## 生成物の構造検証

生成器1つにつき1件。生成物を「この文字列を含むか」で見るのではなく、別の処理系として読めることを確かめる。

- HTML/JavaScript: `<script>`を取り出して`node --check`(nodeが無い環境では行ごとの引用符の偶奇)で構文検証する。JSを持たない生成物でも、タグの対応・`<style>`の波括弧の釣り合い・f文字列のエスケープ漏れ(`{{` `}}`の残存)は同じ位置づけの構造検証になる
- JSON/plist/YAML: 標準ライブラリでパースできること
- Markdown: 必須見出しの存在と、Mermaidブロックのエッジラベルに半角括弧が無いこと

**検証対象が0件でも緑になることに注意する。** 生成物から要素を取り出して検査する形は、抽出が1件も無いときに「誤り無し」として通る。取り出した件数が1件以上であることをテスト自身で確かめる。生成器がその要素を持たない場合は、壊れた要素を与えれば落ちることを確かめる形にして、検査の経路が働いていることを示す。

## 環境スモーク

成果物が動く本番と同じ起動経路で1回だけ通し、ロジックではなく「起動できる・成果物が出る・失敗時の通知が届く」を確かめる。機能ごとではなく**実行経路ごと**に1回(launchd起動・`claude -p`・手元ターミナル)。tasks.md末尾の確認チェックリストに次の3項目を定型で置く。

```markdown
- [ ] 本番と同じ経路(launchd / claude -p / 手元ターミナル)で起動する → 結果
- [ ] 成果物(ファイル・通知・ページ更新)が出る → 結果
- [ ] 失敗させたときの通知・ログが届く → 結果
```

**無人実行・定期実行するものは省略不可**(3項目のいずれかが未了なら実装レビューで🔴)。チャットから人が起動するSkillは任意で、省略する場合は理由を1行書く。

## 実データE2E

外部サービスを実際に呼び、目的の動作がエンドツーエンドで1件成功することを確かめる。工程の途中では呼ばず、次の2箇所に集約する。

- 要件定義の実現性確認(`~/.claude/feasibility-check.md`) — 外部依存が要件の成立条件になる場合。ここで届いた応答をfixtureとして保存する
- 出荷後の初回実行 — 実データで成果物が出るまでタスクを完了にしない

## 性能テスト

自分のコードで閉じる数値要件(集計・生成の所要時間、API呼び出し回数、消費量)を、実データと同じ規模・ばらつきのfixtureで確かめる。数値要件1つにつき1件。

- 単体テストとは別スイート(`tests/perf/`)に置き、毎回のTDDサイクルでは回さない。実装レビューとPR作成前に1回回す
- 時間の閾値は要件値の1/2〜2/3に置く(実行環境の揺れで落ちない余裕)。時間より、呼び出し回数・件数・バイト数など毎回同じ値になる量を優先して判定する
- 要件値はrequirements.mdの`[n]`に数値で書く(「速いこと」では判定できない)

## 否定確認と変異テスト

テストが「落ちる」ことを確かめる、テストのテスト。

- **否定確認**(手動・常時): 🟢Greenのあと、分岐と生成物のテストは実装を1箇所壊して🔴Redになるのを見てから戻す。壊し方はテストのdocstringに1行残す(例: `# 否定確認: \\n を \n に戻すと落ちる`)
- **変異テスト**(機械・試行中): mutmutで変更ファイルに限定し時間上限つきで回す。生き残った変異は「意図的か」を書く。常設するかは1〜2案件の実測で決める

# 量の目安と完了条件

| リスク種別 | 1つの`[n]`あたりの量 | 十分と言える条件 |
|---|---|---|
| 論理 | 正常1 + 分岐の数(目安2〜4件)。パーサ・日時・集計は性質テスト1件 | 否定確認で分岐ごとに落ちる。変異の生存が説明つきで残っているだけ |
| 境界 | fixture 1種類につき正常1 + 失敗形各1 | fixtureが実応答由来。想像で書いたfixtureが残っていない |
| 生成物 | 生成器1つにつき構造検証1件 | わざと壊した生成物でテストが落ちることを確かめた |
| 環境 | 実行経路ごとに1回 | 本番経路で成果物が1回出た |
| 並行 | 競合1パターンにつき1件 | 競合を再現するテストが修正前の実装で落ちる |
| 非機能 | 自コード内は数値要件1つにつき性能テスト1件。外部律速は監視側に判定1つ | 性能テストが要件値の1/2〜2/3の閾値で通る。外部律速は実運用N回で数値を満たした(Nは仕様に書く) |

テストを書き終えてよい条件は次の5つがすべて満たされたとき。件数・カバレッジ率・「増やしたい」という感覚は続ける理由にしない。

1. 全`[n]`にテスト種別が割り当たり、対応するテストが揃っている
2. 分岐・生成物のテストは否定確認(または変異テスト)を通っている
3. 境界のfixtureが実応答由来で、失敗形のテストがある
4. 無人実行するものは本番経路で1回成果物が出ている
5. 順序依存・非決定的なテストがない(単独実行・順序入れ替えでも通る)

# fixture

テストのために用意する固定の入力データ。境界の項目では中身の出所が品質を決める。

- **出所**: 実現性確認・実データE2Eで実際に届いた応答をそのまま保存する。AIが仕様書から想像して書いたものは「想像fixture」と呼び、テスト戦略表の備考にその旨を書く(実応答が得られるまでの仮置き)
- **置き場所**: テストコードと同じリポジトリの`tests/fixtures/<外部サービス名>/<応答の種類>.json`など、テストから相対パスで読める場所。spec(requirements.md/design.md)には置かない
- **匿名化**: 人名・メールアドレス・会議ID・URLの個人識別部分は置き換える。**形式は変えない**(時刻のタイムゾーンを直す・欠けているフィールドを補う・件数を減らして揃える、はしない)。直した時点で実物の意味が消える
- **加工禁止**: テストが通るようにfixtureを編集しない。通らないなら、実装か仕様のどちらかが実物と合っていない

# 静的検査と道具

| 道具 | 用途 | 状態 |
|---|---|---|
| ruff | Pythonの書き方の崩れ・未使用import | 採用。実装レビュー前に回す |
| bandit | 危険な関数・秘密情報の直書きの静的検査 | 採用。Python対象。TypeScriptはeslintで代替 |
| pip-audit / npm audit | 依存パッケージの既知の脆弱性 | 採用 |
| mutmut | 変異テスト(変更ファイル限定・時間上限) | 試行中。常設は実測で判断 |
| coverage.py | カバレッジの計測 | 候補。導入しても目標値は置かず、テストの無い領域の地図として四半期の点検で見る |
| hypothesis | 性質テスト | 候補。導入前は境界値列挙で代替 |
| gitleaks | コミット前の秘密情報スキャン | 候補。サンドボックスの読み取り制限と役割が重なるため要検討 |

導入は新しいOSSの導入(`~/.claude/oss-adoption.md`)の手順で承認を得てから行う。いずれも開発時にだけ使う道具で成果物に組み込まないため、ライセンスの義務は成果物に及ばない。

# 社内標準ハーネスの試験フェーズとの対応

社内標準のAI駆動開発ハーネスは、実装フェーズのTDD(単体テスト)の後に試験フェーズ(`/test-design`)で結合試験・総合試験・性能試験・セキュリティ試験の仕様書を作り、観点セット(QA / AIC / PF / SEC / NF)で網羅を確かめる。この方針のテスト種別との対応は次のとおり。標準PJでは標準の呼び名と成果物に従い、この方針は個人リポジトリのspec単位のテストにだけ使う。

| 標準の試験フェーズ | 標準の観点セット | この方針での対応 |
|---|---|---|
| 単体テスト(実装フェーズのTDD。試験フェーズの対象外) | — | 単体 / 性質 / 構造検証 |
| 結合試験(IT) | QA / AIC | 契約 + 環境スモーク(+ 実データE2E)。spec単位では「結合」とまとめず、境界ごとに契約・環境スモークへ分けて書く |
| 総合試験(ST) | QA / AIC / NF | [/test-design](skills/test-design/SKILL.md)の`system-test.md`(spec横断の業務シナリオ・非機能・合否判定)。個人の小規模アプリ・バッチでは作らない |
| 性能試験(PT) | PF | 性能テスト(自分のコードで閉じるもの)と出荷後の実測(外部が律速のもの) |
| セキュリティ試験(SCT) | SEC | 静的検査と道具(`bandit`・`pip-audit`・秘密情報の静的検査)。DASTは対象外(下記) |

# 対象外・採用しないもの

- **DAST**(動かして外から攻める検査): 公開エンドポイントを持たないため対象がない。代わりに秘密情報の静的検査と依存の脆弱性確認を行う。公開APIを持つ成果物ができたら再検討する
- **カバレッジ率の目標値**: 目標にするとAIが目標へ最適化して薄いテストが増える。計測はしても判定には使わない
- **E2E自動化の拡大**: UIがあり継続的に改修が入るプロジェクトの主要シナリオに限る。Power Automate・OneDrive・Teamsは自動テストから動かす手段が無い
- **工程途中での外部サービス呼び出し**: 実現性確認と出荷後の初回実行に集約する

# 手順書(Skill本文)の検証

開発フローSkillの本文そのものは、`evals/`のpromptfooによる回帰テスト(requirement / design / spec-review の3本)で「この依頼を渡すとこの形の成果物が返る」を採点する。**design.mdのテスト戦略表では、この検証の種別名を `evals` と書く**(リスク種別ベースの7種とは別枠。Skill本文の検証は7種のどれでもないため、表に書ける名前をここで与える)。Skill本文を改修したときに手元ターミナルで回す(実施方法は[evals/README.md](evals/README.md))。1回あたり数分・数万トークンを消費するため、implementation / fix 向けの追加は行わず、リンク切れ・参照先ファイルの実在などは静的検査で補う。
