# JIRAチケット自動更新(GitHub Actions連携) 設計

## 処理フロー

### PR作成・更新時のJIRA更新

対象: PR作成(opened)・更新(synchronize)イベント

手順:
1. PRのブランチ名からJIRAチケットキーを正規表現で抽出する(複数のキーらしき文字列が含まれる場合は、最初に一致した1件のみを対象とする)
2. 抽出できない場合、以降の処理を行わずに終了する(エラーではなく正常系の分岐)
3. 抽出できた場合、対象チケットの現在のステータスに対して有効な遷移一覧をJIRAから取得する
4. 有効な遷移の中に「レビュー中」への遷移が含まれる場合、その遷移を実行する。含まれない場合はステータス変更を行わずスキップする
5. イベント種別(作成/更新)・PRタイトルとURL・変更内容概要・変更ファイル一覧(または件数)をまとめて、対象チケットにコメントを追記する

関連するビジネスルール: [requirements.md#pr作成更新時の自動更新](requirements.md#pr作成更新時の自動更新)、[requirements.md#ビジネスルール制約](requirements.md#ビジネスルール制約)[2][3]

### PRマージ時のJIRA更新

対象: PRクローズイベントのうち、マージによるクローズ(merged=true)のみ

手順:
1. PRのブランチ名からJIRAチケットキーを抽出する(複数のキーらしき文字列が含まれる場合は、最初に一致した1件のみを対象とする)。抽出できない場合は以降の処理を行わずに終了する
2. マージされたPRの変更ファイル一覧を取得する
3. 変更ファイルがすべて仕様関連ディレクトリ(`specs/`配下、または`apps/*/specs/`配下)内であれば「仕様承認PRのマージ」、1件でもそれ以外のファイルを含む場合は「実装PRのマージ」と判定する
4. 判定結果に応じて遷移先ステータス名を決める(仕様承認PRのマージの場合は「進行中」、実装PRのマージの場合は「完了」)
5. 対象チケットの現在のステータスに対して有効な遷移一覧を取得し、4で決めた遷移先が含まれる場合のみ実行する。含まれない場合はステータス変更を行わずスキップする
6. PRタイトル・URL・変更内容概要をまとめて、対象チケットにコメントを追記する

関連するビジネスルール: [requirements.md#prマージ時の自動更新仕様承認pr](requirements.md#prマージ時の自動更新仕様承認pr)、[requirements.md#prマージ時の自動更新実装pr](requirements.md#prマージ時の自動更新実装pr)、[requirements.md#ビジネスルール制約](requirements.md#ビジネスルール制約)[2][3]

## エラーハンドリング

- JIRA API呼び出し(コメント投稿・遷移一覧取得・遷移実行)がエラーになった場合、ワークフロー全体を失敗させない。エラー内容をログに記録した上で、そのジョブは成功終了とする([requirements.md#ビジネスルール制約](requirements.md#ビジネスルール制約)[1]に基づく非ブロッキング設計)
- JIRA REST APIの一時的な5xxエラー・レート制限には、簡易的なリトライ(1〜2回、短い間隔)を行う。それでも失敗する場合は上記の通りログのみ記録して終了する
- フォークからのPR(`pull_request`イベントでリポジトリのシークレットが渡らないケース)は、JIRA APIトークンが取得できないためJIRA更新処理自体を行わずスキップする。GitHub Actionsの標準的な権限モデルにより自然にスキップされるが、実装上も「シークレットが空の場合は早期終了する」ガードを明示的に入れる

## 関連するファイル(抜粋)

- `.github/workflows/jira-sync.yml`(新規) — `pull_request`イベント(`opened`/`synchronize`/`closed`)をトリガーに本処理を実行するワークフロー定義。他ジョブへの依存を持たない単独ジョブとして実行する
- `.github/scripts/jira-sync/`(新規、Node.js/TypeScript) — 本処理のスクリプト本体
  - `index.ts` — GitHub Actionsから渡されるイベントペイロード・環境変数を読み取り、各関数を組み合わせて実行するエントリポイント
  - `extractIssueKey.ts` — ブランチ名からJIRAチケットキーを抽出する
  - `classifyMerge.ts` — 変更ファイル一覧から「仕様承認PRのマージ」か「実装PRのマージ」かを判定する
  - `resolveTransition.ts` — 現在有効な遷移一覧から、指定した遷移先ステータス名に一致する遷移を解決する
  - `buildComment.ts` — コメント本文を組み立てる
  - `jiraClient.ts` — JIRA REST API(コメント追加・遷移一覧取得・遷移実行)の呼び出しをラップする
- `.claude/skills/pr/SKILL.md`(既存・更新) — ブランチ命名規約を`feature/<機能名>` → `feature/<JIRAキー>-<機能名>`に変更する

作業開始時のJIRAチケット確認(存在確認→キー取得、または新規作成/チケット管理なしの選択)は、study固有ではなくこのPC全体のグローバル方針であるため、本specの対象外([前提](requirements.md#前提-チケットキーとブランチの紐付け)[3]参照)。`~/.claude/CLAUDE.md`・`~/.claude/skills/requirement/SKILL.md`・`~/.claude/skills/fix/SKILL.md`側で対応済み。

## セキュリティ

- JIRA APIトークンはGitHub Actionsのリポジトリ(または組織)シークレットとして保存し、ワークフローYAML・スクリプト内に平文で書かない
- フォークからのPRに対してはJIRA更新処理をスキップする(上記エラーハンドリング参照)。これにより外部コントリビューターがブランチ名やPR内容を細工しても、シークレットにアクセスできず不正なJIRA操作はできない
- ブランチ名・PRタイトルなど外部から渡る値をシェルコマンドに直接展開しない(JavaScriptの変数として扱い、シェルインジェクションを避ける)
- コメント本文に転記するのはファイルパス・PRタイトル・URLのみとし、ファイルの中身は転記しない

## ログ

- 処理開始時: 対象PR番号・イベント種別、抽出したJIRAチケットキー(抽出できなかった場合はその旨)をINFOレベルで出力する
- コメント投稿・ステータス遷移それぞれについて、成功/スキップ(遷移先が見つからない等)/失敗をINFOまたはWARNレベルで出力する
- JIRA API呼び出しが失敗した場合、エラー内容(ステータスコード・エンドポイント)をWARNレベルで出力する(処理自体は継続・正常終了する)
