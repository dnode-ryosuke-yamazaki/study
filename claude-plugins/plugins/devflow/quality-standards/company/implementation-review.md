# 会社標準 品質基準追加分 — implementation-review

社内のAI駆動開発 標準テンプレート(`add-skeleton`)の `.claude/rules/coding-standards.md`(言語非依存の共通規約)から、コードレビューの観点として効く項目を抜き出したもの。成果物の書式(フロントマター・ID体系・必須見出し)に依存する規約はここには入れない(標準テンプレートを採用したリポジトリ側の `.claude/quality-standards/implementation-review.md` に置く)。重要度基準・フィードバックテンプレートはbase層を継承する。見出しに添えた `CR-xx` はbase層のチェックリスト見出し(社内標準のコードレビュー観点ID)との対応で、合成するときはその観点の下に加える。

## 追加チェックリスト

### エラーハンドリング(CR-09 エラーハンドリング・ログ)
- [ ] 🔴 捕捉した例外を握りつぶしていないか。捕捉したら「処理する・変換して再送出する・そのまま再送出する」のいずれかを必ず行っているか
- [ ] 🟡 利用者向けのエラーメッセージと開発者向けのログが区別され、スタックトレース・SQL・内部パスなどの内部情報が利用者に露出していないか
- [ ] 🔴 外部システム呼び出し(API・DB・ファイルI/O)ごとに、失敗時の挙動(再試行するか・呼び出し元に何を返すか・処理を続けるか止めるか)が実装されているか

### セキュリティ(CR-07 セキュリティ)
- [ ] 🔴 秘密情報(APIキー・パスワード・接続文字列・トークン)をコードやリポジトリにハードコードしていないか
- [ ] 🔴 外部からの入力(リクエスト・ファイル・環境変数・他システムの応答)をすべて検証してから使っているか(インジェクション対策)
- [ ] 🟡 認証・認可のロジックを設計書の方針どおりに実装しているか。独自判断で簡略化していないか

### 命名・構造(CR-02 可読性 / CR-03 保守性・拡張性 / CR-04 設計・責務分離)
- [ ] 🟡 名前が役割の読み取れる完全な単語で構成され、独自の省略形を作っていないか。言語・フレームワークの標準的な命名慣習(ケース規則等)に従っているか
- [ ] 🟡 定数・設定値・マジックナンバーが名前付き定数として定義されているか
- [ ] 🟡 1関数・1メソッドが1つの責務に収まっているか。3段以上の深いネストが早期リターン等で解消されているか

### コメント・可読性(CR-02 可読性 / CR-06 パフォーマンス)
- [ ] 🟢 コメントが「コードから読み取れないこと」(制約・仕様上の理由・外部システムの都合)に絞られ、コードの動作をなぞるだけのコメントになっていないか
- [ ] 🟢 性能最適化が計測結果に基づいて行われ、その理由がコメントに残っているか(計測なしの最適化で可読性を落としていないか)

### テスト(CR-05 テスタビリティ)
- [ ] 🔴 既存テストの形骸化がないか: 差分の中で既存テストを削除・skip(`@pytest.mark.skip`・`xit`・`test.skip` 等)・`.only`化していないか、アサーションを削除・緩和(期待値をゆるめる・例外を握りつぶす・常に真になる条件に置き換える)していないか。既存テストへの変更は1件ずつ「仕様変更に伴う正当な修正」か「テストを通すための弱体化」かを判定し、正当な場合はPR本文に理由があることを確かめる(理由が無いものは🔴)
- [ ] 🟡 テストが他のテストの実行順序に依存していないか(単独実行・順序入れ替えでも通るか)
