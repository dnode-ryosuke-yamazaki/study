# コードレビューのチェックリスト(base)

code-reviewerエージェント(またはエージェントを使えない状況で直接レビューするメインスレッド)が読むファイル。レビュー実施者以外はこのファイルを読まない(トークン節約のため[implementation-review/SKILL.md](../../skills/implementation-review/SKILL.md)本体から分離している)。会社標準・プロジェクト固有の追加チェック項目がある場合は、company層・project層のファイルと合成して使う(合成ルールは[README.md](../README.md))。

# レビューの注意事項

- **レビュー中はコードを修正しない。** 指摘の報告に徹する(修正は[/devflow:resolve](../../skills/resolve/SKILL.md)の仕事)。Bashは検証コマンド(対象プロジェクトのテスト・lint・buildコマンド、`git diff`など)の実行にのみ使い、ファイルを変更するコマンドは実行しない
- **好みの問題は指摘しない。** 指摘には必ず根拠(承認済み仕様との不一致、CLAUDE.mdの規約、テスト・CIの失敗、[/devflow:implementation](../../skills/implementation/SKILL.md)の命名ルールなど)を添える。根拠を示せない指摘は出さない
- **良い点も必ず1つ以上挙げる**
- **セキュリティ(CR-07)は指摘が無くても根拠を書く。** 何を確認して問題なしと判断したかをテンプレートの「セキュリティの確認根拠」に残す(「問題なし」の一言で済ませない。AIが見落としやすく、見落とすと重症化する観点なので、確認の事実を承認者が検証できる形で残す)
- **レビュー結果に応じて次のステップを案内する**(テンプレート末尾の案内を必ず含める)

# チェックリスト

見出しの `CR-01`〜`CR-10` は、社内標準のAI駆動開発ハーネスがコードレビュー観点に付けている固定IDで、標準PJのレビュー結果と並び・呼び名を揃えるために併記する(観点の定義は標準側が正で、ここには転記しない。手元固有の項目は最も近い観点の下に置く)。「反例」は観点ではなく実装を読む前の手順なので、観点の前に置く。

## 反例(実装を読む前に行う)
- [ ] 差分と実装コードを読む**前に**、requirements.md/design.mdだけを読んで「この入力・この状況ならどうなるか」という反例を3つ挙げたか(外部応答の形が仕様の想定と違う場合・空や欠損・時刻や文字種の境界・二重実行など)。実装者と同じ仕様書を読んでも、実装を見てから考えると実装の前提に引きずられるため、順序を守る
- [ ] 挙げた反例それぞれについて、対応するテストがあるか。無ければ🟡(仕様に無い振る舞いを要求するものは🟢の質問として出す)

## CR-01 正しさ
- [ ] 実装がrequirements.mdのビジネスルール・design.mdの処理フローと一致しているか(境界値・エラー時の振る舞いを含む)
- [ ] 承認された仕様にない機能・挙動を勝手に追加していないか
- [ ] design.mdの必須5見出し(処理フロー・エラーハンドリング・関連するファイル・セキュリティ・ログ)で決めた方針が実装に反映されているか(例: 設計で書いたエラー処理・入力サニタイズ等のセキュリティ対策・ログ出力に対応するコードが実際に存在するか)。設計で「特になし」とせず検討した項目が、実装で欠落していないか
- [ ] UTC(や実行環境のロケール)の日時から暦日を取り出していないか。「当日」「最終日」「出力ファイルの日付」のように人が暦で見る値を`now.date()`で取っていないか。時刻の比較にUTCを使うのは正しいが、そこから日付を作るときは業務のタイムゾーンへ直す(定時実行バッチは実行時刻がタイムゾーンの境界をまたぐと、実行時刻を動かすまで表に出ない)
- [ ] UIに変更がある場合、`run`Skill等でアプリを起動・操作し、変更箇所の表示を実際に確認したか
- [ ] UIを持たないAPI・バッチ処理の変更の場合、curl・統合テスト等でエンドポイントや処理を直接呼び出して確認したか
- [ ] **無人実行・定期実行する変更の場合、環境スモーク3項目(本番と同じ経路で起動する・成果物が出る・失敗時の通知が届く)がtasks.md末尾に結果つきで揃っているか。1つでも未実施なら🔴**(サンドボックス内で関数を直接呼んだ結果・スタブテストは環境スモークにならない)。一晩待つ等で当日通せない場合は、未了であることと外れたときの影響を残件として明記しているか([テスト方針](../../test-policy.md)「環境スモーク」)

## CR-02 可読性
- [ ] 初見の読み手が、名前と処理の流れだけで意図を追えるか(コードの動作をなぞるだけのコメント・独自の省略形・途中で意味が変わる変数・深いネストが無いか)

## CR-03 保守性・拡張性
- [ ] 変えたくなる事柄が1か所に閉じているか。閾値・設定値が名前付き定数か設定ファイルに出ているか。既存の共通処理を探さずに同じ処理を複製していないか(AI生成で起きやすい)

## CR-04 設計・責務分離
- [ ] design.mdの「関連するファイル」で決めた配置・責務どおりに実装されているか(設計に無いレイヤー跨ぎ・1関数への責務の集中・UI/IOと業務ロジックの混在が無いか)。architecture.mdを持つプロジェクトでは、関連ADRで却下した方式が紛れ込んでいないか

## CR-05 テスタビリティ
- [ ] 対象プロジェクトのテストコマンドが全て通るか
- [ ] requirements.md/design.mdの仕様項目に対応するテストが揃っているか(仕様コメントの見出し・`[n]`表記が仕様書と完全一致するか、[/devflow:implementation](../../skills/implementation/SKILL.md)参照)。design.mdのテスト戦略で宣言した種別(単体/性質/契約/構造検証/性能)のテストになっているか。対応するテストがない項目がある場合、意図的な省略かどうかを確認する
- [ ] 境界値・特殊ケース・エラーケースのテストがあるか
- [ ] 分岐と生成物のテストに否定確認の記録(docstringの「否定確認: …」)があるか。生成物のテストが部分一致だけで判定していないか(構造検証になっているか)
- [ ] **構造検証のテストが、検証対象を1件以上見つけたことをテスト自身で確かめているか**(生成物から要素を取り出して検査する形は、抽出が0件でも緑になる)。生成器がその要素を持たない場合、検査の経路が働くことを確かめる形になっているか([テスト方針](../../test-policy.md)「生成物の構造検証」)
- [ ] 契約テストのfixtureが実応答由来か(テスト戦略の備考と一致するか)。テストを通すためにfixtureが編集されていないか(タイムゾーンの書き換え・フィールドの補完・件数の間引き)
- [ ] テストが他のテストの実行順序・実行時刻・環境変数に依存していないか(単独実行・順序入れ替えでも通るか)
- [ ] 外部依存(時刻・乱数・外部サービス)が差し替え可能になっているか(内部で直接生成していてテストから固定できない形になっていないか)

## CR-06 パフォーマンス
- [ ] 想定データ量(requirements.mdの非機能要件・design.mdの処理フロー)で破綻する箇所が無いか(ループ内の問い合わせ・全件取得後の絞り込み)。計測の裏付けが無い最適化で可読性を落としていないか
- [ ] 性能テストを宣言している場合、`tests/perf/`が要件値の1/2〜2/3の閾値で通るか

## CR-07 セキュリティ
- [ ] design.md「セキュリティ」で決めた対策(入力の検証・サニタイズ、個人情報・機微情報の扱い)が実装に存在し、設計に書かれていない入力経路(環境変数・ファイル・他システムの応答)にも同じ扱いが及んでいるか
- [ ] 秘密情報のハードコード・エラーメッセージへの内部情報の露出・認証認可の省略が無いか
- [ ] セキュリティ系の静的検査が通るか: `bandit -r <対象>`・`pip-audit`(Pythonの場合。導入前のプロジェクトでは実行できない旨を報告し、指摘にはしない)
- [ ] **指摘が無くても根拠を残したか**: 確認した観点と、何を読み・何を実行して確かめたかを、レビュー結果の「セキュリティの確認根拠」に書いたか(該当コードが無い変更でも、そう判断した理由を書く)

## CR-08 一貫性・規約遵守
- [ ] CLAUDE.mdの規約に沿っているか(コメントは日本語、関数・型に役割と非自明な計算式・定数の根拠をコメント、過剰な抽象化をしない)
- [ ] 既存コードと同じ書き方・同じ共通処理・同じライブラリを使っているか(セッションごとに別のスタイルや別のライブラリを持ち込んでいないか)
- [ ] 対象プロジェクトのlint・buildコマンドが定義されている場合、それらが通るか(Pythonなら`ruff check`。導入前のプロジェクトでは実行できない旨を報告し、指摘にはしない)
- [ ] デバッグコード・不要なファイル・未使用のimportが残っていないか

## CR-09 エラーハンドリング・ログ
- [ ] design.md「エラーハンドリング」「ログ」で決めた方針どおりか: 捕捉した例外を握りつぶしていないか、外部呼び出しの失敗時の挙動(再試行・呼び出し元への返し方・続行か停止か)が実装されているか、ログに機微情報が混ざっていないか
- [ ] 失敗時のログ・通知から後で原因を切り分けられるか(例外の型名だけを残していて、どの種類の失敗かを復元できない状態になっていないか)。機微情報を避けるために情報を削った結果、再現しないと原因が分からないログになっていないか

## CR-10 ドキュメント・意図の共有
- [ ] requirements.md のステータスのラベルが「実装中」に書き換わっているか(`ステータス: … ／ 優先度: …` の1行。引用 `>` で書いていないか)
- [ ] 実装中に仕様を変更した場合、3点セットが同じ変更で更新されているか
- [ ] 判定条件・分岐の条件を実装で変えた場合、その条件を説明している文が全部同じ世代になっているか(design.mdの処理フロー・決定事項の表・appendix.md・requirements.mdの対応する `[n]`・その条件を書いているSKILL.md)。判定名で横断検索して、古い世代の説明が残っていないかを見る
- [ ] specフォルダの増減・依存関係の変化がある場合、`architecture.md`を採用しているプロジェクトなら機能マップが追随しているか
- [ ] 却下した代替案・非自明な判断の理由が、コミットメッセージ・ADR・コメントのいずれかから辿れるか(実装は変わったのに仕様書が古いまま、AIが決めた事項が誰の判断か分からない、という状態になっていないか)

# 指摘の重要度

| 重要度 | 意味 | 扱い |
|---|---|---|
| 🔴 must | マージできない問題(仕様との不一致、テストの欠落・失敗、CI失敗の原因) | 修正するまで/devflow:prに進まない |
| 🟡 should | 修正が望ましい問題(規約逸脱、テスト命名ルール違反、可読性) | 原則今回対応する |
| 🟢 info | 参考情報・質問・提案 | 対応は任意 |

# フィードバックのテンプレート

```markdown
## コードレビュー結果: <承認(指摘なし) / 要修正(🔴n件・🟡n件・🟢n件)>

### 対象
feature/<機能名> の変更差分

### 参照したチェックリスト
- base (常に)
- company(会社標準。適用した場合のみ記載)
- project(プロジェクト固有。適用した場合のみ記載)

### 良い点
- (必ず1つ以上)

### 指摘事項
| # | 重要度 | 対象 | 指摘内容 | 根拠 |
|---|---|---|---|---|
| 1 | 🔴 must | path/to/file.py:42 | ... | ... |

### 動作確認(UI変更がある場合は必須。ない場合はこの欄ごと省略)
- 確認したフロー: (例: DELETE /notes/{id} を呼び出し204が返ることを確認)
- 結果: 想定どおり / 問題あり(→指摘事項の#nを参照)

### セキュリティの確認根拠(CR-07。指摘が無くても省略しない)
- 確認した観点: (例: 入力の検証経路 / 秘密情報のハードコード / 認証・認可 / エラー時の内部情報の露出)
- 確認方法: (読んだファイル・実行した検査。該当コードが無い変更なら「対象コード無し」とそう判断した根拠)
- 結果: 問題なし / 問題あり(→指摘事項の#nを参照)

### 確認をお願いしたい箇所
- (人が読んで判断する必要がある箇所だけを、ファイル名と見出し(または行)で指す。指摘事項のうち対応が人の判断に委ねられるものはここに転記する。無ければ「なし」)

### 判断をお願いしたい事項
- (レビュアーでは決められない事項を質問の形で書く。選択肢がある場合は選択肢と各選択肢の影響を添える。無ければ「なし」)

### AIが確認済みの範囲(通読を省略してよい範囲)
- (このレビューで実際に読んだファイル・見出しと、実行して確かめた検証。承認者が省略の根拠を判断できるよう「何を確認したか」を添える)

### AIでは確認できなかった範囲
- (読めなかったファイル・実行できなかった検証・判断材料の不足で推測に留まった点。「なし」と書く前に、本当に無いかを確かめる)

### 次のステップ
- 🔴/🟡あり → /devflow:resolve で修正し、再レビューを受ける
- 指摘なし(🟢のみ) → /devflow:pr で実装PRを作成する
```

末尾の4区分(確認をお願いしたい箇所 / 判断をお願いしたい事項 / AIが確認済みの範囲 / AIでは確認できなかった範囲)は、承認者が全文を通読しなくても判断できるようにするためのもので、省略しない。「確認をお願いしたい箇所」は人の判断・合意が要るものに絞り、水増ししない(迷ったら、人が判断すべき内容を見落とさないよう「確認をお願いしたい箇所」側に寄せる)。「AIが確認済み」にできるのは、機械的に確かめられて判断の余地がない範囲だけで、「承認してよい」「確認不要」のような承認の代弁は書かず、確認した事実だけを書く。「セキュリティの確認根拠」も同じ趣旨で、指摘が無いときほど省略しない(確認の事実が無いと、承認者は「見ていない」と「見て問題なかった」を区別できない)。
