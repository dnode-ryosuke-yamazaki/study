# 仕様レビューのチェックリスト(base)

spec-reviewerエージェント(またはエージェントを使えない状況で直接レビューするメインスレッド)が読むファイル。レビュー実施者以外はこのファイルを読まない(トークン節約のため[spec-review/SKILL.md](../../skills/spec-review/SKILL.md)本体から分離している)。会社標準・プロジェクト固有の追加チェック項目がある場合は、company層・project層のファイルと合成して使う(合成ルールは[README.md](../README.md))。

# レビューの注意事項

- **レビュー中は対象を修正しない。** 指摘の報告に徹する(修正は[/devflow:resolve](../../skills/resolve/SKILL.md)の仕事)
- **好みの問題は指摘しない。** 指摘には必ずルール上の根拠([/devflow:requirement](../../skills/requirement/SKILL.md)・[/devflow:design](../../skills/design/SKILL.md)のテンプレート、CLAUDE.mdの規約、既存specとの整合性など)を添える。根拠を示せない指摘は出さない
- **良い点も必ず1つ以上挙げる**
- **レビュー結果に応じて次のステップを案内する**(テンプレート末尾の案内を必ず含める)

# チェックリスト

## requirements.md
- [ ] ユーザーストーリーが利用者視点(「〜としては、〜したい」)で書かれているか
- [ ] ビジネスルールの数値・条件に根拠(法令・公式資料・過去の意思決定)が添えられているか
- [ ] 外部ツール・コマンドのオプションを安全機構(禁止・遮断・制限)としてビジネスルールに書いている場合、そのオプションが**何を保証するか**をヘルプ・公式ドキュメントの原文で確認した根拠が添えられているか。「対象を事前承認するだけのオプション」を「範囲外を拒否するオプション」と取り違えていないか(取り違えると、仕様上は守られているつもりの一次防御が実際には存在しない状態になる)
- [ ] テストを対応させたい箇条書きに`[n]`が振られているか。「〜の場合、〜になること」の文体になっているか
- [ ] `[n]`を振った各項目にリスク種別(論理/境界/生成物/環境/並行/非機能)が添えられているか。非機能要件が数値(〜件を〜秒以内・〜回以下)で書かれているか(定義は[テスト方針](../../test-policy.md))
- [ ] 数式・変数名・実装方法(HOW)が混ざっていないか
- [ ] スコープ外(今回やらないこと)が明記されているか
- [ ] 新規specならステータスが「仕様確認中(未実装)」になっているか(置き場は下の「先頭の見出し」の項目を見る)
- [ ] 他specへの依存が内容の書き写しでなく`<spec名>/requirements.md#見出し-n`の参照形式になっているか
- [ ] ユーザー入力・リクエストの極端なパターン(未入力・境界値・想定外の値)に対する挙動がビジネスルールとして決まっているか
- [ ] 日付・時刻を扱う仕様で、**基準日をどのタイムゾーンで求めるか**が書かれているか。実行時刻だけを決めて基準日の定義を書かないと、実装がUTCで日付を取っても仕様違反にならず、実行時刻を変えた日に初めて1日ずれが表に出る
- [ ] 先頭の見出しが`## 概要`で、誰の何を解決するか・この仕様で作るものと何のために要るか・進め方が読み取れるか。タイトルと最初の`##`の間にステータスのラベル1行以外を置いていないか。要約だけを並べる「サマリ」の見出しを置いていないか
- [ ] **ユースケース図**があるか。無い場合、省略した理由が一言添えられているか([architecture-workflow](../../skills/architecture-workflow/SKILL.md)の「図の運用方針」)
- [ ] 会話で確認していない方針が推測で書かれていないか(会話ドリブン原則)

## 層分けと出所の目印(requirements.md / design.md / architecture.md 共通)

- [ ] **機械検査の違反は1件を🔴(修正必須)の指摘1件として扱う**(起動指示に添えられた違反一覧をそのまま指摘に写す)。検査を実施できなかった場合(区分け表が読めない・起動失敗)も🔴1件として扱い、原因を報告に書く
- [ ] 読み手がAIの見出しが「見出し → 見える要点1〜2行 → `<details>`で畳んだ本文」の形になっているか。読み手が人の見出しを畳んでいないか(判定は機械検査に任せてよい)
- [ ] 承認者が読む行(人が読む見出しの箇条書き・AIが読む見出しの要点行・決定事項の表の行)に`〔合意〕`か`〔提案〕`がちょうど1つ付いているか
- [ ] **このspecで新しく作るもの(表・設定ファイル・スクリプト・生成物)について、名前の初出で「誰が何のために使うか」「何が入っているか」が読み取れるか。**名前を出すだけ・名前に種類を足すだけで、何のために作るのかが書かれていないものは🟡。目的は、それを使う機能要件の要点行か、その成果物を定義しているビジネスルールの要点行のどちらかにあるか
- [ ] **見えている行が、その行だけを読んで意味が取れるか。**「数値なし・根拠あり」のような定型の圧縮、意味を添えない絵文字・社内略語が残っていないか
- [ ] **要点行・図の説明・タスク名で、主語(何が・誰が)と対象(何を・どのファイルを)が省かれていないか。**「読むだけで書かない」「手順書を直す」のように、何の話か分からない行が残っていないか
- [ ] **起動指示に添えられた「承認者が実際に目にする行」だけを通しで読み、意味の取れない行を挙げたか。**仕様書の他の部分を読んで補完しないこと(承認者はその行しか読まない)
- [ ] 用語の説明だけを並べた節(用語集・前提知識)を文書の前段に置いていないか。説明はその語を使う見出しの中で補われているか
- [ ] tasks.md のタスク名が、開かなくても何をするか分かる言い方になっているか。各タスクに何のための作業かの1行が付いているか
- [ ] **承認者が「合意した覚えのない〔合意〕」を指摘した場合は🔴1件として扱う**([/devflow:resolve](../../skills/resolve/SKILL.md)で直してから承認に進む)。目印が本当に会話で決めたことを指しているかは機械では検査できず、承認者の目視だけが頼りになる

## design.md(作成している場合)

形式:
- [ ] 必須5見出し(処理フロー・エラーハンドリング・関連するファイル・セキュリティ・ログ)が検討されているか。安易な「特になし」で済ませていないか
- [ ] 処理の呼び名が業務的な言葉になっているか(関数名・ファイル名などの実装詳細が混ざっていないか)
- [ ] 手順が日本語の文章で書かれ、分岐が「〜の場合は…、そうでない場合は…」の形で網羅されているか
- [ ] 先頭の見出しが`## 概要`で、処理の全体像が読み取れるか。タイトルと最初の`##`の間に本文を置いていないか(ステータスのラベルを持つのは requirements.md だけ)
- [ ] 概要の直後に**決定事項**の表(論点 / 選んだ案 / 採らなかった案 / 理由 / 影響範囲 / 出所 の6列)があるか。分かれ道が無い設計では「決定事項なし」と1行書かれているか
- [ ] 決定事項の直後に**品質統制の適用**の表(統制 / 判定 / 理由 / 反映先 / 出所 の5列)があり、IMC-01〜06 の6行が対象外の行も含めて全部そろっているか。「判定」が`適用`か`対象外`のどちらかで、対象外の行に当てはまらない根拠が1行書かれているか(観点は[/devflow:design](../../skills/design/SKILL.md)の「品質統制の適用」。統制の定義は社内標準ハーネスの implementation-control-catalog.csv が正)
- [ ] **本文で選択・却下を述べている箇所が、決定事項の表に1行ずつ載っているか**(処理フロー・エラーハンドリング・セキュリティの本文に「〜とする」「〜は採らない」とあるのに表に無いものは🔴。表の網羅は機械では検査できないため、ここで目視する)
- [ ] 設定・キャッシュ・コマンド・ログの書式が design.md の本文でなく appendix.md に移され、design.md にリンクが1行残っているか
- [ ] 作成条件を満たす**Mermaid図**(シーケンス図・画面遷移図・状態遷移図)が描かれているか。無い場合、省略した理由が一言添えられているか

中身:
- [ ] requirements.mdの全ビジネスルールが処理フローのいずれかでカバーされているか(設計漏れがないか)
- [ ] 境界値・特殊ケース(空・NULL・上限値ちょうど、想定外の入力など)が分岐として現れているか
- [ ] エラーハンドリングが起こりうる失敗ごとに具体的か(何が失敗したら・呼び出し元に何を返し・処理を継続するか中断するかまで決まっているか)
- [ ] 失敗時にログ・通知へ**何を残すか**が決まっているか。機微情報を出さない制約(何を出さないか)だけを書いて、運用者が原因を切り分けられる情報(どの段階の・どの種類の失敗か)を残すことが決まっていない状態になっていないか。無人実行・バッチのように後からログだけで調べる機能では特に重要
- [ ] セキュリティがこの機能固有のリスクを検討しているか(保存する個人情報が必要最小限か、外部からの入力をどこまで信頼するかを考えたか)
- [ ] **品質統制の判定が機能の中身と合っているか。** 更新・削除・外部連携があるのに IMC-02 冪等性や IMC-03 監査ログを`対象外`にしている、外部入力・永続化・通信があるのに IMC-06 を`対象外`にしている、のように適用条件に当たる統制を外していれば🔴
- [ ] 品質統制で`適用`にした行の「反映先」の見出しに、その対策が実際に書かれているか(IMC-01 は個人情報をログ・レスポンスに出さない扱い、IMC-02 は同じ依頼が2回来たときの結果、IMC-03 は誰が・何に・何をして・結果どうなったかを残すログ、IMC-06 は入力の信頼範囲と認可)。反映先に書かれていなければ🟡。適用を理由に、要件に無い仕組み(監査用テーブル等)を合意なく足していれば🔴(会話ドリブン原則)
- [ ] IMC-01・IMC-06 を`対象外`にした行は、人の確認が要る判定として「確認をお願いしたい箇所」に挙げたか(標準でも人のレビューを必須にしている)
- [ ] データベース設計がある場合、型・キー設計に根拠があるか。既存の属性・テーブルと重複していないか
- [ ] 画面設計がある場合、正常表示以外の状態(ローディング・エラー・空・未入力)が考慮され、既存画面と用語・操作感が一貫しているか
- [ ] specフォルダに画面モック`mock.html`がある場合、requirements.mdの「UI/UX要件」がモックを参照し、design.mdの画面設計の表示項目・操作・画面遷移図の状態がモックの画面・状態と1対1に対応しているか(モックにだけある振る舞いが requirements.md に書かれずに残っていないか)
- [ ] 省略された任意見出し(バリデーション・パフォーマンスなど)が本当に該当しないか。逆に、書かれている見出しで実装に委ねてよい詳細まで書き込んでいないか
- [ ] 設計がプロジェクト構成・既存のアーキテクチャ決定と矛盾なく実現可能か
- [ ] 自動化・バッチが作る運用ファイル(申し送り・作業メモ・ログ・下書き)がある場合、その置き場所がリポジトリの成果物と分けて決まっているか。人手での削除・後片付けを前提にした仕様になっていないか
- [ ] 外部ツールの表示・出力から読み取る値について、それが本来不変(または月次などで変わる固定値)なら、毎回読み直す設計ではなく設定に持つ設計になっているか
- [ ] **テスト戦略**見出しがあり、requirements.mdの全`[n]`採番された仕様項目にリスク種別とテスト種別(単体/性質/契約/構造検証/環境スモーク/性能/出荷後の実測)が割り当てられているか(割り当て漏れがないか)。「手動確認」がテスト種別として残っていないか(環境スモークか実データE2Eに言い換える)。E2E自動化を選んでいる項目がある場合、「UIがあり継続的に改修が入るプロジェクトの主要シナリオ」の基準に沿っているか(基準の正は[テスト方針](../../test-policy.md))
- [ ] 境界の項目に、fixtureの出所(実現性確認で保存した実応答か、想像fixtureか)が備考に書かれているか。想像fixtureのまま実応答を得る予定がないものは🟡
- [ ] 生成物(HTML・JavaScript・Markdown・plist・JSON等)を作る機能で、生成器ごとの「構造検証」の行があるか
- [ ] 無人実行・定期実行する機能で、「環境スモーク」の行があるか。無ければ🔴(省略不可)。チャット起動のSkillで省略している場合は理由が書かれているか

## tasks.md(作成している場合)
- [ ] 各タスクが🔴Red→🟢Green→🔵Refactorで完結できる粒度か
- [ ] 冒頭にTDD宣言文があるか
- [ ] design.mdの全処理がいずれかのタスクでカバーされているか
- [ ] タスクの並び順が依存関係の順(先に必要なものが先)になっているか
- [ ] **全タスクに`【担当: claude】`または`【担当: copilot】`が付いているか**(条件なし。`~/.claude/config/agent-routing.json`が無いマシン・プロジェクトでも全タスクを`【担当: claude】`にして付ける。マークが1つも無いtasks.mdは、判定した結果claude担当になったのか判定自体を飛ばしたのかが区別できないため🟡指摘とする)
- [ ] `~/.claude/config/agent-routing.json`がある場合、**全タスクがclaude担当になっているなら、その理由**(設定の付与総額またはリセット日が未設定・不正/残量が委任用閾値未満/委任基準を満たすタスクが無い)が示されているか。理由なく全件claude担当になっているものは、委任判定が行われていない疑いとして🟡指摘とする
- [ ] copilot担当タスクが委任基準4条件(自己完結している・受け入れ条件が明確・設計判断を含まない・実機検証が不要)を満たしているか。「自己完結している」は後続タスクから成果物が参照されない(依存の葉である)ことを含む
- [ ] まとめて1回で渡せるcopilot担当タスクが不必要に分割されていないか

## architecture.md(採用しているプロジェクトで、今回のspecが横断的な観点に触れる場合)
- [ ] 必須3つ(コンテキスト図・システム構成図・機能一覧表(機能マップ))があり、先頭の見出しが`## 概要`か。タイトルと最初の`##`の間に本文を置いていないか。要約だけを並べる「サマリ」の見出しを置いていないか
- [ ] 機能一覧表(機能マップ)に「状態」列があり、値が3段階(仕様のみ(未実装) / 実装中 / リリース済み)のいずれかになっているか
- [ ] システム横断の任意見出しが、作成条件に当たるのに無い状態になっていないか([architecture-workflow](../../skills/architecture-workflow/SKILL.md)の見出しテンプレート): 非機能要件のあるspecがあるのに「非機能要件への対応」が無い / APIを提供するのに「API共通仕様」が無い / データを永続化するのに「データ運用」が無い / 認証・認可や個人情報を扱うのに「セキュリティ」に認証・認可・監査ログの記述が無い / ファイル・メッセージで外部連携するのに「外部連携IF一覧」が無い / クラウドを使うのに「インフラ・運用」が無い
- [ ] 横断見出しの内容が、spec単位の記述(design.mdのAPI設計・データベース設計・セキュリティ)を繰り返していないか。どちらが正かが読み取れるか

## system-test.md(作成している場合。[/devflow:test-design](../../skills/test-design/SKILL.md)の成果物)
- [ ] 先頭に**サマリ**章があり、対象範囲(spec名)・シナリオ数・合否判定の要点がつかめるか
- [ ] 試験方針に対象specの一覧と、design.mdのテスト戦略(単体・性質・契約・構造検証・環境スモーク・性能)との役割分担が書かれているか
- [ ] 業務シナリオ試験が複数のspecをまたいでいるか。単一specで閉じるシナリオ(design.mdのテスト戦略と重複するもの)を繰り返していないか
- [ ] 異常系(外部システム停止・タイムアウト・同時実行・途中離脱)のシナリオが含まれているか
- [ ] 非機能試験の各行に、検証方法と合格基準(数値または合意した実施方法)が書かれているか
- [ ] 要件との対応表に、対象specの全`requirements.md`の`[n]`付き見出しと非機能要件が1行ずつ載り、全項目が最低1つ(design.mdテスト戦略またはST-xxx)でカバーされているか。カバーできない項目に理由が書かれているか
- [ ] 合否判定基準に、残った不具合の重要度別の扱い・未実施ケースの扱い・判定者が決まっているか
- [ ] ST採番が業務シナリオ`ST-001`〜・非機能`ST-101`〜で、削除・再利用がないか(廃止は番号を残して明記しているか)
- [ ] 試験環境・テストデータ・合格基準の数値が、会話で確認した内容か(推測で埋めていないか)。決まっていないものが「未決事項」に決定者・期限つきで残っているか

## 最新仕様のみが書かれているか(requirements.md / design.md / architecture.md / system-test.md 共通)
- [ ] 変更の経緯・履歴が混ざっていないか(「〜から〜に変更した」「旧〜」「移設した」「廃止した」「撤去」などの差分ナラティブ)
- [ ] 移設・変更を示すマーカー(「【〜で移設】」など)が残っていないか
- [ ] 内輪のコードネーム・呼称(第三者・後任が読んで意味が分からない語。例:「方向B」)が使われていないか
- [ ] 合意日付などセッション固有の言い回し(例:「2026-08-19合意」)が残っていないか
- [ ] 残すべき経緯・決定理由がADRに分離され、仕様書からはリンクだけになっているか(ADRの置き場所は[architecture-workflow](../../skills/architecture-workflow/SKILL.md))

## 3点セットの整合性
- [ ] requirements↔design↔tasksの間で矛盾(designにだけある処理、requirementsにだけあるルール)がないか
- [ ] 新規spec作成 vs 既存spec更新の判断([/devflow:requirement](../../skills/requirement/SKILL.md)のStep0)が正しいか
- [ ] `architecture.md`を採用しているプロジェクトの場合、機能マップ(spec一覧・依存関係・状態列)と矛盾しないか
- [ ] 各Markdownに埋め込まれたMermaid図が本文・実装と矛盾していないか。**エッジラベルに半角括弧が混入していないか**(描画エラーで図全体が表示されなくなる)
- [ ] 図が可読ルール([architecture-workflow](../../skills/architecture-workflow/SKILL.md)「Mermaidの書き方ルール」)に沿っているか。構成/構造図はノード10個・エッジ12本以内、シーケンス図は参加者4人以内・メッセージ12本以内で、**参加者の並び順はやり取りの多いペアが隣接しライフラインをまたぐ矢印が最小になっているか**。超える図は観点・フェーズ単位で分割されているか

# 指摘の重要度

| 重要度 | 意味 | 扱い |
|---|---|---|
| 🔴 must | 承認できない問題(要件の欠落・矛盾、根拠のないビジネスルール、テンプレート必須項目の欠落) | 修正するまでチャット承認に進まない |
| 🟡 should | 修正が望ましい問題(表現の曖昧さ、`[n]`の振り忘れ、文体の不統一) | 原則今回対応する |
| 🟢 info | 参考情報・質問・提案 | 対応は任意 |

# フィードバックのテンプレート

```markdown
## 仕様レビュー結果: <承認(指摘なし) / 要修正(🔴n件・🟡n件・🟢n件)>

### 対象
(specのローカルミラーパス)

### 参照したチェックリスト
- base (常に)
- company(会社標準。適用した場合のみ記載)
- project(プロジェクト固有。適用した場合のみ記載)

### 良い点
- (必ず1つ以上)

### 指摘事項
| # | 重要度 | 対象 | 指摘内容 | 根拠 |
|---|---|---|---|---|
| 1 | 🔴 must | requirements.md#ビジネスルール | ... | ... |

### 確認をお願いしたい箇所
- (人が読んで判断する必要がある箇所だけを、ファイル名と見出し(または行)で指す。指摘事項のうち対応が人の判断に委ねられるものはここに転記する。無ければ「なし」)

### 判断をお願いしたい事項
- (レビュアーでは決められない事項を質問の形で書く。選択肢がある場合は選択肢と各選択肢の影響を添える。無ければ「なし」)

### AIが確認済みの範囲(通読を省略してよい範囲)
- (このレビューで実際に読んだファイル・見出しと、実行して確かめた検証。承認者が省略の根拠を判断できるよう「何を確認したか」を添える)

### AIでは確認できなかった範囲
- (読めなかったファイル・実行できなかった検証・判断材料の不足で推測に留まった点。「なし」と書く前に、本当に無いかを確かめる)

### 次のステップ
- 🔴/🟡あり → /devflow:resolve で修正し、再レビューを受ける
- 指摘なし(🟢のみ) → ユーザーにチャット上で明示的な承認を求める
```

末尾の4区分(確認をお願いしたい箇所 / 判断をお願いしたい事項 / AIが確認済みの範囲 / AIでは確認できなかった範囲)は、承認者が全文を通読しなくても判断できるようにするためのもので、省略しない。「確認をお願いしたい箇所」は人の判断・合意が要るものに絞り、水増ししない(迷ったら、人が判断すべき内容を見落とさないよう「確認をお願いしたい箇所」側に寄せる)。「AIが確認済み」にできるのは、機械的に確かめられて判断の余地がない範囲だけで、「承認してよい」「確認不要」のような承認の代弁は書かず、確認した事実だけを書く。
