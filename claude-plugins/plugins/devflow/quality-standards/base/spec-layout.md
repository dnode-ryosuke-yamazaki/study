> 読み手: AI

仕様3点セットと architecture.md の見出しごとの読み手(人 / AI)と、要点・畳み・出所の目印の書式の正。
/devflow:requirement・/devflow:design・architecture-workflow はこのファイルを参照し、各SKILL.mdに区分け表を転記しない。

## 概要とステータスのラベル

どのファイルも先頭の見出しは `## 概要` にする。**タイトルと最初の `##` の間に本文を置かない**
(機械検査が「章の外に本文」として検出する)。例外は requirements.md のタイトル直下に置く
ステータス・優先度のラベル1行だけで、引用(`>`)にはしない。

requirements.md:

```markdown
# <タイトル>

ステータス: <仕様確認中(未実装)|実装中|リリース済み> ／ 優先度: <高|中|低>

## 概要

<誰の何を解決するか。1〜3行>

- **<この仕様で作るもの>**: <何が入っているか。何のために要るか>

進め方: <読み手が先に知っておくべき前提。無ければ書かない>
```

ステータスのラベルの値は次の3つで、architecture.md の機能マップの状態列と同じ3段階を指す。
ラベル行は消さずに値だけを書き換える(行が無いと、どの段階なのかが読み取れない)。

| ラベルの値 | 書き換えるタイミング | 書き換える工程 | 機能マップの状態列 |
|---|---|---|---|
| 仕様確認中(未実装) | requirements.md を新規に作った時 | [/devflow:requirement](../../skills/requirement/SKILL.md) | 仕様のみ(未実装) |
| 実装中 | 仕様の承認(チャット承認、または仕様承認PRのマージ)を確認して実装に着手する時(最初の🔴Redのテストを書いた時) | [/devflow:implementation](../../skills/implementation/SKILL.md) | 実装中 |
| リリース済み | 実装PRのマージ後、本番反映の確認が済んだ時 | [/devflow:pr](../../skills/pr/SKILL.md)の完了時案内 | リリース済み |

リリース済みのspecに修正・改修で再度手が入ったら「実装中」に戻し、本番反映の確認が済んだ時点で
「リリース済み」に戻す([/devflow:fix](../../skills/fix/SKILL.md))。機能マップの状態列と食い違わせない。

design.md・architecture.md(ステータスのラベルは持たない):

```markdown
# <タイトル>

## 概要

<design.md は処理の全体像、architecture.md は何をするシステムか。1〜3行>
```

## 読み手宣言行

区分け表に無い見出しを足す場合は、見出し行の直後に読み手を示す引用行を1行置く。
値は `人` か `AI` のどちらかで、他の値は「読み手不明」の違反になる。

```markdown
## 用語

> 読み手: AI
```

## `<summary>` の文言

`<summary>` の文言は「詳細を開く」に固定する。`</summary>` の直後には空行を1行置く
(空行が無いと中のMarkdownが描画されない)。

## 要点と畳みの書式

読み手がAIの見出しは「見出し → 見える要点1〜2行 → `<details>` で畳んだ本文」の順に固定する。
読み手が人の見出しの本文は畳まない。

`###` を持たない見出し:

```markdown
## エラーハンドリング

<要点 1〜2行>

<details><summary>詳細を開く</summary>

(本文)

</details>
```

`###` を持つ見出し(機能要件・ビジネスルール・制約・処理フロー)。畳みの単位は `###` ごとで、
`##` の直下には本文を置かない:

```markdown
## 機能要件

### <機能名>

<機能の1行概要>

<details><summary>詳細を開く</summary>

- [1] … 〔論理〕

</details>
```

図がある場合。図とその直後の説明1行は畳みの外に置く:

````markdown
### <処理名>

<処理の1行概要>

```mermaid
sequenceDiagram
    …
```

<図の説明 1行>

<details><summary>詳細を開く</summary>

- **対象**: …
- **手順**: …

</details>
````

## 出所の目印の書式

承認者が読む行(読み手が人の見出しの箇条書き各行・読み手がAIの見出しの要点行・design.md の
決定事項の表の各行)に、`〔合意〕`(要件ヒアリング・/devflow:consult・承認時の会話で決めたこと)または
`〔提案〕`(会話に無く書き手が補ったこと)のどちらか1つを必ず付ける。迷ったら `〔提案〕`。
ひな形に書いてある目印は置き場所の例で、行ごとにその行の出所で選び直す。
プレビューHTMLでの見せ方(提案の行に下地を敷く・目印をバッジにする)は [deliverable-preview.md](../../deliverable-preview.md) が正。

目印は箇条書きの行末・要点の文末に置き、リスク種別の目印(`〔論理〕` 等)がある行ではその前後
どちらでもよい。[/devflow:autopilot](../../skills/autopilot/SKILL.md) が付ける `【推測】` と並ぶ行でも前後どちらでもよい
(検査は行末の `【…】` を読み飛ばして目印を数える)。ステータスのラベル行・見出し・図・図の説明1行・畳みの中(`[n]` 項目・手順・表)には付けない。

```markdown
- 仕様の承認者としては、… したい 〔合意〕
- [1] … 〔非機能〕 〔提案〕
```

要点行:

```markdown
### <機能名>

<機能の1行概要> 〔提案〕
```

design.md の決定事項の表は6列で、「出所」列の値は `合意` か `提案`。「採らなかった案」が無い行は
「なし」と書く(空欄にしない):

```markdown
| 論点 | 選んだ案 | 採らなかった案 | 理由 | 影響範囲 | 出所 |
|---|---|---|---|---|---|
| … | … | なし | … | … | 合意 |
```
