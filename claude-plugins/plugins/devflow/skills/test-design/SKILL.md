> ワークフロー上の位置: 任意の工程(商用案件向け)。[/devflow:implementation-review](../implementation-review/SKILL.md) → **/devflow:test-design(本Skill)** → [/devflow:spec-review](../spec-review/SKILL.md)(system-test.mdのレビュー)→ 承認 → 試験実施・結果記録 → [/devflow:pr](../pr/SKILL.md)(実装PR)またはリリース判定。全体フロー・モデル対応表は[dev-flow.md](../../dev-flow.md)を参照

# いつ使うか

spec単位の「仕様項目とテストの対応」は既に2段で確認されている([dev-flow.md](../../dev-flow.md)の「仕様とテストの対応付けの仕組み」)。本Skillはその**外側**、1つのspecの中では出てこない確認を成果物として残すためのもので、次のいずれかに当たるときだけ使う。

- 顧客・発注者への受入(検収)の根拠が必要な商用案件
- 複数のspecをまたぐ業務シナリオ(例: 注文 → キャンセル → 履歴確認を一気通貫で通す)がある
- 非機能要件(性能・可用性・運用)に合格基準を定めて実証する必要がある

個人の小規模アプリ・自動化バッチでは使わない(design.mdのテスト戦略・tasks.mdの環境スモークチェックリスト・[マージ後のリリース確認チェックリスト](../../dev-flow.md#マージ後のリリース確認チェックリスト)で足りる)。

# 置き場所と承認

- `architecture.md`と同じ階層(specの置き場所の直下)に`system-test.md`を1冊置く(アプリ単位)。リリース範囲を分けて試験する場合は`system-test-<リリース名>.md`とする。置き場所の解決は[dev-flow.mdの「specの置き場所」](../../dev-flow.md#specの置き場所ローカル専用リポジトリにコミットしない)に従う
- 承認方式はspecと同じ(チャット承認、または仕様承認PR方式のプロジェクトでは[/devflow:pr](../pr/SKILL.md)の仕様承認PR)。承認前に試験を実施しない
- [仕様書は「最新仕様のみ」を書く](../../dev-flow.md#仕様書は最新仕様のみを書く恒久ルール)に従う。試験の実施結果も「結果」列の最新状態だけを残し、履歴は書かない

# 前提条件

- 対象範囲の全specの`requirements.md`/`design.md`が承認済みであること。未承認のspecがあれば先に[/devflow:spec-review](../spec-review/SKILL.md)を済ませる
- `architecture.md`があれば機能マップで対象specを確定する(無ければ対象specの一覧をユーザーと合意する)
- 作成は実装と並行してよいが、試験の実施は実装PRのマージ後(本番相当環境またはステージング)に行う

# system-test.mdの書き方

会話ドリブン原則([/devflow:requirement](../requirement/SKILL.md)参照)に従い、試験環境・テストデータ・合格基準の数値・判定者はユーザーと確認したものだけを書く。推測で埋めず、決まっていない点は「未決事項」に決定者と期限つきで残す。

0. **サマリ(必須)** — `##`見出しでファイル先頭に置く。対象範囲(spec名の列挙)・シナリオ数・非機能試験の数・合否判定の要点を3〜5行で
1. **試験方針** — 目的(要件の充足を業務シナリオで確認する)、対象範囲(対象specの一覧)、design.mdのテスト戦略(単体・性質・契約・構造検証・環境スモーク・性能)との役割分担、対象外
2. **試験環境・前提条件** — 環境(本番相当か)、テストデータ、参加者と役割。決まっていなければユーザーにヒアリングする
3. **業務シナリオ試験** — 利用者の実際の業務の流れに沿ったシナリオを`ST-001`から採番する。**複数のspecをまたぐことが前提**で、単一specで閉じるシナリオはdesign.mdのテスト戦略に既にあるため繰り返さない。異常系(外部システム停止・タイムアウト・同時実行・途中離脱)を必ず含める
   ```markdown
   | ID | シナリオ | 手順概要 | 期待結果 | 対応する仕様項目 | 結果 |
   |---|---|---|---|---|---|
   | ST-001 | 注文してからキャンセルし、履歴で確認する | 1. … 2. … | … | order-creation/requirements.md#注文確定-1、order-cancellation/requirements.md#キャンセル-2 | 未実施 |
   ```
4. **非機能試験** — 対象specの非機能要件ごとに`ST-101`から採番し、検証方法・合格基準(数値)・対応する仕様項目・結果を書く。機械的に検証できないもの(運用訓練・障害復旧手順の確認など)は実施方法をユーザーと合意して書く
5. **要件との対応表** — 対象specの全`requirements.md`について、`[n]`を振った見出し(機能要件・ビジネスルール)と非機能要件を1行ずつ並べ、どこで担保するかを書く。spec内で完結する項目は「design.mdテスト戦略(単体/結合/手動)」、spec横断は該当する`ST-xxx`。**全項目が最低1つでカバーされていること**を確認し、カバーできない項目は理由を明記する
   ```markdown
   | 仕様項目 | 担保する場所 | 備考 |
   |---|---|---|
   | order-creation/requirements.md#注文確定 | design.mdテスト戦略(単体・結合)、ST-001 | |
   | order-creation/requirements.md#非機能要件-1 | ST-101 | 応答時間 |
   ```
6. **合否判定基準** — リリース可否の基準(全STの合格を必須とするか、残った不具合の重要度別の扱い、未実施ケースの扱い)と判定者
7. **未決事項** — 決まっていない事項を決定者・期限つきで
8. **実施結果** — 実施日・実施者・全体の結果(合格/不合格)。個々のケースの結果は3・4の「結果」列に埋める。不合格の不具合は[/devflow:fix](../fix/SKILL.md)で修正し、再試験後に結果を書き換える(履歴は残さない。必要なら不具合のJIRAキーだけを備考に書く)

# ID採番

- `ST-001`〜(業務シナリオ)、`ST-101`〜(非機能)。spec内の`[n]`とは別体系で、spec横断の成果物だけが使う
- 番号は削除・再利用しない。廃止したケースは番号を残して「廃止」と明記する(対応表・他文書からの参照先を保つため)

# 完了時の次ステップ案内

- system-test.mdを書き終えたら[/devflow:spec-review](../spec-review/SKILL.md)でレビューを受ける(チェックリストは[quality-standards/base/spec-review.md](../../quality-standards/base/spec-review.md)の「system-test.md」節)。承認後に試験を実施する
- 試験を実施したら結果を記録し、全体の合否をユーザーに報告する。合格なら[dev-flow.md](../../dev-flow.md)の「マージ後のリリース確認チェックリスト」へ、不合格なら[/devflow:fix](../fix/SKILL.md)へ進むことを案内する
- セッション終了時の出力形式は `~/.claude/session-handoff.md` に従う
