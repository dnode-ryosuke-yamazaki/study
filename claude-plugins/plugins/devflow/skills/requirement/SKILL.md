# specの置き場所

仕様3点セット(requirements.md/design.md/tasks.md)の置き場所(既定のローカルミラーパス・例外リポジトリの扱い)は[dev-flow.mdの「specの置き場所」](../../dev-flow.md#specの置き場所ローカル専用リポジトリにコミットしない)を参照する。以降このSkill群で「specのパス」「対象spec」と書く場合は、そこで定義されたパスを指す。

# 開始時: JIRAチケットの確認

Step0より前に、`${CLAUDE_PLUGIN_ROOT}/jira-ticket-check.md`(グローバル方針)を読み、その手順に従って対応するJIRAチケットの有無を確認する。プロジェクトが独自の`requirement/SKILL.md`を持つ場合は、そちらでも同様にこの節を維持する。

# Step0 入口の判断: 新規spec作成 vs 既存spec更新

機能に着手する前に、新しい`specs/<機能名>/`フォルダを作るか、既存specを更新するかをまず判断する。ここを誤ると、既存機能の修正が別機能のspecとして切り出され、同じビジネスルールが複数のrequirements.mdに分散してしまう。判断基準は[dev-flow.mdの「新規spec vs 既存specの判断基準」](../../dev-flow.md#新規spec-vs-既存specの判断基準)を参照する。既存specを更新すべきサインに該当する場合は新規フォルダを作らず[/devflow:fix](../fix/SKILL.md)のフローへ切り替える。

新規specフォルダを作る前に、他のworktree・他のセッションで同じ/重複する機能が既に進行中でないかを確認する(手順は[parallel-work](../parallel-work/SKILL.md)の「他セッションとの重複を避ける」を参照。ローカルミラーディレクトリを対象パスとして確認する。worktreeを使っていない・並行作業の予定がない場合でも、他セッションの存在に心当たりがなければこの確認は省略してよい)。

# 複数のユーザーストーリーを分割する

要件を1つの巨大なspecフォルダにまとめない。まず利用者視点のユーザーストーリー(「〜としては、〜したい」)を洗い出し、**1ストーリー=1specフォルダ**を原則に`specs/<機能名>/`を縦に分割して作る。

- 洗い出したストーリーの数だけ`specs/<ストーリーを表す機能名>/`を並べて作る(例: 注文管理なら`order-creation`(注文作成)、`order-cancellation`(注文キャンセル)、`order-history`(注文履歴)のように分ける)
- 複数のストーリーの結果を1つのレスポンス・画面にまとめる統合ロジックが必要な場合は、新たに統合専用specを作らず、その統合先(最終的に呼び出し元が使うエンドポイント・画面)を担当するstory specに書く。他のstory specの機能要件には「この結果は`<まとめ先の機能名>`で使われる」と一言添えて依存関係を明示する
- 複数アプリ・モジュールを持つプロジェクトの新規モジュール立ち上げ時は`architecture.md`も最初から作成する(作成基準・書き方は[architecture-workflow](../architecture-workflow/SKILL.md)を参照)。機能マップの状態列は全spec「仕様のみ(未実装)」で初期化する。リポジトリのルートREADME等にアプリ/モジュール一覧の表がある場合は、そこにも1行追加する
- 各specが育ってきて「既存機能の修正・拡張」に該当する変更が発生したら、以降は上記Step0の判断に従う

# 要件ヒアリング

requirements.mdを書き始める前に、以下の5項目が**すべて**確認できているかを確認し、足りないものはユーザーに質問して埋める。

- 誰・何のための機能か(ユーザーストーリーの主語、または呼び出し元システム)
- 何ができればよいか(入出力・レスポンス・画面の完成イメージ)
- ビジネスルールと根拠(数値・条件は法令・公式資料・既存の意思決定などの出典とセットで確認する)
- 今回やらないこと(スコープ外)
- データ量・利用頻度の想定(想定件数・同時アクセス数など、非機能要件やテスト戦略の判断材料になる規模感。「該当なし」と即答できる小規模な機能ならそれでよく、深掘りしない)

**聞き方**: 一度に全部聞かず、**1回の質問は1〜3問まで**にして重要な順に聞く(選択肢を示せる質問はAskUserQuestionで選択肢と影響を並べる)。回答を受け取ったら、残りの項目がまだ埋まっていないか都度確認し、埋まっていなければ続けて質問する(往復して構わない)。ユーザーの最初のメッセージだけで書き始めず、5項目が出揃うまでrequirements.mdの作成に進まない。

**新しい画面を追加する場合**: 「何ができればよいか」の確認で新しい画面・表示の追加(新しい画面、または既存の画面に一覧・入力欄・状態の表示などのまとまりを足すこと)が分かったら、文章だけで質問を返さない。既存の画面の文言の変更や項目の並べ替えのように、新しい表示を足さない変更は対象外。画面イメージは次の2段階ですり合わせ、ユーザーがモックに合意してからrequirements.mdを書く。画面イメージのすり合わせは文言だけのやり取りよりユーザーとの認識のズレを防げる。`/devflow:consult`で機能全体を壁打ち済みで、その中で画面イメージに触れていた場合でも、この2段階は省略しない(会話ベースの合意はワイヤーフレームの選定とモックでの確認の代わりにならない)。

1. **方向性を選ぶ(ASCIIの3案)**: ラフなワイヤーフレーム(テキスト/ASCIIで十分、Figma等の外部ツールは使わない)を、レイアウトの方向性が異なる**3パターン**のレイアウト案として作成し、AskUserQuestionの`preview`機能で並べて提示してから選んでもらう
2. **触れるモックで詰める(HTML)**: 選ばれた1案を、ユーザーが実際に操作できるHTMLの画面モックにして、Artifactで発行したURLを渡す。触ってもらって出た指摘でモックを直し、同じURLへ再発行する往復を合意まで続ける(書き方は下記「画面モックの作り方」)

## 画面モックの作り方

- **置き場所と正本**: specフォルダに`mock.html`として1ファイルで置く。画面が複数あるときも1ファイルにまとめ、画面の切り替えもモックの中で操作できるようにする。画面の配置・見た目・状態の切り替わりの正本はこのファイルで、Artifactは確認用のビュー。発行・再発行でURLを保つ方法は[deliverable-preview.md](../../deliverable-preview.md)に従う。Artifactを発行できないときは、`mock.html`を外部ブラウザで開く`open`のコマンドブロック(絶対パス入り)を渡して触ってもらう
- **再現する範囲**: ボタン・入力欄が実際に反応し、その画面が取る状態(初期表示・入力中・処理中・成功・失敗・一覧が空のときなど)が操作で切り替わるところまで作る。通信・保存・音声などの実処理は行わず、画面の動きだけを再現する
- **外から起きる出来事**: 外部からの受信・処理の失敗・設定が見つからない場合など、画面の操作では起こせない状態は、ページ下部の「モック用の操作」欄のボタンから起こせるようにし、その欄が実際の画面には無いことを欄の中に書く
- **冒頭の注記**: ページの先頭に、画面モックであること・どの機能(specフォルダ名)の画面か・実処理は行わないことを1行で書く
- **データ**: 表示するデータはダミーにする。実データ・顧客名などの社内情報・認証情報を入れない
- **書き方**: 書く前に`artifact-design` Skillを読む。外部のスクリプト・画像に頼らず1ファイルで完結させ、`<html>`・`<head>`・`<body>`を書かず`<title>`と`<style>`から書き始める(Artifactの発行時に外枠が付き、ローカルの外部ブラウザで直接開いてもそのまま表示される)
- **要件の抜けを requirements.md に戻す**: モックを作る途中や触ってもらう中で、ヒアリングで確認していない振る舞い(失敗したときの表示・空のときの表示・上限を超えたときの扱いなど)が要ると分かったら、モックにだけ入れて済ませない。モックのURLを渡すときにその一覧を添え、requirements.md を書くときに該当する見出し(機能要件・UI/UX要件・スコープ外)へ入れる。目印は`〔提案〕`にする(付ける場所は下記「出所の目印」に従い、畳みの中の`[n]`項目として足すときはその見出しの要点行を`〔提案〕`にする)。ユーザーが会話で合意した行だけを`〔合意〕`に改める。requirements.md を書いた後の工程([/devflow:design](../design/SKILL.md)・[/devflow:fix](../fix/SKILL.md))でモックを直して抜けが見つかったときも、同じやり方で requirements.md に書き足す
- **requirements.md への書き方**: 「UI/UX要件」には、合意した要点(並びの順・主な操作・状態の切り替わりの要点)と、モックへの参照(`mock.html`への相対リンクとArtifactのURL)だけを書く。モックの細部やASCIIのワイヤーフレームを書き写さない(2か所に書くとずれる)
- **v0を使う場合(任意)**: 見た目を詰めるためにv0(v0.app)を使ってもよいが、必須の手段にしない。組織ポリシーでMCPサーバーとしては追加できないため(`~/.claude/sandbox-limitations.md`)、使うならユーザーが手元のブラウザで操作する。Freeプランのため、社内情報(実データ・社内の名称・顧客名・仕様書の本文)は入れない。v0の出力を取り込んだ場合も、正本はspecフォルダの`mock.html`とする

# 仕様書は「最新仕様のみ」を書く(恒久ルール)

requirements.mdは[dev-flow.mdの「仕様書は『最新仕様のみ』を書く」](../../dev-flow.md#仕様書は最新仕様のみを書く恒久ルール)に従って書く(差分ナラティブを書かず、常に今の正しい仕様だけを現在形で書く)。

# requirements.mdの書き方

「何を作るか(WHAT)」「なぜその仕様にしたか(根拠)」を言語化する。数式・変数名は使わず日本語の言葉で書く(正確な計算式・スキーマはコードとテストに委ねる)。技術的な実装方法(HOW)はここでは書かない。

見出しは固定セットで、どの見出しを人が読みどれをAIが読むかは[読み手の区分け表](../../quality-standards/base/spec-layout.md#読み手の区分け)が正(このSKILL.mdに転記しない)。読み手がAIの見出しは「見出し → 見える要点1〜2行 → `<details>` で畳んだ本文」の順に固定し、読み手が人の見出しは畳まない。

- **必須6**: 概要 / ユーザーストーリー / ユースケース図 / 機能要件 / ビジネスルール・制約 / スコープ外
- **任意3**: 非機能要件 / 依存関係 / UI/UX要件。該当しない場合は見出しごと置かず、省略の理由も書かない
- **廃止**: 要約だけを並べる「サマリ」の見出しは置かない。要約は「概要」と各見出しの要点行が担う(機械検査が廃止見出しとして検出する)

## どの章にも属さない記載を置かない

**タイトルと最初の`##`の間に本文を置かない。**どの章にも属さない文は、見出しから探せず、読み手にとって位置づけの分からない記載になる。ここに置きたくなった説明は`## 概要`に書く。

例外は**ステータスと優先度のラベル1行**だけ。requirements.md のタイトル直下に、引用(`>`)にせず短く置く。

```markdown
# <タイトル>

ステータス: 仕様確認中(未実装) ／ 優先度: <高|中|低>
```

優先度の根拠のような説明はこのラベルに書かず`## 概要`に回す(括弧の中に長い文を押し込むと、ラベルとして読めなくなる)。ラベルの3つの値(仕様確認中(未実装) / 実装中 / リリース済み)と書き換えるタイミングの正は[区分け表のファイル](../../quality-standards/base/spec-layout.md)。ラベルを置くのは requirements.md だけで、design.md・architecture.md は持たない。

## 承認状態のフロントマター

タイトルより前、ファイルの1行目から**承認状態のフロントマター**を置く。新規作成では `status: draft`・`version: "0.1"` にする(`approved_date` は置かない)。ラベル行が実装の進み具合を表すのに対し、フロントマターは承認の有無を表す別物で、両方を持つ。

**既存specを直すときは、先にフロントマターを見る。** `status: approved` のrequirements.mdに手を入れる場合は、その改訂の最初の変更で `draft` に戻し、`approved_date` を消し、`version` の小数点以下を1つ上げる(`"1.0"` → `"1.1"`)。誤字の修正だけでも同じ。再承認までに重ねて直しても上げ直さない。フロントマターが無い既存specは、先に移行手順で付けてから直す。値の遷移・移行手順の正は[dev-flow.mdの「承認状態のフロントマター」](../../dev-flow.md#承認状態のフロントマター)、書式の正は[区分け表のファイル](../../quality-standards/base/spec-layout.md#承認状態のフロントマター)。

## 「概要」に書くこと

どのファイルも先頭の見出しは`## 概要`にする。ここは**その仕様を読む理由が分かる場所**で、次の3つを書く。

- **誰の何を解決するか。**1〜3行
- **この仕様で作るものと、それが何のために要るか。**作るものを名前だけ並べない。「読み手の区分け表」なら「どの見出しを人が読みAIが読むかを1か所で決める表。書き手と検査スクリプトが同じ判断をするために要る」まで書く([読み手に伝わる書き方](#読み手に伝わる書き方))
- **進め方。**分割してよいか、1回で入れる必要があるかなど、読み手が先に知っておくべき前提。無ければ書かない

design.md の「概要」は処理の全体像、architecture.md の「概要」は何をするシステムかを書く。

## 文書骨格

次の骨格をそのまま写し、`<>` の中身だけを埋める。該当しない任意見出しは見出しごと削る。必須見出しは削らない。

````markdown
---
status: draft
version: "0.1"
---

# <タイトル>

ステータス: 仕様確認中(未実装) ／ 優先度: <高|中|低>

## 概要

<誰の何を解決するか。1〜3行> 〔合意〕

- **<作るもの1>**: <何が入っているか。何のために要るか> 〔合意〕
- **<作るもの2>**: <何が入っているか。何のために要るか> 〔提案〕

進め方: <読み手が先に知っておくべき前提。無ければ行ごと落とす> 〔合意〕

## ユーザーストーリー

- <利用者>としては、<したいこと>したい 〔合意〕

## ユースケース図

```mermaid
flowchart LR
    actor["<アクター>"] --> uc(["<できること>"])
```

線はアクターとユースケースの関わりを表し、処理の順序ではない。正となる文章は機能要件・ビジネスルール・制約を参照。

## 機能要件

### <機能名>

<機能の1行概要> 〔合意〕

<details><summary>詳細を開く</summary>

- [1] <テストと対応づける項目> 〔論理〕

</details>

## ビジネスルール・制約

### <ルール名>

<数値・閾値を持つルールと、根拠が書けているか> 〔提案〕

<details><summary>詳細を開く</summary>

- [1] <ルール>。根拠: <法令・公式資料・既存の意思決定> 〔論理〕

</details>

## 非機能要件

- [1] <数値で書いた要件> 〔非機能〕 〔提案〕

## 依存関係

実現性: <外部依存ごとに できる / できない / 未確定。未確定は名指し> 〔合意〕

<details><summary>詳細を開く</summary>

| 依存 | 結論 | 確認内容 |
|---|---|---|
| <依存> | できる | <実機で確認した内容> |

</details>

## UI/UX要件

<画面モックがある場合: 「画面モック: [mock.html](mock.html)(プレビュー: ArtifactのURL)。配置・見た目・状態の切り替わりはモックが正 〔合意〕」の1行。無い場合はこの行を削る>

- <画面・操作の要件。モックがある場合は合意した要点(並びの順・主な操作・状態の切り替わり)だけ> 〔提案〕

## スコープ外

- <やらないこと> 〔合意〕
````

書式の細かい決まりは[区分け表のファイル](../../quality-standards/base/spec-layout.md)が正。要点は`###`を持つ見出しでは`###`ごとに置き、`##`の直下には本文を置かない。図(Mermaid)とその直後の説明1行は畳みの外に出す。`<summary>`の文言は「詳細を開く」に固定し、`</summary>`の直後に空行を1行置く(空行が無いと中のMarkdownが描画されない)。

## 固定セットに無い見出しを足すとき

区分け表に無い見出しを足す場合は、見出しの直後に読み手を示す引用行を1行置く。宣言が無い見出しは機械検査が「読み手不明」として違反にする。

```markdown
## 用語

> 読み手: AI
```

## 出所の目印(〔合意〕/〔提案〕)

承認者は文書を開いて見えている行だけを読む。そのうち「自分が会話で決めたこと」は読み飛ばせるように、**見えている行それぞれに出所の目印を1つ付ける**。

- `〔合意〕` — 要件ヒアリング・[/devflow:consult](../consult/SKILL.md)・承認時の会話で決めたこと
- `〔提案〕` — 会話に無く、書き手が補ったこと
- **迷ったら`〔提案〕`**。〔提案〕に寄せる誤りは承認者の読む量が増えるだけだが、〔合意〕に寄せる誤りは読まれるべき行が読み飛ばされる
- **骨格に書いてある目印は置き場所の例。行ごとに選び直す。**`〔合意〕`にしてよいのは、ユーザーが会話で言ったことをそのまま書いた行だけ。こちらが言い換えた要求・補った根拠・思いついたスコープ外の項目・整理して書いた進め方は、会話に出ていない内容なので`〔提案〕`
- **見えている行が全部`〔合意〕`のrequirements.mdは出さない。**要件ヒアリングの回答だけで、書き手が1行も補わずに仕様書が書き上がることはほとんど無い。依頼文が確認項目を全部埋めていて「この内容だけで書く」よう求められていても、言い換えた行・補った根拠・整理し直したスコープ外の行・ヒアリングに無い語(認証の方式など)を含む行は`〔提案〕`になる。「言い換えにとどまるので〔合意〕」という扱いはしない(全部〔合意〕になった理由を補足に書いて済ませるのではなく、目印を付け直す)
- 既存の承認済みspecを直すときは、承認済みの内容の行を`〔合意〕`、その改修で追加・変更した行を`〔提案〕`にする

付ける場所は、読み手が人の見出しの箇条書き各行の行末と、読み手がAIの見出しの要点の文末。[/devflow:autopilot](../autopilot/SKILL.md)の`【推測】`と並ぶ行では前後どちらでもよい。ステータスのラベル行・見出し・図・図の説明1行・畳みの中(`[n]`項目・手順・表)には付けない。リスク種別の目印がある行では前後どちらでもよい。

```markdown
- 仕様の承認者としては、… したい 〔合意〕
- [1] … 〔非機能〕 〔提案〕
```

承認者が「合意した覚えのない〔合意〕」を見つけた場合は🔴の指摘になる(目印の正しさは機械では検査できない)。

## 読み手に伝わる書き方

承認者は仕様書を通しで読まず、見えている行だけを読む。**その行だけで意味が取れないなら、読み手は前後を探しに行くか、読み飛ばす。**

### この仕様で作るものは、目的と中身を初出で書く

specの中で新しく作るもの(表・設定ファイル・スクリプト・生成物)は、**名前が初めて出てくる行で「誰が何のために使うか」と「何が入っているか」が読み取れるように書く**。名前を出すだけでは、読み手は「なぜこれを作るのか」が分からないまま読み進めることになる。

名前に何の表か・何の設定かを入れる(「区分け表」ではなく「読み手の区分け表」)のは最低限で、**それだけでは足りない**。目的は次のどちらかに書く。

- **それを使う機能要件の要点行**: 「…割り当ては1枚の表にまとめ、書き手も検査もそれを見る」
- **その成果物を定義しているビジネスルールの要点行**: 「読み手の区分け表は、ファイルと見出しごとに読む相手と本文の見せ方を決めた1枚の表」

ユーザーストーリーに「〜のために〜したい」の形で書いてあれば、その成果物がどこへ向かうものかは読み取れる。成果物の名前を出すときは、そのストーリーとつながる言い方にする。

### 主語と対象を省かない

要点行・図の説明・タスク名は、**何が(誰が)・何に対して**するのかを省かない。短く書くことと主語を落とすことは別で、主語が無いと読み手は何の話か分からないまま本文を開くことになる。

- ❌ 「読むだけで書かず、出すのは見出し名と件数だけ」 → ⭕ 「**検査スクリプトは**Markdownを**読むだけで書き込まず**、出すのは見出し名と件数だけ」
- ❌ 「どの見出しを誰が読むかの表を1ファイルにまとめる」 → ⭕ 「**requirements.md・design.md・architecture.md の**見出しごとの読み手を1つの表にまとめる」
- ❌ 「表の『理由』は1〜2行に収める」 → ⭕ 「**決定事項の表の**『理由』列は1〜2行に収める」

箇条書きが長くなって折り返すときは、2行目以降を**字下げする**(字下げしないと機械検査が別の項目として数え、行末に付けた出所の目印を1行目が持っていないと判定する)。

ファイルの話なら**どのファイルか**を名前で書く。処理の話なら**何が動くのか**を書く。「上の表」「この仕様」のような指示語は、指す先が同じ画面に見えているときだけ使う。

### 用語の説明を前段に並べない

「用語集」「前提知識」を文書の頭に作ると、本題に入るまでの障害物になって読む量が増える。説明が要る語は、**その語を使う見出しの中で一度だけ短く補う**。

### 見えている行はその行だけで意味が取れる文にする

内輪の略称、「数値なし・根拠あり」のような定型の圧縮、意味を添えない絵文字は、そのままでは読めないので展開して書く。

### 長くなる構造は図に置き換えてよい

言葉で説明すると長くなる構造(誰が何を読むか・処理の流れ・画面や状態の移り変わり)は、**図を1枚置いて説明を短くしてよい**。図は折りたたみの外に置き、直後に1行だけ説明を添える。Mermaidの中身は承認者が読む文字数に数えないので、図で済ませたほうが結果的に読む量は減る。

## 既存specの扱い

既存のspecを一括で新形式に書き換えない。次にそのspecを更新する工程([/devflow:fix](../fix/SKILL.md)・[/devflow:design](../design/SKILL.md)・/devflow:requirement)の中で、その変更と同じコミットで新形式に直す。

直すときは、サマリの廃止と「概要」への集約・要点行の追加・目印の付与・畳み・決定事項の表の追加・appendix.mdへの付録分離をまとめて行い、**部分適用の状態(畳みだけ新形式、等)で残さない**。requirements.md と design.md の片方だけを直すこともしない。

## 分量(数値ルールが6件以上なら分割を提案する)

「ビジネスルール・制約」の各`###`の要点行に挙がる、数値・閾値を持つルールの合計が**5件を超えたら**、要件定義の完了報告でspecの分割を提案する(人が一目で追える上限に揃える)。分割するかどうかはユーザーが決める。

承認者が読む量(検査スクリプトが出す「人が読む文字数」)が上限を超えたときは、**要点行を削るのではなく、畳みの中へ移せるものを探す**。決定事項の表なら判断に効かない行を折りたたみへ、要点行なら1行に収まるまで言い換える。それでも収まらなければ、specを分けることを提案する。


## 会話ドリブン原則(推測で埋めない)

requirements.mdに書く方針は、「概要」・要点行・任意見出し(非機能要件・UI/UX要件など)も含め、**要件ヒアリングまたは[/devflow:consult](../consult/SKILL.md)の会話の中で確認したもの・こちらから提案して合意したものだけを書く**。会話に出ていない方針を推測で埋めない。判断に迷う点が残ったら、書き切る前にユーザーに確認するか、少なくとも提案の形で認識合わせをしてから記載する。つまりrequirements.mdは「会話で合意したことがドキュメントになっているだけ」の状態を目指す。

## ユースケース図の書き方(Mermaid)

- 図はMermaidコードブロックとして「ユースケース図」見出しに直接埋め込む(専用ファイル・画像は作らない)。アクター(利用者・呼び出し元システム・定期実行トリガー)とユースケースの関係を描く(`flowchart LR`でアクターからユースケースを線でつなぐ形で十分。厳密なUML記法にこだわらない)
- **図は文章を置き換えない。** ユーザーストーリー・機能要件が正、図は俯瞰用の補助。`[n]`採番・テストとの対応付けの対象は従来どおり文章側
- ノード名・ラベルは業務的な言葉にする/1行1エッジ/図の直後に正となる文章へのリンクを置く/**エッジラベルに半角括弧を書かない**([architecture-workflow](../architecture-workflow/SKILL.md)の「Mermaidの書き方ルール」に従う)

## [n]採番ルール

機能要件・ビジネスルール・制約など、個別にテストを対応させたい箇条書きには見出し内で連番の`[n]`を振る(見出しが変わればまた`[1]`から振り直してよい、グローバルな採番ではない)。

```markdown
### ノート削除API
- [1] 対象: 自分が作成したノートのみ
- [2] 挙動: 対象ノートが存在しない場合は404を返す
- [3] 挙動: 削除に成功した場合は204を返す
```

概要・ユーザーストーリー・スコープ外など、そもそもテスト対象にならない見出しには`[n]`を振らなくてよい(見出し単位でスキップ登録の対象になる)。

箇条書きは「〜の場合、〜になること」という文体に揃えておくと、そのままテストの`it()`に転記しやすい。非機能要件(所要時間・呼び出し回数・到達時間など)は「速いこと」ではなく「〜件を〜秒以内」「〜回以下」のように数値で書く(数値がないとテストで判定できない)。

## リスク種別の付与

`[n]`を振った各項目には、設計のテスト戦略で使うリスク種別を1つ添える(論理 / 境界 / 生成物 / 環境 / 並行 / 非機能。定義は[テスト方針](../../test-policy.md)「リスク種別」)。書き方は箇条書きの末尾に`〔境界〕`のように付ける。迷ったら「その項目が壊れたとき、原因は自分のコードの中にあるか、外(外部サービス・実行環境・別の処理系)にあるか」で分ける。

```markdown
### 候補の提示
- [1] 探索の応答に含まれる枠を日本時間に変換して表示すること 〔境界〕
- [2] 候補が0件の場合、代替案の提示へ分岐すること 〔論理〕
- [3] 選択画面のHTMLを生成し、ボタン操作で選択結果が書き出されること 〔生成物〕
```

# 出す前に、承認者と同じものを読み返す

仕様書を書いた本人は自分の文脈で読めてしまうため、**主語の抜け・目的の書かれていない成果物・意味の取れない略称は、書き手には見えない。**出す前に必ず、承認者が実際に目にする行だけを機械に抜き出させて読み返す。

```
python3 ${CLAUDE_PLUGIN_ROOT}/lib/spec_layout_check/scripts/check_spec_layout.py --visible <specフォルダの絶対パス>
```

畳みの中を除いた「見えている行」だけが順に出る。これを読んで次を確かめる。

- **その行だけで意味が取れるか。**主語(何が・誰が)と対象(何を・どのファイルを)が省かれていないか
- **この仕様で作るものについて、何のために作り何が入っているかが書かれているか。**名前だけ出て目的が無いものは無いか
- **どの章にも属さない記載が無いか**(`章の外に本文` の違反として出る)
- **目印が全部`〔合意〕`になっていないか。**こちらが補った行を`〔合意〕`にすると、承認者はそれを読み飛ばす
- **タスク名だけで何をするか分かるか**

**書いているspecで終了コード2(旧形式)が返ったら、それは旧形式ではなく書きかけ。** 畳みも出所の目印もまだ1つも無い状態は、この仕様より前に書かれた既存specと文字面が同じなので機械では見分けられず、`--visible` も1行も出ない。骨格の `<details>` と `〔合意〕`/`〔提案〕` を入れてから回し直す。種別が `フロントマター無し` の行なら、骨格の先頭にあるフロントマター(`status: draft`・`version: "0.1"`)の入れ忘れなので、入れてから回し直す。

**この出力を、完了報告にそのまま貼る。**承認者がspecのファイルを開かなくても、読む量の全部をその場で確認して指摘できる状態にするため。自分で読み返さずに「できました」と報告すると、指摘を受けてから直す往復がそのぶん増える。

# 完了時の次ステップ案内

requirements.mdをユーザーに提示し、[/devflow:design](../design/SKILL.md)(設計・タスク分解)へ進むことを案内する。この時点のフロントマターは `status: draft` のままにする(`in-review`・`approved` にするのは3点セットがそろった後の[/devflow:spec-review](../spec-review/SKILL.md))。仕様が承認されるまでコード(テストを含む)は書き始めない。

requirements.mdを書き終えた時点で、compactや新しいセッションへの切り替えを行っても支障はない。セッション終了時の出力形式は `~/.claude/session-handoff.md` に、プロンプト例は[dev-flow.md](../../dev-flow.md)の「次セッションへの引き継ぎプロンプト例」に従う。
