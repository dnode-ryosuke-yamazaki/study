> ワークフロー上の位置: どのプロジェクトでも使える知識Skill。並行作業を始めるとき・終えるときに参照する(単独のワークフロー工程ではない)

# いつ使うか

**1つの作業ディレクトリで`git checkout`によるブランチ切り替えを往復しない。** 2つ以上の作業を並行して進めたくなったら、作業ごとにgit worktreeで作業ディレクトリ自体を分ける。

**このルールを強制する仕掛けは、現在動いていない。** hook(`~/.claude/hooks/enforce-worktree.sh`)がブランチ切り替えをブロックする作りになっているが、組織の管理設定でユーザー定義hookが実行されないため空振りしている(`~/.claude/sandbox-limitations.md`)。**運用ルールとして各自が守る**必要がある。

hookが動いていたとしても防げない範囲があることにも注意する。このhookは`git checkout`/`git switch`のうち、**デフォルトブランチへの切り替え・デフォルトブランチからの新規ブランチ作成・`git checkout -- <file>`によるファイル復元を正常な手順として許可する**。したがって、他セッションがデフォルトブランチへ戻る操作は許可対象であり、その巻き添えで未コミットの変更が消える事故は止められない(下記「注意事項」)。

典型的なきっかけ:
- 1つの作業のレビュー・承認待ちの間に、別の作業を始めたい
- 作業の途中で、緊急のバグ修正が割り込んだ
- **工程Skillを始めようとしたら、メインの作業ディレクトリが別作業のブランチ上・未コミット変更ありで埋まっていた**(受け身のきっかけ。埋まっている作業には触れず、mainベースのworktreeを作って新しい作業をそちらに隔離してから進める)

1つの作業を最初から最後まで順番に進めるだけなら、worktreeは不要(通常どおりメインの作業ディレクトリでfeatureブランチを切る)。

# 並行してよい作業の条件

worktreeで解決できるのはブランチ切り替えの混乱だけで、**同じファイルを両方で変更すればマージ時にコンフリクトする**。並行を始める前に以下を確認する:

- 触るファイルが重ならないこと。モジュール・ディレクトリが完全に分かれているなら安全。同じモジュール内の別機能は、共有するファイル・共通コードを両方が変更しないか先に確認する
- 共通部分(共通のインフラ定義・共通ライブラリ・設定ファイル)を変更する作業は、他の作業と並行しない
- 実装フェーズ(コード変更)を2本同時に走らせるより、「片方はレビュー・承認待ち・もう片方は実装フェーズ」とフェーズをずらすほうが安全

# 他セッションとの重複を避ける

worktreeは同じ`.git`(ブランチ・コミット)を共有しているため、**あるworktreeでのコミットは、pushやfetchなしで他のworktreeから`git log`等を通じて即座に見える**。一方、コミットする前の作業中の変更はファイルとしてしか存在せず、他のworktreeのgit操作(`git log`等)では見えない。この「コミットするまで見えない」時間差が、片方のセッションが作業を進めているのに、もう片方が同じ対象をゼロから始めてしまうといった重複を生む。

新しい作業に着手する前に、以下を確認する:

- **`git worktree list`で他に動いているworktreeを確認し、そのディレクトリを直接`ls`・`cat`で覗く。** worktreeは単なる別ディレクトリなので、コミットされていない作業中のファイルもこの方法なら見える(git操作を介さないため、コミットの遅延に影響されない)
- **`git log --all --oneline -- <対象パス>`で、他のブランチ(未マージ含む)が同じ対象を触っていないか確認する。** ローカルの参照なのでpush/fetchなしで確認できる
- 上記で判断がつかない、あるいは「これから着手する予定」でまだファイルが存在しない段階の重複が心配な場合は、**ユーザーに「他に並行して進めている作業はありますか」と確認する。** 全セッションの状況を把握しているのはユーザーだけであり、git・ファイルの状態だけでは検出できない重複はここでしか防げない
- 重複が疑わしい対象に気づいたら、新規着手を保留し、状況をユーザーに報告してから進め方を決める

自分の作業も、早めに区切ってコミットしておくと、他セッションが上記の確認をした際に見つけてもらいやすくなる(逆に、長時間コミットせずに作業を溜め込むと、他セッションからの重複検出が効かなくなる)。

プロジェクトが仕様ドキュメント(specs/等)を専用の場所に置く規約を持っている場合は、その置き場所を対象パスとして重複チェックする。プロジェクト固有の規約はそのプロジェクトの`.claude/skills/parallel-work/SKILL.md`に追記する。

# 進め方

## 1. worktreeを作る

worktreeは**すべて`~/worktrees/`の下**に、`<リポジトリ名>-<機能名>`という名前で作る(ブランチ名の`feature/<機能名>`と揃える)。リポジトリの隣(`../<リポジトリ名>-<機能名>`)には作らない。サンドボックスのBash書き込み許可は`~/.claude/settings.json`の`permissions.additionalDirectories`で決まり、`~/worktrees`はそこに登録されている一方、`~/repo/`直下やホーム直下は登録されていないため、隣に作るとworktree内のファイルを一切書けない(`~/.claude/sandbox-limitations.md`「書き込みの可否はセッションによって変わる」):

```bash
git worktree add ~/worktrees/<リポジトリ名>-<機能名> -b feature/<機能名>
```

`~/worktrees`が無い・書けないときは、`mkdir -p ~/worktrees`と`additionalDirectories`への登録をユーザーに依頼する(ホーム直下はBashから作れない)。

## 2. 作業環境を整える

Git管理外のファイルはworktreeに引き継がれないため、新しいworktreeごとに用意する:

```bash
cd ~/worktrees/<リポジトリ名>-<機能名>
# 環境変数ファイル・設定ファイルなど、Git管理外の設定ファイルを元の作業ディレクトリからコピーする
# 依存関係のインストールは package.json 等がある階層で行う
```

## 3. セッションとworktreeを1対1にする

worktreeごとにClaude Codeのセッション(VSCodeウィンドウ)を1つ開き、そのセッションでは他のworktree・他のブランチを触らない。「1 worktree = 1ブランチ = 1セッション」を守ることが、切り替え混乱を防ぐ核になる。

## 4. 隔離した作業の確認・レビューはコミット/PR経由で行う

worktree内の成果物は、メインの作業ディレクトリを開いている手元のIDEには表示されない(別ディレクトリのため)。隔離した作業の内容確認・レビューは、手元IDEのファイルツリーではなくコミット/PR(GitHubのdiff)経由で行うようユーザーに案内する(worktreeで進めた仕様書をユーザーが手元IDEで見つけられない、という取り違えが起きやすい)。

## 5. マージ後に取り込む・掃除する

- 片方の変更がmainにマージされたら、続行中のworktreeでmainの変更を取り込む。`git fetch origin`はリモートへの通信を要しサンドボックスから実行できないことが多いため(`~/.claude/sandbox-limitations.md`参照)、ユーザーに実行を依頼する。取得後の`git rebase origin/main`はローカル操作なのでこちらで行ってよい
- 作業がすべて終わったworktreeは削除する:

```bash
git worktree remove ~/worktrees/<リポジトリ名>-<機能名>
```

- **Copilotへの委任worktreeは使い捨てにする。** agent-routingの担当マーク方式でcopilot担当タスクを委任するとき、[/devflow:implementation](../implementation/SKILL.md)はfeatureブランチの現在位置から委任用ブランチを切り、リポジトリの外に専用のworktreeを作る。命名は次のとおり:

  - 委任ブランチ: 単一タスクは `feature/<機能名>-copilot-task<タスク番号>`、まとめて渡す場合は `feature/<機能名>-copilot-task<最小番号>-<最大番号>`
  - 委任worktree: `~/worktrees/<リポジトリ名>-copilot-task<番号>` または `~/worktrees/<リポジトリ名>-copilot-task<最小番号>-<最大番号>`(`~/.claude`自身を委任するときは `~/worktrees/claude-copilot-task<番号>`)
  - **委任worktreeの絶対パスが、Command Sandboxingの`deniedPaths`のどの要素とも前方一致しないこと**を確かめる。前方一致するとworktreeごと書き込み拒否になり、委任先が何もできない。`~/worktrees/`配下なら拒否パスの `/Users/ryosyamazaki/.claude` とは前方一致しないが、worktreeを作る前に必ず確認する

  委任結果を検査してfeatureブランチへ差分を適用・コミットしたら、**worktreeと委任ブランチを必ず削除する**。残したままにすると、上記「他セッションとの重複を避ける」の確認で他セッションの作業と見分けがつかず、重複検知のノイズになる。逆に、この命名規則に一致するworktreeが残っている間は「未取り込みの委任がある」ことの目印になり、[/devflow:implementation-review](../implementation-review/SKILL.md)が開始時にそれを見て取り込む

# 注意事項

- **共有している作業ディレクトリに、未コミットの変更を残したまま離れない。** worktreeに分けていない作業ディレクトリは他セッションと共有しており、相手のブランチ操作で作業ツリーのファイルが入れ替わる。コミットしていない変更はgitのどこにも記録が無いため、消えたら復元できない(2026-08-25、`~/.claude/sandbox-limitations.md`への追記1件を実際に失った。stashにも残っていなかった)。**1行の修正でも、編集したらその場でコミットまで済ませる**
- **共有ディレクトリの追跡ファイルを短時間だけ直したいときは、使い捨てのworktreeを切る。** 相手が作業中のブランチ・未コミット変更に一切触れずに済む。`~/worktrees/<リポジトリ名>-<目的>`にデフォルトブランチベースで作り、そこで編集・コミットし、片付ける:

  ```bash
  export GIT_CONFIG_NOSYSTEM=1
  git -C <リポジトリ> worktree add ~/worktrees/<リポジトリ名>-<目的> <デフォルトブランチ>
  # 編集してコミット
  git -C <リポジトリ> worktree remove ~/worktrees/<リポジトリ名>-<目的>
  ```

  `~/.claude`ではこの方法に追加の利点がある。共有クローンの`skills/`・`hooks/`配下はサンドボックスの書き込み禁止対象だが、**リポジトリ外のworktreeは通常のパス扱いになるため、Bashから普通に編集・コミットできる**(`git merge`のunlinkがブロックされる問題も避けられる)
- **作業を中止したブランチ・worktreeは放置せず削除する。** 残っていると他セッションの重複検出(`git log --all`・`git worktree list`)でノイズになり、「進行中の作業」と誤認される
- **同じブランチを複数のworktreeでチェックアウトできない**(Gitの仕様)。「fatal: '...' is already used by worktree」が出たら、そのブランチは別のworktreeが使っている
- **開発サーバーのポート衝突**: 複数のworktreeで同時に開発サーバーを起動する場合、2つ目以降はポートをずらす
- **削除は`git worktree remove`で行う**。ディレクトリを`rm -rf`で直接消すとGit側に登録が残る(残ってしまった場合は`git worktree prune`で整理する)
- worktreeの一覧は`git worktree list`で確認できる。迷子になったらまずこれを実行する
