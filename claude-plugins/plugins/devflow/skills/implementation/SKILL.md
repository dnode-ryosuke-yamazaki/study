# 前提条件

- 仕様の承認を得てから着手する(3点セットについて[/devflow:spec-review](../spec-review/SKILL.md)の承認ゲートでユーザーの明示的な承認(「承認します」等)を得ていること。仕様承認PR方式のプロジェクトでは仕様承認PRがマージ済みであること。承認前はコード・テストを書かない)。着手前に3点セットのフロントマターを読み、3ファイルとも `status: approved` であることを確かめる。`draft`・`in-review` が残っていれば承認前か承認後に直されたままなので着手せず、ユーザーに確認する(値の遷移の正は[dev-flow.mdの「承認状態のフロントマター」](../../dev-flow.md#承認状態のフロントマター))。3点セットが未作成なら[/devflow:requirement](../requirement/SKILL.md)から、作成済みで未承認なら[/devflow:spec-review](../spec-review/SKILL.md)から始める
- `feature/<機能名>`(JIRAチケットがある場合は`feature/<JIRAキー>-<機能名>`)ブランチを切る(mainでは作業しない)。別の作業と並行する場合は[parallel-work](../parallel-work/SKILL.md)(worktree)で作業ディレクトリを分ける
- 対象プロジェクト/アプリが`architecture.md`(機能マップ)を持つ場合は、実装に着手する時点で該当specの状態列を「実装中」に更新し、更新後の機能マップ全体を報告に貼る([architecture-workflow](../architecture-workflow/SKILL.md)の「更新タイミング」。implementerエージェントに委譲する場合もこの更新はメインスレッドが行う)
- 対象specのtasks.mdの先頭(タイトル直下)へ `> 実装中: session <session名>, branch: <ブランチ名>, started: <着手日時のISO8601>` を1行追記する。他セッションが同じspecに気づかず並行着手する事故(仕様レビュー担当と実装担当が互いの存在を知らないまま同じ仕様書に同時着手した過去のニアミス)を防ぐための目印であり、tasks.mdを開けば実装着手済みかどうかが分かる状態にする。implementerエージェントに委譲する場合もこの追記はメインスレッドが行う

# 実施方法(メインスレッド or implementerエージェント)

通常はメインスレッドが本Skillの手順で直接実装する(実装中の判断をユーザーと対話しながら進められるため)。次の場合はimplementerエージェント(Agentツールの`subagent_type`は`devflow:implementer`。定義は`${CLAUDE_PLUGIN_ROOT}/agents/implementer.md`)に実装を委譲できる:

- [parallel-work](../parallel-work/SKILL.md)で複数機能を並行開発していて、一方の実装を任せたいとき
- tasks.mdが十分に詳細で、対話なしで完走できる見込みが高いとき

委譲する場合は対象spec(ローカルミラーパス)と作業するfeatureブランチ(またはworktree)を伝えて起動する。エージェントは仕様との食い違いに気づくと実装を中断して報告を返すので、ユーザーに確認してから再開する。コミット・PR作成・動作確認の案内はメインスレッドが行う。エージェントの既定モデルはSonnet([dev-flow.md](../../dev-flow.md)のモデル対応表参照)。複雑なロジック・複数の状態管理を伴う実装に限り、起動時に`model: opus`で上書きしてよい。

# TDDサイクル

🔴Red(失敗するテスト)→🟢Green(最小実装)→🔵Refactorのサイクルを、tasks.mdのタスクごとに完結させてから次に進む。書くテストの種類・量はdesign.mdのテスト戦略表に従う(種別の定義と完了条件の正は[テスト方針](../../test-policy.md))。

最初の🔴Redに着手し、仕様項目に対応するテストが書けたら、requirements.md のステータスのラベルの値だけを「実装中」に書き換える(行ごと消さず、優先度も残す。例: `ステータス: 実装中 ／ 優先度: 高`)。ラベルの3つの値と書き換えるタイミングの正は[区分け表のファイル](../../quality-standards/base/spec-layout.md)。

サイクルの中で次の3点を守る:

- **否定確認**: 分岐と生成物のテストは、🟢Greenのあと実装を1箇所壊して🔴Redになるのを見てから戻す。壊し方はテストのdocstringに1行残す(例: `否定確認: 条件の不等号を反転すると落ちる`)。緑のまま壊れているテスト(部分一致しか見ていない生成物テストなど)を残さないための手順
- **fixtureは加工しない**: 契約テストのfixture(実応答由来)は、テストが通るように編集しない。通らないなら実装か仕様のどちらかが実物と合っていないので、仕様との食い違いとして扱う(下記「実装中に仕様との食い違いに気づいたら」)
- **性能テストは別スイート**: `tests/perf/`に置き、TDDの毎サイクルでは回さない。全タスク完了後の動作確認とPR作成前に1回回す

# テストのコメント・命名ルール

コードを一切読まなくても、どの機能を・なぜ・どんな条件でテストしているかがテストの構造とコメントだけで分かる状態を目指す(以下は`describe`/`it`形式のテストフレームワークを前提にした表記。対象プロジェクトのテストフレームワークが異なる場合は同等の単位に読み替える)。

## describe
- どの機能・どの処理を検証しているかを、利用者に見える言葉で書く
- なぜそのテストが必要か(仕様の背景)が伝わるようにする
- 変数名・型名・関数名などコードの識別子をそのまま書かない

## it
- どんな条件(状況)で何が起こるべきかを日本語の文章で書く
- コード構文ではなく、意味のある言葉に置き換える(例:「リクエストボディにidが含まれない場合」)
- 境界値・特殊ケースは、なぜそのケースを検証するのかが伝わるようにする

## 仕様書との対応
テストの直前に1行、対応するspecの項目を参照するコメントを入れる。requirements.mdの見出し内で箇条書きに`[n]`が振られている場合は`見出し-n`の形式で、振られていない見出し(概要・スコープ外など)は見出し名だけを参照先にする。1つのテストが複数の箇条書きに対応する場合は`、`区切りでフルパスを繰り返す(`[n]`の付け方は[/devflow:requirement](../requirement/SKILL.md)参照)。

```
# 仕様: ~/.claude/local-specs/Users/you/repo/foo/specs/note-deletion/requirements.md#ノート削除API-2
```

specをリポジトリにコミットする例外リポジトリでは、リポジトリ内の相対パスを書く(例: `# 仕様: apps/notes-api/specs/note-deletion/requirements.md#ノート削除API-2`)。

specがリポジトリの外(ローカルミラー)にある場合、コメント中のパスはコードを読む人にとって「このコメントの意味が分かればよい」程度の参照として扱う。いずれの場合も、見出し名・`[n]`の表記は仕様レビュー・コードレビューで一致を確認する対象になるため、requirements.md側の表記と一字一句揃える。

# Copilotへの委任(agent-routing)

`~/.claude/config/agent-routing.json`があるプロジェクト・マシンで、tasks.mdに`【担当: copilot】`が付いたタスク(または[/devflow:design](../design/SKILL.md)がまとめた「まとめて渡せる組」)に到達したときの手順。設定が無ければこの節ごと不要で、`【担当: copilot】`が付いたタスクに到達してもclaude担当として実装する(判断材料が欠けたら安全側に倒し工程は止めない、という方針に揃える)。

## 委任コマンドの組み立て

委任は**非対話モード(`-p`)**で実行する。委任worktreeの外への書き込みは、承認プロンプトではなく**Command Sandboxing**(OSレベルの隔離。macOSではSeatbelt)で遮断する。

非対話モードは`--allow-all-tools`が必須で承認プロンプトが一切出ないため、**Command Sandboxingが有効であることが委任の前提条件**になる。`--add-dir`は「そのディレクトリを事前承認する」オプションであって範囲外のハード拒否ではないので、承認プロンプトが無い状態では単独では何も守らない。

### 前提1: Command Sandboxingが有効であること

Command Sandboxingは`~/.copilot/settings.json`の`sandbox`キーで設定する**恒久設定**で、委任のたびに投入し直さない。**Claudeはこのファイルを書き換えない**(マシン単位の設定で、手元のCopilotを他の用途にも使っているため)。委任コマンドを提示する前に、次のブロックで設定が生きていることを毎回確認する。

**手元のターミナル**に貼る確認用ブロック:

```bash
cat ~/.copilot/settings.json
cat ~/.copilot/permissions-config.json
```

`settings.json`が満たすべき条件:

- トップレベルに`"experimental": true`。Command Sandboxingは実験機能で、これが無いと`sandbox`キーが効かない(コマンドライン側で有効化する場合は`--experimental`)
- `sandbox.enabled`が`true`
- `sandbox.addCurrentWorkingDirectory`が`true`(委任worktreeを読み書き可能にする)
- `sandbox.allowBypass`が`false`(コマンド単位でサンドボックスを抜ける逃げ道を塞ぐ)
- `sandbox.auth.git`と`sandbox.auth.gh`がどちらも`false`(サンドボックス内のコマンドにgit・`gh`の資格情報を注入させない)
- `sandbox.userPolicy.filesystem.deniedPaths`に、守りたいディレクトリの絶対パスが列挙されている(最低限`~/.claude`)
- `sandbox.userPolicy.network.allowOutbound`が`true`(依存パッケージの取得に要る)

**`deniedPaths`の指定は省略できない。**Command Sandboxingの既定の付与範囲には、作業ディレクトリ・PATH上のディレクトリ・一時ディレクトリに加えて**ユーザーのホームディレクトリが含まれる**。`deniedPaths`を書かなければ、サンドボックスが有効でもホーム配下の`~/.claude`や他リポジトリには届いてしまう。委任worktreeの外で守りたい場所は明示的に列挙する。

条件を満たしていなければ委任を中断し、満たすべき値をユーザーに提示する。

**委任worktreeの絶対パスが`deniedPaths`のどの要素とも前方一致しないことを、worktreeを作る前に確かめる。**前方一致するとworktree自体が拒否パスの内側に入り、委任先はどのファイルも書けないまま終わる。[parallel-work](../parallel-work/SKILL.md)の命名規約どおりの名前が衝突する場合(`~/.claude`を拒否パスに持ち、かつ`~/.claude`自身を委任する場合の`.claude-copilot-task1`など)は、衝突しない名前へ変えて、変えた理由をユーザーに伝える。

### 前提2: 恒久承認が残っていないこと

`~/.copilot/permissions-config.json`の`locations`が空(`{"locations":{}}`)であることを確認する。**恒久承認は残さない運用にする。**

Copilot CLIを対話モードで使ったときに「常に許可」を選ぶと、その承認がこのファイルへ書き出され、以後の全セッション(非対話の委任を含む)に効き続ける。恒久承認は`--deny-tool`と違ってコマンドラインに現れないため、委任コマンドだけを読んでも実際の権限が分からなくなる。対話モードで許可を求められたときは、その場限りの許可だけを選ぶ。

`locations`に項目が残っていたら内容をユーザーに提示し、消してから委任する。消す前のファイルは`permissions-config.json.bak-<日付>`として退避する。

### 遮断の範囲

Command SandboxingがOSレベルで隔離するのは**シェルコマンド**で、CLI組み込みのファイル編集ツールはOSサンドボックスの外にあり、同じポリシーにベストエフォートで従うにとどまる。したがって下記「委任結果の取り込み」のスナップショット比較は、サンドボックスがあっても省略しない。

### 手順

1. 委任worktreeへ移動してCopilot CLIを**非対話モード**で起動する行を作る。起動オプションには次を必ず含める
   - 非対話実行に必須のツール許可: `--allow-all-tools`。これは「シェルのリダイレクトを含め、ツール実行の確認を出さない」指定で、遮断はCommand Sandboxingが担う
   - コミットの実行を拒否するツール権限の指定: `--deny-tool='shell(git commit)'`。**拒否指定は`--allow-all-tools`より優先される**ため、非対話モードでもコミット禁止は効く
   - 読み書きを許すディレクトリの指定: `--add-dir`。仕様の該当箇所を委任先に読ませる必要がある場合は対象specのディレクトリも加える
   - セッションのクレジット上限: `--max-ai-credits <セッション上限>`(設定`delegationSessionMaxCredits`。既定300。CLIが受け付ける最小値は30で、設定がこれを下回る場合は30へ切り上げ、切り上げた事実を表示する)
   - 実消費の出力先: `--usage-output-file <委任worktree>/copilot-usage.json`。下記「委任1件ごとの消費の記録」でClaudeが直接読む
   - 問い返しの無効化: `--no-ask-user`。非対話モードで委任先が質問を返すと、答える相手がいないまま止まる
   - 委任プロンプト: `-p "$(cat '<委任プロンプトファイル>')"`。プロンプト本文はClaudeがファイルへ書き出しておき、コマンドでは読み込むだけにする

   **次の3つは使ってはいけない**(パス検証を無効化し、`deniedPaths`より手前にある既定のパス制限まで外れる)
   - `--allow-all-paths`
   - `--allow-all` / `--yolo`(いずれも`--allow-all-tools` + `--allow-all-paths` + `--allow-all-urls`)
   - 対話中の`/permissions`での全許可
2. 起動前にユーザーが行う操作を、次の順でブロックに添える
   - 委任用アカウントでログインしていることを確認する。**非対話モードには`/user`が無い**ため、`~/.copilot/config.json`の`lastLoggedInUser.login`を確認する。**このファイルは資格情報ストアが使えない環境ではトークンも保持するため、`cat`で全体を表示せず該当行だけを取り出す**
   - 委任用アカウントでなければ、`copilot`を素で起動して`/login`で切り替え、`/exit`で抜けてから委任コマンドを実行する

   **切り替えは必ず`/login`で行う。`/logout`を案内しない。**`/logout`は`/login`で作ったセッションしか消せず、GitHub CLI由来の資格情報は消せないため、実行するとレビュー用アカウントに戻るだけになる(ここで「まず`/logout`してから」と補ってしまうと、レビュー用アカウントのクレジットで委任が走りアカウント分離が実行時に破れる)。何もログインしていなければCopilot CLIはGitHub CLIのトークンを継承してレビュー用アカウントで動く
3. 委任プロンプトの定型には、そのタスク(まとめて渡す場合は全タスク)の内容と受け入れ条件・**変更してよい対象ファイルの範囲**・**テストファイルの変更禁止**・テストの実行方法を必ず含める。コミット禁止と委任worktreeの外を触らせないことは手順1のツール権限とCommand Sandboxingで強制されるためプロンプトには書かない。一方`--add-dir`と`deniedPaths`が絞れるのはディレクトリ単位までで、worktree内のどのファイルまで触ってよいかは権限では表現できないため、対象ファイルの範囲はプロンプトで伝え、下記「委任結果の取り込み」の検査で担保する。**委任worktreeがエージェント向けの指示ファイル(`CLAUDE.md`・`AGENTS.md`等)を追跡している場合、委任先はそれを読んで従う**ため、それと食い違う指示を委任プロンプトに書かない(2026-09-16、`~/.claude`の委任で、プロンプトの`git add -A`が追跡されている`CLAUDE.md`の禁止規定に上書きされた)
4. セッション上限は**soft cap**であり、上限を超えたあとの次のモデル呼び出しがブロックされる形で止まるため上限をわずかに超えうること、上限の50%・75%・90%到達時にCLI側で通知されることをブロックに添える。**上限に達してモデル呼び出しがブロックされ委任が途中で止まった場合は、下記「委任結果の取り込み」以降で打ち切りと同じ扱いにする**(そこまでの成果物を検査に回す。`--usage-output-file`は失敗・中断で終わった場合もJSONを書き出すため、実消費は打ち切りでも読める)
5. 実行が想定所要時間を大きく超えた場合の打ち切りの目安をブロックに添える。**非対話モードの打ち切りは、実行中のターミナルでのCtrl-C**であること、打ち切ってもそこまでの成果物を検査に回すことも添える。打ち切っても`--usage-output-file`のJSONはそこまでの実消費を載せて書き出される。**スクリプトから打ち切る場合はプロセスグループ宛てにSIGINTを送る**(ジョブ制御を有効にしたうえで`kill -INT -<pgid>`)。Copilot CLIのプロセス単体へ送ると無視され、実行中のシェルコマンドが終わるまで止まらない(2026-09-16、`sleep 300`の実行中にプロセス単体へ送って5分8秒完走した)
6. オプション名・対話コマンド名・表示形式はCopilot CLIの自動更新で変わりうる。ユーザーから「オプションが受け付けられない」と報告を受けたら、推測で書き換えず現行の名称を実機で確認してから仕様側を更新する
7. **提示するブロックとその手順には、必ず「どこに打つか」のラベルを付ける。**1回の委任でユーザーが触る場所は次の2つで、どちらも見た目が同じテキストブロックのため、ラベルが無いと区別できない(2026-09-10、ラベル無しで提示して「自分は次何をすればいいのか」と指摘を受けた)
   - **手元のターミナル**: 上記「前提1」「前提2」の確認ブロック、手順2のアカウント確認、手順1の委任コマンドブロック
   - **Copilot CLIの対話プロンプト**: 手順2でアカウントの切り替えが必要になった場合の`/login`・`/exit`だけ

   委任プロンプトはClaudeがファイルへ書き出してコマンドから読ませるため、**ユーザーがCopilot CLIへ本文を貼り付ける操作は無い**。ラベルはブロックの外側に1行で置く(ブロックの中はコマンドだけにする)。手順の箇条書きの中でも、各ステップの主語が上記のどちらなのかが読み取れる書き方にする

**アカウント確認ブロックの雛形**(**手元のターミナル**に貼るもの):

```bash
grep -A2 '"lastLoggedInUser"' ~/.copilot/config.json | grep '"login"'
```

表示された`login`が委任用アカウントのユーザー名でなければ、`copilot`を素で起動して`/login`で切り替え、`/exit`で抜ける。

**委任コマンドブロックの雛形**(`<>`は実値に置き換える。パスに空白や括弧が含まれる場合はクォートする)。ブロックの中にはコマンドだけを置き、説明はブロックの外に書く。**ブロックの直前に宛先を1行で書く**(例: 「手元のターミナルに貼ってください(Claude Codeのチャットではありません)」):

```bash
cd '<委任worktreeの絶対パス>'
copilot \
  --allow-all-tools \
  --deny-tool='shell(git commit)' \
  --add-dir '<委任worktreeの絶対パス>' \
  --add-dir '<対象specディレクトリの絶対パス>' \
  --max-ai-credits <セッション上限> \
  --usage-output-file '<委任worktreeの絶対パス>/copilot-usage.json' \
  --no-ask-user \
  -p "$(cat '<委任プロンプトファイルの絶対パス>')"
```

`--add-dir`は複数回指定できる。specを読ませる必要がなければ2つ目の`--add-dir`は省く。`settings.json`に`"experimental": true`が無い場合だけ、先頭に`--experimental`を足す。

**委任プロンプトファイル**は、Claudeが**委任worktreeの外**(`<委任worktreeの絶対パス>-prompt.md`)へ書き出す。worktreeの中に置くと、下記「委任結果の取り込み」の追跡外ファイルの収集に引っかかり、委任先の成果物と区別できなくなる。`copilot-usage.json`のほうはCLIの出力先の都合でworktree内に置くため、取り込み時に既知のファイルとして除外する。

**委任プロンプトの雛形**(**Claudeがファイルへ書き出す**もの。ユーザーがCopilot CLIへ貼る操作は無い):

```
次のタスクを実装してください。

## タスク
<タスクの内容。まとめて渡す場合は全タスクを番号付きで列挙する>

## 受け入れ条件
<各タスクの受け入れ条件。requirements.md/design.mdの該当項目の文言をそのまま使う>

## 変更してよいファイル
<対象ファイルのパスを列挙する。ここに挙がっていないファイルは変更しないでください>

## 変更してはいけないもの
- テストファイル(<テストファイルのパス>)。テストは既に用意してあります。テストを通す実装のみを行ってください

## テストの実行方法
<テストコマンド>

上記のテストがすべて通ることを確認してから完了を報告してください。
```

コードを持たないタスク(ドキュメント・設定ファイルの更新)を委任する場合は、`## 変更してはいけないもの`と`## テストの実行方法`の2セクションを外し、代わりに受け入れ判定の観点(記載内容の何をもって受け入れるか)を書く([委任タスクのテスト](~/.claude/local-specs/Users/ryosyamazaki/.claude/specs/agent-routing/requirements.md#委任タスクのテスト)の「コードを持たないタスクは記載内容の検査で受け入れを判定する」に対応)。

## 委任の実行

1. 対象specが承認済みであることを確認する(未承認なら委任しない)
2. **前提の確認**: Copilot CLIの実体が導入されているかを確認する。PATH上の`copilot`はVSCode拡張が持つラッパーであることがあり、`command -v copilot`だけでは導入確認にならない。実体のパスとバージョン表示まで確認し、未導入なら導入コマンドブロック(`npm install -g @github/copilot`)を提示して委任を中断する
3. **Redテストの用意**: そのタスク(まとめて渡す場合は組の全タスク)がコードを変更するなら、Claudeがfeatureブランチ側で各タスクの受け入れ条件を表す失敗するテストを書き揃えてコミットする。コードを持たないタスク(ドキュメント・設定の更新)ではこの手順を飛ばす
4. featureブランチの現在位置から委任用ブランチを切り、リポジトリの外に委任worktreeを作る(命名は[parallel-work](../parallel-work/SKILL.md)参照)。**このときのコミットSHAを「委任基点」として記録する**(キャッシュには保存しない。セッションをまたいで取り込む場合など委任基点が手元に無いときは、`git merge-base <featureブランチ> <委任ブランチ>`で復元する)。あわせて親リポジトリの作業ディレクトリの状態(`git status --porcelain`)を委任前スナップショットとして記録する。**上記「委任コマンドの組み立て」手順1で`--add-dir`に対象specのディレクトリを加える場合は、そのディレクトリぶんのスナップショットも同時に取る**(specがローカルミラーにある場合は親リポジトリとは別のリポジトリなので、親のスナップショットには含まれない。git管理下なら同じく`git status --porcelain`、管理外ならファイル一覧とハッシュで代替する)
5. 上記「委任コマンドの組み立て」に従い、委任プロンプトを`<委任worktreeの絶対パス>-prompt.md`へ書き出したうえで、前提の確認ブロック・アカウント確認ブロック・委任コマンドブロックを提示する
6. 提示と同時に、下記「委任1件ごとの消費の記録」の暫定計上を行う
7. ユーザーから完了報告(または打ち切りの報告)を受けたら「委任結果の取り込み」へ進む

## 委任結果の取り込み

1. **変更の収集**: 委任worktreeで次の3つを取る。(a) 委任基点([委任の実行](#委任の実行)手順4。手元に無ければ`git merge-base`で復元する)以降のコミット、(b) 作業ツリーの未コミット変更、(c) 追跡外ファイル。(c)は**`git status --porcelain --ignored`**で取り、`??`行と`!!`行の両方を見る。`--ignored`を省いてはいけない: `.gitignore`が「全部無視してホワイトリストで戻す」方式(`/*`で始まる。`~/.claude`がこれにあたる)のリポジトリでは、委任先が新規に作ったファイルが無視対象に入るため素の`git status --porcelain`には1行も出ず、収集が静かに空になる。(c)からは`copilot-usage.json`(委任コマンドで指定した実消費の出力先)を除外する。(a)〜(c)がすべて空の場合、Copilot CLIをまだ起動していないのか、起動したが成果を残せなかったのかのどちらかなので、**`copilot-usage.json`の有無で判定する**。ファイルがあれば起動されている(このファイルは委任が失敗・中断で終わった場合も書き出される)。ファイルが無ければ起動したかどうかをユーザーに確認する。起動していなければ暫定計上を取り消す。起動していた場合は成果物がゼロでもセッションを1つ立てた固定費ぶんの消費が発生しているため取り消さない。いずれの場合も、実行を待つかclaude引き取りに切り替えるかをユーザーに選んでもらう
2. **コミット禁止違反の検出**: (a)が空でない場合、ツール権限による禁止をすり抜けてコミットされた事実を報告する。成果物は破棄せず`git reset --soft <委任基点>`で作業ツリーの内容を保ったまま平坦化してから検査に進む。この検出はCLIの自動更新でオプションが効かなくなった場合の検知を兼ねるため、報告には権限指定の見直しが必要である旨を添える
3. **範囲外変更の検出**: 親リポジトリの作業ディレクトリの現在の状態を委任前スナップショットと比較し、差があれば報告する。あわせて**委任worktree内の**変更ファイルが委任プロンプトで指定した対象ファイルの範囲に収まっているかを確認し、範囲外があればユーザーに提示して取り込みの可否を判断してもらう。マシン単位の設定ファイル(`~/.claude/config/`配下)への変更は常に範囲外として報告する。**上記「委任コマンドの組み立て」手順1で`--add-dir`に対象specのディレクトリを加えた場合は、そこも同じ要領で検出対象に含める**(`--add-dir`は読み取りと書き込みを分けられないため、委任先が仕様書を書き換えられる。委任前に`git status --porcelain`のスナップショットを取っておき、取り込み時に比較する)

   **変更ファイルの判定にCLIの出力を使わない。**`copilot-usage.json`の`codeChanges.filesModified[]`・`filesModifiedCount`は、シェル経由で作成・変更されたファイルを取りこぼす(組み込みの編集ツールを通らないため。実測では`filesModifiedCount`が0のまま新規ファイルが1つ作られていた)。範囲の検査は常にスナップショット比較と`git status`で行う。Command Sandboxingが有効でも同じで、OSレベルで隔離されるのはシェルコマンドだけであり、組み込みの編集ツールはポリシーにベストエフォートで従うにとどまる
4. **テストによる検査**: コードを変更するタスクでは、委任worktreeでテストを実行して各Redテストがそれぞれ通ったことを確認し、テストファイル自体が変更されていないことも確認する。どちらか欠けたら検査不通過
5. **仕様との突き合わせ**: 変更内容をrequirements.md/design.mdの該当項目と突き合わせてレビューする。まとめて渡した場合は組の全タスクについて行う
6. **消費の確定**: まず委任可否を判断する経路の前処理として、[/devflow:design](../design/SKILL.md)の「クレジット残量の記録」の手順1〜3で記録を有効にする(取り込みが別セッション・別の日になっていても、リセット日を越えた記録に消費を積まないため)。設定が無効なら委任自体を提示しないので暫定計上は起きず、記録は書き換えない。そのうえで委任worktreeの`copilot-usage.json`を読み、`totalNanoAiu`を`1e9`で割った値を実消費のAIクレジット額として下記「委任1件ごとの消費の記録」へ渡す(例: `9454250000` → `9.45425`クレジット)。ファイルが無い・JSONとして読めない・`totalNanoAiu`が欠けている場合は実測が得られなかったものとして扱う
7. **取り込み**: 検査通過の場合のみ、差分をパッチとしてfeatureブランチ側へ適用してコミットする。コンフリクトした場合はClaudeが手で解消してからコミットする(委任worktree側をやり直させない)。`copilot-usage.json`と`<委任worktreeの絶対パス>-prompt.md`は取り込まない
8. **claude引き取り**: 手順3〜5のいずれかで問題を検出した場合、または打ち切り報告だった場合は、同じタスクを再委任せず、Claudeが差分を取り込んだうえで自分で修正・実装してからコミットする(クレジットを重ねて消費しない)。**手順2のコミット禁止違反は報告のみで引き取りの理由にしない**(成果物を破棄しないのが要件で、平坦化したうえで手順3〜5の検査を通れば通常どおり取り込む)。**失敗理由がクレジット切れ**(Copilot CLIがプランの上限到達でモデル呼び出しを止めた)だった場合は、引き取りに加えて、記録の「使った量」(`planUsedCredits`)をプラン上限(`planLimitCredits`)と同じ値にして有効残量を0にし、以後の委任を止める(次の実測の貼り付けか次のリセット日の繰り越しまで委任しない。下記「委任1件ごとの消費の記録」手順6)。クレジット切れの判定は、Copilot CLIの出力(完了報告に貼られた末尾)にプランの上限到達の旨が出ていること、または`copilot-usage.json`が書き出されているのに成果物が皆無で`totalUserRequests`が1以下であることのどちらかによる
9. **掃除**: 委任worktreeと委任ブランチを削除し、`<委任worktreeの絶対パス>-prompt.md`も消す。**手順6で実消費を読み取ってから消す**(worktreeを消すと`copilot-usage.json`も一緒に消える)

## 委任1件ごとの消費の記録

対象は`~/.claude/config/agent-routing-credits.json`の`unreportedConsumption`。**キー名・構造は[/devflow:design](../design/SKILL.md)の「キャッシュのフォーマット」に従い、その場で決め直さない**(決め直すと次回の読み取りで必須項目の欠損と判定され、記録が壊れたものとして退避され続ける)。有効残量の計算と消し込みは同じく[/devflow:design](../design/SKILL.md)の「有効残量の計算と未反映消費の消し込み」に従う。

残量は、設定の付与総額から月ごとに用意する記録を土台にした自己計上で求める。実消費は**Claudeが`copilot-usage.json`から直接読み**、ユーザーに貼り付けは求めない。プラン上限とプランの使った量(プラン値)は委任セッションのJSONに含まれないが、ユーザーが`/usage`の出力を任意の補正として貼り付けてきたときだけ手順5で受け付ける。

1. **暫定計上**(コマンドブロックの提示時): まず委任可否を判断する経路の前処理として、[/devflow:design](../design/SKILL.md)の「クレジット残量の記録」の手順1〜3で記録を有効にする(リセット日を越えた記録に積まないため)。設定が無効なら委任自体を提示しないので暫定計上は起きず、記録は書き換えない。そのうえで未反映消費リストに、設定のセッション上限(既定300)を消費額とし、暫定であることを示す印・提示時刻・**委任ブランチ名**を添えたエントリを1件追加する。委任ブランチ名は、1回の走行で複数の委任を出したときに実測をどのエントリへ書き戻すかを決めるために要る。プラン値の読み取り日時は更新しない
2. **実測への置き換え**(完了時): [委任結果の取り込み](#委任結果の取り込み)手順6で読み取った実消費(`totalNanoAiu / 1e9`)で、**委任ブランチ名が一致するエントリ**の消費額を上書きし、暫定の印を外す。打ち切られた委任・上限に達して止まった委任でも、`copilot-usage.json`は書き出されるため同じく置き換える。ここでもプラン値の読み取り日時は更新しない
3. **実測が得られない場合**: `copilot-usage.json`が無い・JSONとして読めない・`totalNanoAiu`が欠けている場合は、手順1の暫定エントリをそのまま残し、実測ではなくセッション上限で計上している事実を報告する。あとからファイルが見つかれば手順2で置き換える
4. **未起動の場合**: 取り込み手順1で変更が皆無であり、`copilot-usage.json`も無く、**かつCopilot CLIを起動していないことがユーザーの回答で確認できた場合に限り**、手順1の暫定エントリを削除する
5. **プラン値の消し込み**: ユーザーが`/usage`の出力を貼り付けてきたときだけ、満額の記録を用意せず([/devflow:design](../design/SKILL.md)の「クレジット残量の記録」の手順1の設定の検証と手順2の記録の読み取り・退避のみ行う)、貼り付け前の記録と比べて消し込みまたはリセットまたぎの判定を行う(同じ節の手順8〜10と同じ要領。貼り付けは求めない)。プラン値は`copilot-usage.json`には含まれないため、貼り付けが無ければプラン値は変えず、未反映消費の積み上げだけで有効残量を更新する
6. **報告と停止判定**: まず委任可否を判断する経路の前処理として、[/devflow:design](../design/SKILL.md)の「クレジット残量の記録」の手順1〜3で記録を有効にする。設定が無効なら委任自体を提示しないので暫定計上は起きず、記録は書き換えない。そのうえで更新後の有効残量とその内訳を報告する。有効残量が委任用閾値未満になったら以後の委任を止め、次に委任基準を満たすタスクへ到達しても委任コマンドブロックを提示せずclaude担当として実装し、残量不足で止めた旨を表示する。委任がクレジット切れで失敗していた場合([委任結果の取り込み](#委任結果の取り込み)手順8)は、`planUsedCredits`を`planLimitCredits`と同じ値にして有効残量を0にし、次の実測の貼り付け(手順5)か次のリセット日の繰り越しまで委任を提示しない(自己計上が実際より多く見積もっていた証拠なので、残量を信用せず止める)

# 実装中に仕様との食い違いに気づいたら

実装を仕様に合わせるのが原則。仕様側が誤っている・不足していると分かった場合は、勝手に実装だけ変えず、3点セットを同じ変更で更新する(更新時の確認範囲は[/devflow:fix](../fix/SKILL.md)のStep2を参照)。ビジネスルールの変更に当たる場合はユーザーに確認する。

# 動作確認

全タスクのテストが通ったら、実際に動かして変更した機能が期待どおり動くことを確認する。UIを持つアプリは`run`Skill等でアプリを起動して画面を操作し、UIを持たないAPI・バッチ処理はcurl・統合テスト等でエンドポイントや処理を直接呼び出して確認する。lint・buildコマンドが定義されているプロジェクトはそれらも通しておく。

**tasks.mdの「完了時の確認」に書いた項目は、実測値を添えて埋める。**「〜以内であること」「違反0であること」のように数値・判定で書かれた項目は、実際に測った値をチェックリストの行に書き足す(`- [x] <項目> → <実測値>`)。**満たしていない場合は満たすまで直してから完了とする。**このチェックリストは他人のためではなく、その仕様が自分で決めた条件を守れているかの確認で、埋めずに完了報告すると誰も確かめないまま残る。仕様側の数値が誤っていると分かった場合は、実装だけを変えず3点セットを同じ変更で更新する(上記「実装中に仕様との食い違いに気づいたら」)。

design.mdの「テスト戦略」で**環境スモーク**を宣言した仕様項目がある場合、tasks.mdの末尾に[テスト方針](../../test-policy.md)「環境スモーク」の定型3項目(本番と同じ経路で起動する・成果物が出る・失敗時の通知が届く)を確認チェックリスト(`- [ ] <項目> → 確認結果`)として置き、**本番と同じ起動経路**(launchd・`claude -p`・手元ターミナル)で実際に通した結果を埋める。サンドボックスの中で関数を直接呼んだ結果は環境スモークにならない。無人実行・定期実行するものは3項目とも省略不可で、当日通せない場合(深夜発火を待つ等)は未了であることと外れたときの影響を残件として書く。[/devflow:pr](../pr/SKILL.md)の実装PR本文の「動作確認」はこのチェックリストを参照・転記する。
