## 記録係の判定と行の組み立て

### 2. 記録係の Swift パッケージを作り、設定ファイルを読んで記録するかどうかを決める処理を作る 【担当: claude】

終わりの日時を過ぎたら記録を止め、設定が読めなければ記録しない側に倒せるようにする。

<details><summary>詳細を開く</summary>

- `recorder/Package.swift`(外部の依存なし)、`Sources/RecorderCore/Config.swift`・`RecordingDecision.swift`
- 設定ファイルの形は appendix.md「設定ファイルの形」。必須項目の欠け・型違い・壊れた JSON は「設定が読めない」になる。`stoppedAt` は必須でなく、欠けていたら `null` とみなす。設定ファイルが無い場合は「設定が読めない」ではなく「終わりの日時が無い」として扱い、`configError` を `null` にする
- 判定: 終わりの日時なし・今がその日時以降は停止。開始の行を書くべきかは直前の回の状態から決める。停止の行を書くべきかは記録のファイルの最後の行の種類から決める(最後の行が停止の行でなく、今は記録しない状態なら停止の行を書く)。停止の理由は設定の `endsAt`・`stoppedAt` から決める(`endsAt` が有り今がそれ以降なら `endsAtPassed`、`endsAt` が無く `stoppedAt` が有れば `stopRequested`、どちらも無ければ `endsAtMissing`)
- 停止の行の時刻: 終わりの日時を過ぎて書く場合は最後の行の時刻と終わりの日時の遅い方、止める依頼で書く場合は最後の行の時刻と `stoppedAt` の遅い方。どちらも無い場合(設定ファイルが無い場合を含む)は理由 `endsAtMissing`・時刻はその回の時刻。その時刻の日本時間の日付のファイルに書く(design.md 手順3)
- 起動した最初の回の初期化(`Sources/RecorderCore/LastLine.swift`): いちばん新しい記録のファイルの最後に読める行の時刻と種類を読む。書きかけの最終行は飛ばして1つ前を使う。ファイルが無い・読める行が無い場合は停止の行とみなす
- 設定が読めない回は停止の行を書かず、「記録していない回」として扱う。読めるようになった最初の回は開始の行を書く
- テスト: 記録の始め方・止め方-4(1秒前・ちょうど・後、停止の行が1回だけ。起動し直した最初の回・設定が読めるようになった回に、記録しない状態なら停止の行を書く。最後の行がすでに停止なら書かない。停止の行の時刻: 水曜18時終了・水曜17時30分に閉じて木曜9時に開いた例で水曜18時になり水曜のファイルに書かれる、止める依頼で `stoppedAt` と最後の行の遅い方、`endsAt` と `stoppedAt` がどちらも null なら理由 `endsAtMissing`・時刻はその回の時刻(設定が読めなかった時間が停止の行より前の空きとして残る)。初期化: 書きかけの最終行を飛ばす・ファイルが無い・読める行が無い)、-5、設定が読めない回に停止の行を書かないこと、設定ファイルが無い回は最後の行が停止でなければ `endsAtMissing` の停止の行を書き `configError` が `null` になること。設定ファイルの契約テストは、fixture を書き出すタスク11で置く

</details>

- `exclude-add --request-file` は、週次レポートの依頼文をそのままファイルから読む。1行目の決まり文句を確かめ(違えば `badRequest`)、「ことば: 」「アプリ: 」の行に分け、空の行・形の違う行を除き(`skippedLines`)、すでにあるものは足さずに控え(`alreadyExists`)、残りを1回の書き換えで足して(`added`)、足したあとの一覧を返す。`--bundle-ids-file` にあればそのアプリに付ける(design.md「記録しないアプリ・ことばを変える・メモを書き足す」の手順6、呼び方と結果の形は appendix.md)。設定ファイルが読めないときは何も足さずに断る
- 同じ依頼文の中の重複は1つにまとめる。有効な行が1つも無いときは設定ファイルを書き換えず `ok: true` で `added` を空にして返す。`--bundle-ids-file` に依頼文に無いアプリ名・すでにあるアプリ名が来たら無視する(design.md「バリデーション」)
- 共有 fixture `tests/fixtures/exclusion_request.txt` をこのタスクで作る。中身は appendix.md「操作スクリプトの呼び方」の依頼文の3行(決まり文句・`ことば: 給与明細`・`アプリ: 家計簿`)で、末尾に改行1つ。weekly-automation-report のタスク9もこの fixture を使う
- ログには追加・削除の件数だけを書き、ことば・アプリ名は書かない
- バリデーションは design.md「バリデーション」。メモの番号の形は appendix.md「メモのファイルの形」
- 設定ファイルが壊れているときは、除外の追加・削除を `configUnreadable` で断る(メモは書ける)
- テスト: 記録しないアプリ・ことばの一覧-5・-6・-7(-7 は weekly-automation-report と共有する fixture `tests/fixtures/exclusion_request.txt` を `exclude-add --request-file <fixture のパス>` でそのまま読む契約テスト。正常(fixture のことば1件・アプリ1件)・決まり文句違い・形の違う行・空の行・すでにある・設定ファイルが読めない。テストの中で組み立てた依頼文で、ことば2件・重複をまとめる・有効な行が無い・`--bundle-ids-file` の無視の分岐。書けないときに `inputFile` と `bundleIdsFile` の2つが返る分岐、`--request-file` が無い・読めないときの `badInputFile` の分岐。面倒だった作業のメモ-1 に入力ファイルから読む・`badInputFile`・`dataFolderUnwritable`(入力ファイルが残り、その絶対パスが返る)の分岐を含める。-5 に設定ファイルが壊れているときに断る分岐を、-6 に設定ファイルが無いときは初期値を返しファイルを作らない分岐を含める)、面倒だった作業のメモ-1〜5(-5 は 1,999字・2,000字・2,001字)、日付と週の基準-2(日曜 23:59 と月曜 0:00 のメモの週の振り分け)
