# 0003. 開催者自身の予定の件名だけを専用フローで取得する

## ステータス

Proposed (2026-10-08)。仕様承認PRのマージをもって Accepted にする

## コンテキスト

候補の絞り込みでは、開催者を含む参加者全員の空き状況が「空き」の枠だけを候補にしている([adr/0002](0002-availability-interpretation-in-skill.md))。この判定では、参加者全員は空いていて開催者自身の予定(仮・予約済みなど)だけが重なる枠も、他の参加者が埋まっている枠と同じく候補から外れ、選択画面にもチャットにも出ない。実際の運用で、候補が少ないときに候補ファイルを人が読み返してそうした枠を見つける場面があった。

開催者自身の予定は開催者が動かせるため、他の参加者に確認せずに開けられる「調整しろ」として価値がある。ただし「どの予定が重なるか」が分からないと動かしてよいか判断できないので、枠と一緒に重なる予定の件名を示す必要がある。

一方、このアプリは予定の件名を扱わない方針を取っている。参加者の予定の件名を取る経路(開催者のメールボックスにマウントされた共有カレンダーを読む)は、参加者側のカレンダー共有設定に依存し、実際の名簿372名のうち共有されていたのは1名だけだった。そのため、仮の予定を持つ参加者の件名を取る予定詳細フローは機能として当てにできないと判断して廃止し、代替案1では「誰に仮の予定があるか」までを示すことにしている。

今回の要求は参加者ではなく開催者自身の予定の件名であり、前提が異なる。

- 開催者自身の既定カレンダーは、共有設定に関係なくOffice 365 Outlookコネクタの専用アクションで常に読める
- 件名は開催者本人の情報であり、他人の予定を扱う問題が起きない
- 空き時間の探索(「会議の時間を検索 (V2)」)の応答には開催者の空き状況(`organizerAvailability`)はあるが件名は無く、探索フローの応答だけでは件名を示せない
- Graphパススルーは `POST /me/events` 以外の経路が通らず、読み取りには使えない(architecture.md 技術的制約)

## 決定

- **参加者全員が「空き」で開催者だけが「空き」以外の枠を「開催者の予定のみ重なる枠」として、候補とは別の区画で示し、候補と同じように選べるようにする。** 候補には数えず、候補が0件かどうかの判定にも含めない。開催者が自分の予定を調整すれば開けられる枠であることを見出しに書く
- **重なる開催者の予定の件名・開始と終了・空き状況の種別は、開催者自身の既定カレンダーだけを読む専用のPower Automateフロー(開催者予定フロー)で取得する。** アクションは「カレンダー ビューの取得 (V3)」とし、繰り返し予定を回ごとに展開して受け取る。Skillは開催者の予定の依頼ファイルを書き出し、他の台帳と同じくフォルダ監視トリガーとOneDrive同期で結果を受け取る
- **参加者の予定の件名は引き続き扱わない。** 開催者予定フローの対象を参加者に広げない。代替案1の表示(誰に仮の予定があるか)も変えない
- **件名の取得は枠の提示の前提にしない。** 待ち上限(候補の待ちと同じ5分)を超えた・結果に失敗理由が返った・依頼を書き出せなかった場合は、件名なしで枠を示し、取得できなかった理由を添える
- **開催者の予定ファイルは他の台帳と同じく削除しない。** 書き出す項目を件名・開始と終了・空き状況の種別・非公開かどうかに絞り、本文・出席者・場所は書き出さない。非公開(プライベート)の予定は件名の代わりに「非公開の予定」と示す

採らなかった案:

- **探索フローの応答だけで済ませ、件名を示さずに枠だけを出す**: フローを増やさずに済むが、どの予定が重なるか分からないと動かしてよいか判断できず、結局カレンダーを開いて確かめることになる
- **探索フローの中で開催者の予定も読んで候補ファイルに含める**: 往復が1回で済むが、開催者の予定のみ重なる枠が無い依頼でも毎回カレンダーを読むことになり、探索フローが「渡された条件で探す」だけの役を超える(architecture.md 設計方針3)
- **Graphパススルーで `me/calendarView` を読む**: コネクタの検証で読み取りの経路は通らない(実測済み)

## 影響

- Power Automateフローが4本になり、開催者予定フローの構築は開催者が画面での手作業で行う。構築手順は `application/power-automate/README.md` に記録する
- 台帳フォルダに `organizerEventsRequest/` と `organizerEvents/` の2つが増える。進行状態の判定は台帳ファイルの有無から導く方式のままで、新しい状態は作らず、候補到着・代替案の各状態の処理の中で開催者の予定の依頼と待ちを行う
- 開催者の予定のみ重なる枠がある依頼では、選択画面の提示までに開催者の予定の往復(候補の待ちと同じ上限)が1回増える。候補が0件のときは代替案2の待ちと同時に待つ
- 代替案1の定義は「仮の予定が入っている参加者が1人以上いる枠」になり、開催者だけが仮の枠は代替案1ではなく開催者の予定のみ重なる枠として示す
- 仕様承認PRの前に実機で確かめること(tasks.md の実機確認E8・E9)
  - 空き時間の探索が、開催者の空き状況が「予約済み」の枠を返すか。返さなければ、実際に示されるのは「仮」の枠だけになるが、仕様は「空き」以外のすべてを対象にしたまま変えない
  - 「カレンダー ビューの取得 (V3)」で開催者自身の既定カレンダーから件名・開始と終了・`showAs`・`sensitivity` が取れ、繰り返し予定が回ごとに返り、往復が待ち上限に収まるか
- 将来この判断を見直す場合の再検討先。**同じ調査を繰り返さないこと**
  - 参加者の予定の件名を扱う案は、参加者側のカレンダー共有に依存する前提が変わらない限り再検討しない
  - 探索の応答に件名が含まれるようになった場合(コネクタ側の仕様に依存)は、開催者予定フローを廃止して応答から取る案を検討する
