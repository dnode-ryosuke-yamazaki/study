# 空き時間からの会議候補提示とTeams会議の自動作成 タスク分解

> TDDで進める。各タスクは 🔴 Red(失敗するテストを書く) → 🟢 Green(最小実装) → 🔵 Refactor の順で進める。

テストは `apps/meeting-setup-automation/application/tests/` に unittest で書き、`python3 -m unittest discover -s tests -t .` で実行する(teams-transcript-fetcher・meeting-minutes-generatorと同じ)。OneDriveのフォルダ・メンバー名簿・現在時刻はテストでは一時ディレクトリと固定値に差し替える。Power Automateフローとブラウザは自動テストから動かさない(該当項目は[実機確認](#仕様承認pr前に行う実機確認)と[動作確認チェックリスト](#動作確認チェックリスト)で担保する)。

## 仕様承認PR前に行う実機確認

requirements.mdの成立条件のうち、Power AutomateとOneDrive・ブラウザの実際の振る舞いに依存する5点は未検証である。**この5点をすべて確認してから仕様承認PRを出す。** 確認は Power Automate の画面と使い捨てのファイルで行い、**リポジトリのコード(テストを含む)は書かない**(study CLAUDE.mdの「仕様承認PRがマージされるまで実装に着手しない」に従う)。使い捨てのフロー・ファイルはコミットしない。

- [ ] **E1. 「会議の時間を検索 (V2)」が候補を返す**
  - 手順: Office 365 Outlookコネクタの「会議の時間を検索 (V2)」を単発のフローで実行する。必須出席者に自分と社内メンバー1名、所要時間60分、期間を当日から2週間、活動の範囲を勤務時間、出席可能率の下限を100%、最大件数を20で試す
  - 合格条件: 枠が1件以上返り、枠ごとに開始・終了と出席者ごとの空き状況が取れること。枠が0件のときはその理由が取れること
  - だめだった場合: 候補探索の手段が無くなる。requirements.mdの候補の提示から作り直す(別コネクタ・別アクションの調査へ戻る)
  - 対応: [requirements.md#候補の提示](requirements.md#候補の提示) [1] / [design.md#power-automateフローの役割](design.md#power-automateフローの役割)

- [ ] **E2. `POST /me/events` に出席者を含めて作成できる**
  - 手順: Office 365 Outlookコネクタのパススルー(「HTTP 要求を送信します」)で `POST /me/events` を呼ぶ。件名・開始・終了・必須出席者1名以上・オンライン会議として作る指定を入れる
  - 合格条件: 会議が作成され、出席者に招待が届き、応答から参加URLが取れること。物理会議室が押さえられていないこと。開催者が自分になっていること
  - だめだった場合: 会議作成の手段が無くなる。requirements.mdの会議の作成から作り直す
  - 対応: [requirements.md#会議の作成内容](requirements.md#会議の作成内容) [1][2][3][4]

- [ ] **E3. 自前のアジェンダ本文を指定しても会議オプション画面の直リンクが応答の会議本文に残る**
  - 手順: E2と同じ呼び出しで、会議本文に自前のアジェンダのHTMLを指定する。応答の会議本文をそのまま確認し、あわせて作成後の会議を再取得した本文も確認する
  - 合格条件: 会議本文の中に会議オプション画面のURLが含まれ、URLとして機械的に取り出せること
  - だめだった場合: **手動での録画・ファシリテーター有効化の前提が崩れる。** 本文を指定しない作成に切り替えるか、直リンクを本文以外から得る経路を探すかの方針判断が必要になるため、仕様承認へ進まずrequirements.mdの録画とファシリテーターの設定を見直す
  - 対応: [requirements.md#録画とファシリテーターの設定](requirements.md#録画とファシリテーターの設定) [2][3]

- [ ] **E4. 会議オプション画面でオンにしたトグルがサーバー側に保存される**
  - 手順: E2で作成した会議の会議オプション画面を直リンクから開き、録画の自動開始とファシリテーターのトグルをオンにして保存する。画面を閉じて開き直し、別の経路(Teamsのカレンダー)からも開いて確認する
  - 合格条件: 開き直してもオンのままであること
  - だめだった場合: 自動作成した会議では手動での有効化もできないことになる。会議設定の自動化そのものの価値が下がるため、スコープの見直しをユーザーに相談する
  - 対応: [requirements.md#録画とファシリテーターの設定](requirements.md#録画とファシリテーターの設定) [1]

- [ ] **E5. OneDrive上のHTMLがビューア形式URLで開き、クリップボードコピーが動く**
  - 手順: ラジオボタンとコピーボタン(押した瞬間の同期コピー → クリップボードの機能 → 入力欄の自動選択の3段構え)を持つ使い捨てのHTMLを `auto/meetingSetting/html/` に置き、ビューア形式URLで開く
  - 合格条件: ブラウザ内で表示されること(ダウンロードにならないこと)。ラジオボタンが操作できること。コピーボタンでクリップボードに入るか、少なくとも入力欄が選択状態になって手作業でコピーできること
  - だめだった場合: 選択画面の置き場所または選択結果の受け渡し方法を変える。requirements.mdの候補の提示・候補の選択を見直す
  - 対応: [requirements.md#候補の提示](requirements.md#候補の提示) [6] / [requirements.md#候補の選択](requirements.md#候補の選択) [1][2]

確認した結果(合格・不合格と実際の値)は仕様承認PRの説明に書く。不合格が1つでもあれば、該当するrequirements.mdを直してから仕様承認に進む。

## タスク一覧

### 1. 設定モジュール(config.py)

- 台帳フォルダ(`auto/meetingSetting/` 配下の request / candidates / selection / result / html)・通知フォルダ(`auto/teamsNotice/meetingSetting/`)・作業フォルダ(`~/Library/Application Support/meeting-setup-automation/`)のパスを持つこと
- 環境変数で台帳のルートと作業フォルダを差し替えられること(テスト用。teams-transcript-fetcherの `TRANSCRIPT_FETCHER_WORK_DIR` と同じ方式)
- 待ち上限(5分)・確認間隔(5秒)・同期の猶予(30秒)を持ち、環境変数で上書きできること
- 既定の探索条件(期間2週間・時間帯9時30分から17時30分・候補5件・出席可能率の下限100%・フローに返させる最大件数)を持つこと
- 候補選択画面のビューアURLとサーバー相対パスを持ち、環境変数で上書きできること(sprint-review-generatorと同じ `output_web_viewer` / `output_web_dir` の考え方)
- 対応: [design.md#関連するファイル抜粋](design.md#関連するファイル抜粋) / [requirements.md#候補探索の既定条件](requirements.md#候補探索の既定条件) [1]

### 2. 日本の祝日の判定(holidays_jp.py)

- 指定した日が土曜・日曜・祝日のいずれかであるかを判定できること
- 祝日は固定テーブルで持ち、標準ライブラリだけで完結すること(新しいOSSを追加しない)
- テーブルの範囲外の年を渡された場合は、範囲外であることが分かる形で扱うこと(黙って平日と判定しない)
- `retro-check` の `holidays_jp.py` と同じ出典・同じ更新方法をモジュールの先頭に書くこと
- 対応: [requirements.md#候補探索の既定条件](requirements.md#候補探索の既定条件) [2]

### 3. メンバー名簿の読み込みと名前の解決(roster.py)

- 作業フォルダの `roster.json` を読み、名前からメールアドレスへの対応表を得ること
- 名簿が無い場合・読めない場合は、解決を試みずその旨を返すこと
- 名前を1件解決できること
- 名簿に登録がない名前を解決できないものとして返すこと
- 名簿の中に同じ名前が複数ある場合も解決できないものとして返すこと
- 複数の名前をまとめて解決し、解決できなかった名前の一覧を返すこと(1件でもあれば全体を失敗として扱う)
- 対応: [requirements.md#会議設定の依頼](requirements.md#会議設定の依頼) [3][4] / [requirements.md#参加者の解決](requirements.md#参加者の解決) [1][2][3]

### 4. 依頼IDの生成と依頼の書き出し(request.py)

- 依頼IDを「年月日と時分秒+乱数4文字」の形で生成すること。同じ時刻に連続して生成しても重ならないこと
- 依頼の内容(依頼ID・試行番号・件名・所要時間・必須出席者・探索の指示・絞り込みの条件)を組み立てること
- 探索条件の指定がない項目に既定値を使い、指定がある項目はそれを優先すること
- 日時をISO 8601形式の日本時間のオフセット付きで書くこと
- 依頼フォルダへ `request-<依頼ID>-a<試行番号>.json` の名前で書き出すこと
- 書き出しに失敗した場合は例外を投げず、失敗した旨を呼び出し元に返すこと
- 対応: [requirements.md#会議設定の依頼](requirements.md#会議設定の依頼) [1][2][5] / [requirements.md#台帳ファイルの扱い](requirements.md#台帳ファイルの扱い) [1][2]

### 5. 入力値のバリデーション(request.py)

- 所要時間が5分未満、または時間帯の長さを超える場合を不正として返すこと
- 探索期間の開始が終了より後、または開始が当日より前の場合を不正として返すこと
- 時間帯の開始が終了以降、またはその差が所要時間未満の場合を不正として返すこと
- 候補件数が0以下の場合を不正として返すこと
- 不正があった場合は依頼を書き出さないこと
- 対応: [design.md#バリデーション](design.md#バリデーション)

### 6. 進行状態の判定(progress.py)

- 依頼IDから、その依頼の台帳ファイルの有無を調べて進行状態(依頼済み・候補到着・選択済み・作成済み)を返すこと
- フォルダの一覧を取らず、依頼IDから決まるファイル名の有無だけで判定すること(同期フォルダは一覧の取得が許可されないことがあるため)
- その依頼IDの依頼ファイルのうち最も大きい試行番号を今の試行として返すこと
- 依頼ファイルが1つも無い依頼IDを、存在しない依頼として返すこと
- 対応: [requirements.md#往復の待ち合わせ](requirements.md#往復の待ち合わせ) [3] / [design.md#状態管理](design.md#状態管理)

### 7. 台帳ファイルの到着待ち(wait_for.py)

- 指定したファイルが現れるまで一定間隔で確認し、現れたら内容を返すこと
- ファイルはあるが想定の形式として読み取れない場合は、書き込み中とみなして待ち続けること
- 待ち上限を超えたら打ち切り、打ち切ったことが分かる形で返すこと
- 確認のたびに、待っている対象と経過時間を進捗として出力すること
- 上限・間隔を引数で受け取れること(テストでは短い値を使う)
- 対応: [requirements.md#往復の待ち合わせ](requirements.md#往復の待ち合わせ) [1][2][4] / [requirements.md#往復の待ち時間の上限](requirements.md#往復の待ち時間の上限) [1][2]

### 8. 候補の絞り込み(candidates.py)

- 候補ファイルを読み、枠の一覧・枠が無かった理由・失敗理由を取り出せること
- 失敗理由が入っている候補ファイルを、絞り込みへ進まない結果として返すこと
- 土曜・日曜・祝日にかかる枠を除くこと
- 開始から終了までが指定の時間帯に収まらない枠を除くこと
- 参加者全員が空いていない枠を除くこと。全員空きを求めない指示がある場合はこの除外を行わないこと
- 開始時刻の早い順に並べ、既に採用した枠と時間が重なる枠を除くこと
- 上限件数まで採用し、同じ日に複数の枠が残ってもそのまま採用すること
- 除外の内訳(理由ごとの件数)を返すこと(ログ用)
- 対応: [requirements.md#候補の提示](requirements.md#候補の提示) [1] / [requirements.md#候補探索の既定条件](requirements.md#候補探索の既定条件) [2][3][4]

### 9. 再探索の条件の拡張(request.py)

- 試行番号1の依頼から、時間帯を9時30分から18時30分に広げた試行番号2の依頼を作れること
- 試行番号2の依頼から、期間を当日から3週間に広げた試行番号3の依頼を作れること(時間帯は18時30分までのまま)
- 試行番号3で0件だった場合は次の依頼を作らず、試した3通りの条件を返すこと
- 拡張は依頼1件につき2回までであること
- 対応: [requirements.md#候補の提示](requirements.md#候補の提示) [7] / [requirements.md#候補が0件のときの探索条件の拡張](requirements.md#候補が0件のときの探索条件の拡張) [1][2][3][4]

### 10. 候補選択画面の生成(select_html.py)

- 採用した枠から静的HTMLを組み立て、`select-<依頼ID>.html` の名前でHTMLフォルダへ書き出すこと。同じ名前がある場合は上書きすること
- ヘッダーに件名・所要時間・参加者の人数・探索した条件の要約を含めること
- 候補1件につき1枚のカードを縦に並べ、候補番号・日付・曜日・開始と終了の時刻・参加者の空き状況を含めること
- 空き状況は「全員空き」または空いていない人数だけを表示し、予定の件名・場所・参加者を含めないこと
- ラジオボタンで1つだけ選べること(同じ名前のラジオボタン群になっていること)
- 選んだ候補の1行(目印の語・依頼ID・試行番号・候補番号・開始時刻・終了時刻)を組み立てるスクリプトを含めること
- コピーの3段構え(押した瞬間の同期コピー・クリップボードの機能の有無を確かめた呼び出し・入力欄の自動選択)がすべて含まれること
- 件名・参加者名をHTMLとして解釈されない形で埋め込むこと
- 生成物に含まれるJavaScriptが構文として成立していること(f文字列の改行でJSの文字列が壊れる不具合を防ぐ)
- 書き出した後に読み戻して内容が一致すること、続けて読んだときにサイズが変わらないことを確認できること
- 対応: [requirements.md#候補の提示](requirements.md#候補の提示) [2][3][4] / [requirements.md#候補の選択](requirements.md#候補の選択) [1][2] / [design.md#画面設計](design.md#画面設計)

### 11. ビューア形式URLの組み立て(select_html.py)

- 設定のビューアURLとサーバー相対パス、HTMLのファイル名から、ファイルビューアで開く形式のURLを組み立てること
- ビューアURLに付随するクエリを落とすこと
- サーバー相対パスは一度デコードしてからエンコードすること(エンコード済みの値を二重にエンコードしない)
- パスの前後のスラッシュの有無を吸収すること
- 設定が欠けている場合はURLを組み立てず、その旨を返すこと
- 対応: [requirements.md#候補の提示](requirements.md#候補の提示) [5][6]

### 12. 貼られた選択結果の読み取りと書き出し(selection.py)

- 貼られた文字列から、目印の語・依頼ID・試行番号・候補番号・開始時刻・終了時刻を読み取れること
- 前後に余分な文字がある場合でも、目印の語を起点に読み取れること
- 目印の語がない・項目が欠けている場合は、選択結果を書き出さずに読み取れなかったことを返すこと
- 読み取った依頼IDと試行番号の候補ファイルを開き、候補番号の枠があり開始時刻・終了時刻が一致することを確認すること。一致しない場合は書き出さないこと
- その依頼IDの選択結果ファイルが既にある場合は書き出さないこと
- その依頼IDの作成結果ファイルが既にある場合は書き出さず、作成済みとして返すこと
- 選択結果を `selection-<依頼ID>.json` の名前で書き出し、件名・開始・終了・必須出席者・会議本文・オンライン会議として作る指定を含めること。物理会議室を含めないこと
- 対応: [requirements.md#候補の選択](requirements.md#候補の選択) [3][4][5] / [requirements.md#会議の作成](requirements.md#会議の作成) [1][4] / [requirements.md#会議の作成内容](requirements.md#会議の作成内容) [2][3]

### 13. アジェンダの整形(selection.py)

- チャットで受け取ったアジェンダのテキストを、見出しと箇条書きのHTMLに整形すること
- 箇条書きの記号(`-`・`・`・番号)を項目として扱うこと
- アジェンダが空の場合は本文を空にせず、アジェンダが無いことが分かる本文にすること
- アジェンダに含まれるHTMLとして解釈されうる文字をエスケープすること
- 対応: [requirements.md#会議の作成](requirements.md#会議の作成) [2]

### 14. 作成結果の読み取りと直リンクの取り出し(result.py)

- 作成結果ファイルから、会議の識別子・件名・開始・終了・出席者・参加URL・会議本文を取り出せること
- 失敗理由が入っている作成結果を、失敗として返すこと
- 会議本文から会議オプション画面のURLを取り出せること
- URLが複数見つかる場合は最初のものを使うこと
- 会議本文にそれらしいURLが無い場合は、失敗とせず「取り出せなかった」として返すこと
- 対応: [requirements.md#会議の作成](requirements.md#会議の作成) [3] / [requirements.md#録画とファシリテーターの設定](requirements.md#録画とファシリテーターの設定) [2]

### 15. 通知文の組み立てと書き出し(notify.py)

- 選択画面の通知として、件名・候補件数・選択画面のURLと、開けない場合は数十秒待って再読込する旨を含む文を組み立てること
- 完了の通知として、会議の日時・出席者・参加URL・会議オプション画面の直リンクと、録画とファシリテーターは直リンクから手動で有効化する必要がある旨を含む文を組み立てること
- 直リンクが取り出せなかった場合は、その旨とTeamsのカレンダーから会議オプションを開く手順を含めること
- 通知フォルダへ `meeting-<書き出し時刻>.txt` の一意な名前で書き出すこと。通知フォルダが台帳のフォルダと別であること
- 書き出しに失敗しても例外を投げず、失敗した旨を返すこと(チャットへの表示で処理を続ける)
- HTTPで直接投稿する経路を持たないこと(投稿はteams-post経由のファイル書き出しだけ)
- 対応: [requirements.md#完了の通知](requirements.md#完了の通知) [1][2] / [requirements.md#通知](requirements.md#通知) [1][2][3] / [requirements.md#台帳ファイルの扱い](requirements.md#台帳ファイルの扱い) [4]

### 16. ログ出力(logging)

- 進捗と結果を標準出力に出し、あわせて作業フォルダのログファイルへ追記すること(5世代でローテーション)
- design.mdのログ表のタイミングでログを出すこと
- メールアドレス・アジェンダ本文・参加URL・会議本文をログに出さないこと
- 対応: [design.md#ログ](design.md#ログ) / [design.md#セキュリティ](design.md#セキュリティ)

### 17. 台帳フォルダの取り扱いの通し確認(結合テスト)

- 一時ディレクトリを台帳のルートに差し替えた状態で、依頼の書き出し → 候補ファイルを置く → 絞り込み → 選択画面の書き出し → 選択結果の書き出し → 作成結果ファイルを置く → 完了の通知、までを通して動かせること
- 途中で打ち切っても、依頼IDを渡した再開でその続きから進むこと
- 到達した依頼の台帳ファイルが1つも削除されていないこと
- Skillが書くファイルとフローが書くファイルが同じパスに重ならないこと
- 依頼IDが異なる2件を並べても、互いのファイルを取り違えないこと
- 対応: [requirements.md#往復の待ち合わせ](requirements.md#往復の待ち合わせ) [3] / [requirements.md#台帳ファイルの扱い](requirements.md#台帳ファイルの扱い) [1][3] / [requirements.md#非機能要件](requirements.md#非機能要件) [1]
