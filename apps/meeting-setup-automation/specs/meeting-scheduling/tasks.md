# 空き時間からの会議候補提示とTeams会議の自動作成 タスク分解

> TDDで進める。各タスクは 🔴 Red(失敗するテストを書く) → 🟢 Green(最小実装) → 🔵 Refactor の順で進める。

テストは `apps/meeting-setup-automation/application/tests/` に unittest で書き、`python3 -m unittest discover -s tests -t .` で実行する(teams-transcript-fetcher・meeting-minutes-generatorと同じ)。OneDriveのフォルダ・メンバー名簿・現在時刻はテストでは一時ディレクトリと固定値に差し替える。Power Automateフローとブラウザは自動テストから動かさない(該当項目は[実機確認](#仕様承認pr前に行う実機確認)と[動作確認チェックリスト](#動作確認チェックリスト)で担保する)。

## 仕様承認PR前に行う実機確認

requirements.mdの成立条件のうち、Power AutomateとOneDrive・ブラウザの実際の振る舞いに依存する7点を、仕様承認PRを出す前に確認する。**7点はすべて合格しており、実測値と判明した制約は仕様承認PRの説明にある。** 確認は Power Automate の画面と使い捨てのファイルで行い、**リポジトリのコード(テストを含む)は書かない**(study CLAUDE.mdの「仕様承認PRがマージされるまで実装に着手しない」に従う)。使い捨てのフロー・ファイルはコミットしない。

- [x] **E1. 「会議の時間を検索 (V2)」が候補を返し、依頼から候補が届くまでの往復時間が待ち上限に収まる**
  - 手順: Office 365 Outlookコネクタの「会議の時間を検索 (V2)」を、依頼フォルダのファイル作成をトリガーとするフローから実行する。必須出席者に自分と社内メンバー1名、所要時間60分、期間を当日から2週間、出席可能率の下限を100%、最大件数を20で試し、結果を `auto/meetingSetting/candidates/` へ書き出す。使い捨ての依頼ファイルを置いた時刻と、候補ファイルがローカルの同期フォルダに現れた時刻を記録する
  - 合格条件: 枠が1件以上返り、枠ごとに開始・終了と出席者ごとの空き状況が取れること。枠が0件のときはその理由が取れること。**依頼の書き出しから候補ファイルがローカルに現れるまでの往復時間が測れること**(値そのものは合否を分けない。上限を決めるための入力として記録する)
  - だめだった場合: 候補が返らないなら候補探索の手段が無くなるため、requirements.mdの候補の提示から作り直す(別コネクタ・別アクションの調査へ戻る)
  - 対応: [requirements.md#候補の提示](requirements.md#候補の提示) [1] / [requirements.md#往復の待ち時間の上限](requirements.md#往復の待ち時間の上限) [1][3] / [design.md#power-automateフローの役割](design.md#power-automateフローの役割)

- [x] **E2. `POST /me/events` に出席者を含めて作成できる**
  - 手順: Office 365 Outlookコネクタのパススルー(「HTTP 要求を送信します」)で `POST /me/events` を呼ぶ。件名・開始・終了・必須出席者1名以上・オンライン会議として作る指定を入れる。往復時間を測るため、この呼び出しは**選択結果フォルダのファイル作成をトリガーとするフロー**から行い、応答を `auto/meetingSetting/result/` へ書き出す構成にする。使い捨ての選択結果ファイルを置いた時刻と、作成結果ファイルがローカルの同期フォルダに現れた時刻を記録する
  - 合格条件: 会議が作成され、出席者に招待が届き、応答から参加URLが取れること。物理会議室が押さえられていないこと。開催者が自分になっていること。あわせて、選択結果の書き出しから作成結果がローカルに現れるまでの往復時間を記録すること(値そのものは合否を分けない。作成結果の待ちの上限を決めるための入力にする)
  - だめだった場合: 会議が作成できないなら会議作成の手段が無くなるため、requirements.mdの会議の作成から作り直す
  - 対応: [requirements.md#会議の作成内容](requirements.md#会議の作成内容) [1][2][3][4]

- [x] **E3. 自前のアジェンダ本文を指定しても会議オプション画面の直リンクが応答の会議本文に残る**
  - 手順: E2と同じ呼び出しで、会議本文に自前のアジェンダのHTMLを指定する。応答の会議本文をそのまま確認し、あわせて作成後の会議を再取得した本文も確認する
  - 合格条件: 会議本文の中に会議オプション画面のURLが含まれ、URLとして機械的に取り出せること
  - だめだった場合: **手動での録画・ファシリテーター有効化の前提が崩れる。** 本文を指定しない作成に切り替えるか、直リンクを本文以外から得る経路を探すかの方針判断が必要になるため、仕様承認へ進まずrequirements.mdの録画とファシリテーターの設定を見直す
  - 対応: [requirements.md#録画とファシリテーターの設定](requirements.md#録画とファシリテーターの設定) [2][3]

- [x] **E4. 会議オプション画面でオンにしたトグルがサーバー側に保存される**
  - 手順: E2で作成した会議の会議オプション画面を直リンクから開き、録画の自動開始とファシリテーターのトグルをオンにして保存する。画面を閉じて開き直し、別の経路(Teamsのカレンダー)からも開いて確認する
  - 合格条件: 開き直してもオンのままであること
  - だめだった場合: 自動作成した会議では手動での有効化もできないことになる。会議設定の自動化そのものの価値が下がるため、スコープの見直しをユーザーに相談する
  - 対応: [requirements.md#録画とファシリテーターの設定](requirements.md#録画とファシリテーターの設定) [1]

- [x] **E5. OneDrive上のHTMLがビューア形式URLで開き、クリップボードコピーが動く**
  - 手順: ラジオボタンとコピーボタン(押した瞬間の同期コピー → クリップボードの機能 → 入力欄の自動選択の3段構え)を持つ使い捨てのHTMLを `auto/meetingSetting/html/` に置き、ビューア形式URLで開く
  - 合格条件: ブラウザ内で表示されること(ダウンロードにならないこと)。ラジオボタンが操作できること。コピーボタンでクリップボードに入るか、少なくとも入力欄が選択状態になって手作業でコピーできること
  - だめだった場合: 選択画面の置き場所または選択結果の受け渡し方法を変える。requirements.mdの候補の提示・候補の選択を見直す
  - 対応: [requirements.md#候補の提示](requirements.md#候補の提示) [6] / [requirements.md#候補の選択](requirements.md#候補の選択) [1][2]

- [x] **E6. Power Automateが書いてOneDriveが同期で下ろしたファイルを、Skillと同じ実行経路から読める**
  - 手順: E1でフローが書き出した候補ファイルを、Skillを動かすのと同じ実行経路(このMac上のチャットセッション)からフルパスで開いて読む。フォルダの一覧は取らず、ファイル名を直接指定して読む
  - 合格条件: 自分が書いたのではないファイルの中身が読めること。読めるようになるまでの時間がE1で測った所要時間に収まること
  - だめだった場合: **待ち合わせの方式そのものが成り立たない。** 同期フォルダの項目ごとの許可は操作単位でばらつくため、台帳の置き場所か受け渡しの経路を変える必要がある。requirements.mdの往復の待ち合わせ・台帳ファイルの扱いから見直す
  - 対応: [requirements.md#往復の待ち合わせ](requirements.md#往復の待ち合わせ) [1] / [requirements.md#台帳ファイルの扱い](requirements.md#台帳ファイルの扱い) [1] / [design.md#往復の待ち合わせと打ち切り](design.md#往復の待ち合わせと打ち切り)

- [x] **E7. 仮の予定の件名が取得できる**
  - 手順: Office 365 Outlookコネクタの「予定表の取得 (V2)」でカレンダーの一覧を取り、共有されている参加者のカレンダーを選んで「イベントの取得 (V4)」を実行する
  - 合格条件: 他人のカレンダーの予定について、件名・空き状況・非公開かどうかが取れること
  - だめだった場合: 代替案1で件名を示す手段が無くなる。requirements.mdの候補が0件のときの代替案の提示[2]を「件名は示さず、仮の予定を持つ参加者だけを示す」に見直す
  - 対応: [requirements.md#候補が0件のときの代替案の提示](requirements.md#候補が0件のときの代替案の提示) [2][3] / [design.md#power-automateフローの役割](design.md#power-automateフローの役割)

不合格があった場合は、該当するrequirements.mdを直してから仕様承認に進む。

## タスク一覧

### 1. 設定モジュール(config.py)

- 台帳フォルダ(`auto/meetingSetting/` 配下の request / candidates / detailRequest / detail / selection / result / html)・通知フォルダ(`auto/teamsNotice/meetingSetting/`)・作業フォルダ(`~/Library/Application Support/meeting-setup-automation/`)のパスを持つこと
- 環境変数で台帳のルートと作業フォルダを差し替えられること(テスト用。teams-transcript-fetcherの `TRANSCRIPT_FETCHER_WORK_DIR` と同じ方式)
- 候補の待ちの上限(5分)・予定詳細の待ちの上限(5分)・作成結果の待ちの上限(5分)・確認間隔(5秒)・同期の猶予(30秒)を持ち、それぞれ環境変数で上書きできること。3つの上限は別々の設定値にすること(実測の結果、別の値になりうるため)
- 既定の探索条件(期間2週間・時間帯9時30分から17時30分・候補5件・出席可能率の下限100%・フローに返させる最大件数50件)を持つこと
- 代替案の条件(期間3週間・時間帯9時30分から18時30分)と、予定詳細を取る枠の刻み(30分)を持つこと
- 候補選択画面のビューアURLとサーバー相対パスを持ち、環境変数で上書きできること(sprint-review-generatorと同じ `output_web_viewer` / `output_web_dir` の考え方)
- 対応: [design.md#関連するファイル抜粋](design.md#関連するファイル抜粋) / [requirements.md#候補探索の既定条件](requirements.md#候補探索の既定条件) [1]

### 2. 日本の祝日の判定(holidays_jp.py)

- 指定した日が土曜・日曜・祝日のいずれかであるかを判定できること
- 祝日は固定テーブルで持ち、標準ライブラリだけで完結すること(新しいOSSを追加しない)
- テーブルの範囲外の年を渡された場合は、範囲外であることが分かる形で扱うこと(黙って平日と判定しない)
- `retro-check` の `holidays_jp.py` と同じ出典・同じ更新方法をモジュールの先頭に書くこと
- 対応: [requirements.md#候補探索の既定条件](requirements.md#候補探索の既定条件) [2]

### 3. メンバー名簿の読み込みと名前の解決(roster.py)

- 作業フォルダの `roster.json` を読み、名前からメールアドレスへの対応表を得ること
- 名簿が無い場合・読めない場合は、解決を試みずその旨を返すこと
- 名前を1件解決できること
- 名簿に登録がない名前を解決できないものとして返すこと
- 名簿の中に同じ名前が複数ある場合も解決できないものとして返すこと
- 名簿に登録されたカレンダーの表示名を、参加者ごとに任意項目として読めること(未登録の場合は空として返すこと)
- 複数の名前をまとめて解決し、解決できなかった名前の一覧を返すこと(1件でもあれば全体を失敗として扱う)
- 対応: [requirements.md#会議設定の依頼](requirements.md#会議設定の依頼) [3][4] / [requirements.md#参加者の解決](requirements.md#参加者の解決) [1][2][3]

### 4. 依頼IDの生成と依頼の書き出し(request.py)

- 依頼IDを「年月日と時分秒+乱数4文字」の形で生成すること。同じ時刻に連続して生成しても重ならないこと
- 依頼の内容(依頼ID・試行番号・件名・所要時間・必須出席者・アジェンダの原文・探索の指示・絞り込みの条件)を組み立てること
- 絞り込みの条件に、時間帯・「対象とする曜日」(既定は月曜から金曜)・「全員空きを求めるかどうか」・提示する候補の上限件数を含めること(再開時に依頼ファイルだけから同じ条件で絞り込めること)。祝日は常に除くため項目として持たないこと
- 全員空きを求めない指示を受けた場合は、絞り込みの条件だけでなく探索の指示の出席可能率の下限も併せて下げること(下限が100%のままだと一部不在の枠がフローから返らない)。下限を100%にしても全員空きにはならないため、厳密な判定はタスク8で行うこと
- 開催者が明示的に指定した項目(期間・時間帯・候補件数・曜日・全員空き)の一覧を依頼に含めること。既定値と同じ値を指定された場合も指定として扱うこと(値の比較では区別できないため)
- 探索条件の指定がない項目に既定値を使い、指定がある項目はそれを優先すること
- 日時をISO 8601形式の日本時間のオフセット付きで書くこと
- 依頼フォルダへ `request-<依頼ID>-a<試行番号>.json` の名前で書き出すこと
- 書き出しに失敗した場合は例外を投げず、失敗した旨を呼び出し元に返すこと
- 対応: [requirements.md#会議設定の依頼](requirements.md#会議設定の依頼) [1][2][5] / [requirements.md#台帳ファイルの扱い](requirements.md#台帳ファイルの扱い) [1][2][5]

### 5. 入力値のバリデーション(request.py)

- 所要時間が5分未満、または時間帯の長さを超える場合を不正として返すこと
- 探索期間の開始が終了より後、または開始が当日より前の場合を不正として返すこと
- 探索期間の終了日が当日から3週間より先の場合を不正として返すこと
- 時間帯の開始が終了以降、またはその差が所要時間未満の場合を不正として返すこと
- 候補件数が0以下の場合を不正として返すこと
- 参加者の人数では不正としないこと(人数の上限を設けない)
- アジェンダの指定が無い場合は不正とせず、そのまま受け付けること
- 不正があった場合は依頼を書き出さず、満たしていない項目を返すこと
- 対応: [requirements.md#依頼内容の受け付け条件](requirements.md#依頼内容の受け付け条件) [1][2][3][4][5][6][7][8] / [design.md#バリデーション](design.md#バリデーション)

### 6. 進行状態の判定(progress.py)

- 依頼IDから、その依頼の台帳ファイルの有無と中身を調べて進行状態(依頼済み・候補到着・代替案の提示中・代替案の提示済み・選択済み・作成失敗・作成済み)を返すこと
- 作成結果に失敗理由が入っている場合を「作成失敗」として返し、「作成済み」と取り違えないこと
- 代替案の台帳(予定詳細の依頼・試行番号2の依頼)があるかどうかで「候補到着」と代替案の2状態を切り分けること。求めた結果が揃っていなければ「代替案の提示中」、揃っていれば「代替案の提示済み」を返すこと
- **判定は design.md の状態管理の表の順(作成済み → 作成失敗 → 選択済み → 代替案の提示済み → 代替案の提示中 → 候補到着 → 依頼済み)に当てはめ、最初に一致した状態を返すこと。** 選択結果があれば代替案の2状態を返さないこと(予定詳細ファイルは選択後に削除されるため、順序を守らないと来ないファイルを待ち続ける)
- 状態の判定に依頼ファイルの最大の試行番号を使わないこと(代替案2の依頼を書いた直後に「依頼済み」へ戻ってしまう)
- フォルダの一覧を取らず、依頼IDから決まるファイル名の有無だけで判定すること(同期フォルダは一覧の取得が許可されないことがあるため)
- その依頼IDの依頼ファイルのうち最も大きい試行番号を今の試行として返し、選択結果ファイルのうち最も大きい再試行番号を今の再試行として返すこと
- 依頼ファイルが1つも無い依頼IDを、存在しない依頼として返すこと
- 対応: [requirements.md#往復の待ち合わせ](requirements.md#往復の待ち合わせ) [3] / [design.md#状態管理](design.md#状態管理)

### 7. 台帳ファイルの到着待ち(wait_for.py)

- 指定したファイルが現れるまで一定間隔で確認し、現れたら内容を返すこと
- ファイルはあるが想定の形式として読み取れない場合は、書き込み中とみなして待ち続けること
- 待ち上限を超えたら打ち切り、打ち切ったことが分かる形で返すこと
- 確認のたびに、待っている対象と経過時間を進捗として出力すること
- 上限・間隔を引数で受け取れること(テストでは短い値を使う)
- 対応: [requirements.md#往復の待ち合わせ](requirements.md#往復の待ち合わせ) [1][2][4] / [requirements.md#往復の待ち時間の上限](requirements.md#往復の待ち時間の上限) [1][2]

### 8. 候補の絞り込み(candidates.py)

- 候補ファイルを読み、枠の一覧・枠が無かった理由・失敗理由を取り出せること
- 失敗理由が入っている候補ファイルを、絞り込みへ進まない結果として返すこと
- **世界標準時で届いた枠の開始・終了を日本時間に変換してから判定すること。** 変換前に日付・曜日・時間帯を判定しないこと(変換を忘れると9時間ずれた枠を採用する)
- 開始から終了までが指定の時間帯に収まらない枠を除くこと
- 祝日にかかる枠を除くこと
- 対象とする曜日の指定がある場合、その曜日以外の枠を除くこと(土曜・日曜も候補になりうること)。指定がない場合は土曜・日曜の枠を除くこと
- 全員空きでない枠を除くこと。全員空きを求めない指示がある場合はこの除外を行わないこと
- **全員空きの判定は、出席者ごとの空き状況のすべてと開催者の空き状況の両方が「空き」であることとすること。** 出席可能率では判定しないこと(下限を100%にしても仮の予定が入った出席者や開催者を含む枠が返る)。開催者の空き状況は出席者の一覧に含まれない別の項目であること
- 仮の予定が入っている状態を空きとみなさないこと
- 開始時刻の早い順に並べ、既に採用した枠と時間が重なる枠を除くこと
- 上限件数まで採用し、同じ日に複数の枠が残ってもそのまま採用すること
- 同じ候補ファイルを、**仮の予定を空きとみなす条件**で絞り直せること(代替案1で、フローへ依頼を出し直さずに使う)
- 絞り直した結果の枠ごとに、仮の予定を持つ参加者の一覧を返すこと(件名を取りに行く対象になる)
- 除外の内訳(理由ごとの件数)を返すこと(ログ用)
- 対応: [requirements.md#候補の提示](requirements.md#候補の提示) [1] / [requirements.md#候補探索の既定条件](requirements.md#候補探索の既定条件) [2][3][4][5] / [requirements.md#候補が0件のときの代替案の提示](requirements.md#候補が0件のときの代替案の提示) [1]

### 9. 候補が0件のときの代替案の組み立て(request.py)

- 既定の絞り込みが0件だったとき、代替案1と代替案2の両方を作れること(片方だけで止めないこと)
- **代替案1では依頼を作らないこと。** 同じ候補ファイルを仮の予定を空きとみなす条件で絞り直すだけにし、探索の依頼を出し直さないこと
- 代替案2として、期間を当日から3週間・時間帯を9時30分から18時30分に広げた試行番号2の依頼を作れること(対象とする曜日は変えないこと)
- **開催者が明示的に指定した項目は広げないこと。** 探索期間が指定されていれば期間を、時間帯が指定されていれば時間帯を既定のままにし、両方が指定されていれば代替案2を作らないこと
- 代替案をすでに提示したかどうかを、予定詳細の依頼ファイルまたは試行番号2の依頼ファイルの有無で判定すること(進行の記録を別に持たないこと)
- 代替案の候補からさらに条件を緩めないこと。両方の代替案とも0件の場合は次の依頼を作らず、試した条件(代替案2を作らなかった場合は既定と代替案1の2通り、作った場合は3通り)と、開催者の指定のため広げなかった項目を返すこと
- 代替案1が0件で、受け取った枠が依頼で要求した最大件数と同数だった場合は、応答が件数で打ち切られている可能性を結果に含めること
- 代替案2の待ちが上限を超えて打ち切られた場合を異常として扱わず、打ち切りとして返すこと(既定の依頼から間を置かずに続くため往復が伸びる)
- **代替案2が得られなかった場合(打ち切り・候補ファイルに失敗理由・依頼の書き出し失敗)も、代替案1の枠の提示を止めないこと。** 得られなかった理由を結果に含めて返すこと
- 代替案2の候補ファイルの失敗理由を、通常の候補ファイルの失敗(その時点で終了する)と区別して扱うこと
- 対応: [requirements.md#候補の提示](requirements.md#候補の提示) [7] / [requirements.md#候補が0件のときの代替案の提示](requirements.md#候補が0件のときの代替案の提示) [1][3][5][6][7] / [requirements.md#往復の待ち時間の上限](requirements.md#往復の待ち時間の上限) [3]

### 10. 予定詳細の依頼と件名の取り出し(detail.py)

- 代替案1で残った枠と、その枠に仮の予定を持つ参加者のうち**名簿にカレンダーの表示名が登録されている参加者**から、予定詳細の依頼を組み立てて `detail-request-<依頼ID>.json` として書き出せること
- 表示名が登録されていない参加者を依頼に含めず、件名が取得できないものとして返すこと
- 取得する範囲を、代替案1で残った枠すべてを含む開始と終了にすること
- 予定詳細ファイルから、参加者ごとの予定(状態・件名・非公開かどうか・開始・終了)を取り出せること
- **世界標準時で届いた予定の開始・終了を日本時間に変換してから枠と突き合わせること**
- 枠と時間が重なる仮の予定だけを選び、枠ごとに「参加者と件名」の一覧を返すこと
- 件名が空で返った参加者と、対象のカレンダーが見つからなかった参加者を、件名が取得できなかったものとして返すこと
- 繰り返し予定として返ってきたものを件名の取得対象にしないこと(回ごとに展開されないため枠と対応付けられない)
- 非公開に設定された予定の件名を返さないこと(非公開であることだけを返すこと)
- 失敗理由が入っている予定詳細ファイルを失敗として返すこと。代替案1の提示そのものは止めず、件名なしで示せること
- 選択結果を書き出した時点で予定詳細ファイルを削除できること(他人の予定の件名を残さない)
- 対応: [requirements.md#候補が0件のときの代替案の提示](requirements.md#候補が0件のときの代替案の提示) [2] / [design.md#セキュリティ](design.md#セキュリティ)

### 11. 候補選択画面の生成(select_html.py)

- 採用した枠から静的HTMLを組み立て、`select-<依頼ID>.html` の名前でHTMLフォルダへ書き出すこと。同じ名前がある場合は上書きすること
- ヘッダーに件名・所要時間・参加者の人数・絞り込みに使った条件の要約を含めること。自動で条件を緩めた場合は緩めた後の値と、緩めたことが分かる表示を含めること(依頼ファイルの値ではなく、実際に絞り込みに使った条件を渡すこと)
- 候補1件につき1枚のカードを縦に並べ、候補番号・日付・曜日・開始と終了の時刻・参加者の空き状況を含めること。候補番号は画面に並べた順の1からの連番であること
- 代替案として提示する場合は、代替案1の枠と代替案2の枠を見出しで分けて並べること。代替案1の枠には仮の予定を持つ参加者の名前と予定の件名を、代替案2の枠には広げた後の期間と時間帯を添えること。件名が取得できなかった参加者と非公開の予定は、件名の代わりにその旨を示すこと
- 空き状況は「全員空き」または空いていない人数だけを表示し、予定の場所・出席者を含めないこと。予定の件名を含めるのは代替案1の枠の仮の予定についてだけとすること
- ラジオボタンで1つだけ選べること(同じ名前のラジオボタン群になっていること)
- 選んだ候補の1行(目印の語・依頼ID・試行番号・候補番号・開始時刻・終了時刻)を組み立てるスクリプトを含めること。時刻は日本時間のオフセット付きで書くこと
- **試行番号はカードごとに、その枠が入っていた候補ファイルの試行番号を埋め込むこと**(代替案1の枠は1、代替案2の枠は2)。画面単位で1つの試行番号を使わないこと(代替案1の枠が突き合わせで弾かれる)
- コピーの3段構え(押した瞬間の同期コピー・クリップボードの機能の有無を確かめた呼び出し・入力欄の自動選択)がすべて含まれること
- 件名・参加者名をHTMLとして解釈されない形で埋め込むこと
- 生成物に含まれるJavaScriptが構文として成立していること(f文字列の改行でJSの文字列が壊れる不具合を防ぐ)
- 書き出した後に読み戻して内容が一致すること、続けて読んだときにサイズが変わらないことを確認できること
- 対応: [requirements.md#候補の提示](requirements.md#候補の提示) [2][3][4] / [requirements.md#候補の選択](requirements.md#候補の選択) [1][2] / [design.md#画面設計](design.md#画面設計)

### 12. ビューア形式URLの組み立て(select_html.py)

### 13. 貼られた選択結果の読み取りと書き出し(selection.py)

- 貼られた文字列から、目印の語・依頼ID・試行番号・候補番号・開始時刻・終了時刻を読み取れること
- 前後に余分な文字がある場合でも、目印の語を起点に読み取れること
- 目印の語がない・項目が欠けている場合は、選択結果を書き出さずに読み取れなかったことを返すこと
- 読み取った依頼IDと試行番号の候補ファイルを開き、貼られた開始時刻・終了時刻と一致する枠が1つ存在することを確認すること。存在しない場合は書き出さないこと
- 代替案を提示した依頼では試行番号1と2の両方の候補ファイルがありうるため、貼られた試行番号のファイルを見ること
- **候補ファイルの枠は世界標準時、貼られた時刻は日本時間なので、時点として比較すること**(文字列で比較すると常に不一致になる)
- 突き合わせに候補番号を使わないこと(候補番号は表示用の連番で、絞り込みを再現しないと枠に対応付けられないため)
- その依頼IDの選択結果ファイルが既にある場合は書き出さないこと
- その依頼IDの作成結果ファイルが既にあり作成に成功している場合は書き出さず、作成済みとして返すこと
- その依頼IDの作成結果ファイルが既にあり失敗している場合は、再試行として書き出せる状態であることを返すこと(自動では書き出さない)
- 再試行として書き出す場合は、再試行番号を1つ増やした `selection-<依頼ID>-r<再試行番号>.json` に前回と同じ内容を書き出すこと
- 選択結果を `selection-<依頼ID>.json` の名前で書き出し、件名・開始・終了・必須出席者・会議本文・オンライン会議として作る指定を含めること。物理会議室を含めないこと
- 対応: [requirements.md#候補の選択](requirements.md#候補の選択) [3][4][5] / [requirements.md#会議の作成](requirements.md#会議の作成) [1][4][5] / [requirements.md#会議の作成内容](requirements.md#会議の作成内容) [2][3]

### 18. コマンドの入口(main.py)

- `submit` / `resume` / `select` / `retry-create` のサブコマンドを持つこと
- `submit --dry-run` が依頼を書き出さずに依頼の内容だけを返すこと(チャットでの確認に使う)
- `resume` が依頼IDだけを受け取り、進行状態の判定に従って続き(候補の待ち・絞り込み・代替案の提示・選択画面と通知、または作成結果の待ちと完了の通知)を進めること
- `resume` が既定の絞り込みで0件だったとき、代替案1の絞り直しと予定詳細の依頼、代替案2の依頼を出し、両方の到着を待って1枚の選択画面にまとめること
- `resume` が**代替案の台帳がある依頼を再開したとき**は、通常の絞り込みへ進まず代替案1と代替案2の両方を絞り直して1枚にまとめ直すこと(試行番号2の候補だけを絞り込んで代替案1の枠を落とさないこと)
- 2つの待ちのうち片方だけが打ち切られた場合も、届いた側の枠で選択画面を作り、届かなかった側を打ち切りとして伝えること
- `resume` の判定が「作成失敗」だった場合は、完了として報告せず、失敗理由と `retry-create` の案内を出して終わること(打ち切り中にフローが失敗の作成結果を書いた場合がこの経路に入る)
- `select` が貼られた選択結果を受け取り、突き合わせ・書き出し・作成結果の待ち・完了の通知まで進めること
- `retry-create` が失敗した作成の再試行を行うこと。失敗した作成結果が無い依頼IDに対しては何もしないこと
- `retry-create` は、その枠に会議が既に作られていないかを確かめる案内を出力に含めること
- 選択画面を書き出した後の同期の猶予待ちを `resume` の中で行うこと
- どのサブコマンドも、進捗と結果を標準出力に出してチャットへそのまま貼れる形にすること
- 対応: [design.md#手順の担い手](design.md#手順の担い手) / [requirements.md#往復の待ち合わせ](requirements.md#往復の待ち合わせ) [3]

### 19. 台帳フォルダの取り扱いの通し確認(結合テスト)

- 一時ディレクトリを台帳のルートに差し替えた状態で、`main.py` のサブコマンド経由で、依頼の書き出し → 候補ファイルを置く → 絞り込み → 選択画面の書き出し → 選択結果の書き出し → 作成結果ファイルを置く → 完了の通知、までを通して動かせること
- 失敗理由の入った作成結果を置いた場合に完了として報告せず、再試行の指示を受けてから再試行番号付きの選択結果を書き出し、その作成結果で完了まで進めること
- 途中で打ち切っても、依頼IDを渡した再開でその続きから進むこと
- 到達した依頼の台帳ファイルが1つも削除されていないこと
- Skillが書くファイルとフローが書くファイルが同じパスに重ならないこと
- 依頼IDが異なる2件を並べても、互いのファイルを取り違えないこと
- 既定の条件では0件になる候補ファイルを置いたとき、代替案1の絞り直しと代替案2の依頼が両方作られ、1枚の選択画面に2つの見出しで並ぶこと
- 代替案1の枠に仮の予定を持つ参加者の件名が添えられ、選択結果を書き出した時点で予定詳細ファイルが削除されること
- 代替案1の枠(試行番号1)を貼った選択結果が突き合わせを通り、代替案2の枠(試行番号2)を貼った場合も通ること
- 予定詳細ファイルを削除した後に同じ依頼IDで再開しても、代替案の待ちに戻らず選択済み以降として扱われること
- 代替案2の依頼を書いた直後の依頼IDを再開したとき、「依頼済み」ではなく「代替案の提示中」として扱われること
- 代替案2の候補が届かないまま代替案1の枠を選んだ依頼を再開したとき、来ない候補を待たず選択済み以降として扱われること
- 代替案の台帳がある依頼を再開したとき、代替案1と代替案2の両方の枠が選択画面に並び直すこと
- 予定詳細だけが届かなかった場合も、代替案1の枠を件名なしで並べたうえで打ち切りとして伝えること
- 代替案2の候補ファイルに失敗理由が入っていた場合も、代替案1の枠を並べたうえでその理由を伝えること(全体を終了しないこと)
- 開催者が期間と時間帯の両方を指定した依頼では代替案2が作られないこと
- 期間を広げた再探索の待ちを打ち切った場合も台帳が残り、依頼IDを指定した再開で続けられること
- 時間帯を緩めて出た候補について、絞り込みを再現しない別プロセス相当の呼び出しでも選択結果の突き合わせが通ること
- 対応: [requirements.md#往復の待ち合わせ](requirements.md#往復の待ち合わせ) [3] / [requirements.md#台帳ファイルの扱い](requirements.md#台帳ファイルの扱い) [1][3] / [requirements.md#非機能要件](requirements.md#非機能要件) [1] / [requirements.md#候補が0件のときの代替案の提示](requirements.md#候補が0件のときの代替案の提示) [1][2][3][7] / [requirements.md#往復の待ち時間の上限](requirements.md#往復の待ち時間の上限) [3]

### 20. Power Automateフロー3本の構築(テスト対象外)

- 探索フロー: 依頼フォルダのファイル作成をトリガーに、依頼の探索の指示を「会議の時間を検索 (V2)」へ渡し、返った枠を候補ファイルとして書き出す。失敗時も失敗理由を入れた候補ファイルを書き出す
- 作成フロー: 選択結果フォルダのファイル作成をトリガーに、選択結果の内容で `POST /me/events` を呼び、応答を作成結果ファイルとして書き出す。失敗時も失敗理由を入れた作成結果ファイルを書き出す
- 予定詳細フロー: 予定詳細の依頼フォルダのファイル作成をトリガーに、「予定表の取得 (V2)」でカレンダーの一覧を取り、指示された表示名に一致するカレンダーだけを対象に「イベントの取得 (V4)」を呼び、応答を予定詳細ファイルとして書き出す。一致するカレンダーが無い参加者はその旨を書き出す。失敗時も失敗理由を入れた予定詳細ファイルを書き出す。**パススルーの「HTTP 要求を送信します」は使わない**(このコネクタでは予定の取得に使えない)
- **3本のいずれも、書き出すファイルの名前は読んだファイルの名前の先頭を置き換えて決める**(探索フローは `request-` を `candidates-` に、作成フローは `selection-` を `result-` に、予定詳細フローは `detail-request-` を `detail-` に)。番号を解釈して名前を組み立てる分岐をフローに持たせない。名前が食い違うとSkillは現れないファイルを待ち上限まで待つことになる
- E1〜E3・E7で確認した実際のアクション名・入力値をそのまま反映する。構築手順と設定内容の記録は次のタスクで行う
- 対応: [requirements.md#依存関係](requirements.md#依存関係) / [design.md#power-automateフローの役割](design.md#power-automateフローの役割)
