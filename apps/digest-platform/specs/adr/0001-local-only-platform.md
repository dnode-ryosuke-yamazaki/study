# 0001. 外部サービスを使わず、このPCだけで完結させる

## ステータス

Accepted (2026-11-05)

## コンテキスト

5つのダイジェストアプリ(ai-dev-digest / news-digest / future-digest / research-digest / trend-digest)は、もともと個人サイト「べんりやつーる」の一部として、次の共通構成で動いていた。

- 記事づくりのバッチは GitHub Actions(日次・週次の cron)。記事JSONは PR → CI → 自動マージで main に入れ、マージを契機に別ワークフローが配信する
- 記事サイトは Next.js の静的エクスポートを Cloudflare Workers で配信
- 読者の付箋(ブックマーク+メモ)と運営者のフィードバックは Supabase(Postgres + RLS)、読者のログインは Supabase Auth の Google OIDC
- 新着の配信と失敗通知は LINE Messaging API(共通の LINE 公式アカウント)
- 要約・判定は Claude Code CLI のヘッドレス実行(`claude -p`)

これを会社支給の Mac で動かし直す。この Mac では、次の制約がある。

- Supabase・Cloudflare・LINE・Google OIDC などの外部 SaaS は使えない(組織のポリシーと、個人サービスのアカウントを業務端末に持ち込まない方針)
- GitHub Actions は会社の GitHub で一部動くが、Anthropic の認証を Actions の Secrets に置けない。記事づくりに要る `claude -p` は運営者のサブスク認証でこの Mac の上でしか動かない
- Claude Code のサンドボックスからは外部ネットワーク・127.0.0.1・`launchctl` に届かない。一方、launchd から起動したプロセスは社内プロキシ経由で外に出られる(CAバンドルの指定が要る)
- Teams への投稿は HTTP の直叩きが DLP で止められ、OneDrive の監視フォルダに置いたファイルを Power Automate が投稿する経路だけが通る(既存の teams-post Skill の方式)

この Mac には、同じ制約の下で動いている既存の自動化(launchd の定期実行・`claude -p` の無人実行・teams-post・毎朝のヘルスチェック・127.0.0.1 の常駐サーバー)が既にあり、その型に乗せられる。

## 決定

外部サービスを1つも使わず、この PC だけで完結させる。元の構成の各要素を次のように置き換える。

| 元の構成 | この PC での置き換え |
|---|---|
| GitHub Actions の cron と PR 自動マージ | launchd の `StartCalendarInterval` で実行係(共通ラッパー)を起動し、記事JSONを直接書く。研究発見・未来予測の再実行は時刻表ではなく実行状態ファイルの試行回数で判定する |
| Cloudflare Workers での配信 | 127.0.0.1 の固定ポートで記事サイトを配信する常駐の配信サーバー(launchd、ログイン時に起動) |
| Supabase + Google OIDC(付箋・フィードバック・ログイン) | 配信サーバーの保存APIを通して `~/Library/Application Support/digest/` に保存する。認証は持たない(読者は本人1人) |
| LINE の配信と失敗通知 | teams-post の投稿先として、新設する自分専用の Digestチャネルに配信スレッド5本(アプリごと)と監視スレッド1本を持ち、Power Automate のフローが各スレッドへ返信として投稿する |
| `workflow_run` イベントと cron 時刻表の照合による失敗判定 | 実行係が終了コード・成功マーカー・生成物の3点で成否を決め、試行回数で「最後のやり直しか」を判定する。毎朝のヘルスチェックに最終成功時刻を加えて無言停止の保険にする |

あわせて、実装言語と置き場所を次のとおりにする。

- アプリの画面と選定・判定のロジックは TypeScript のまま使う(元の純粋関数と仕様書・タスク一覧が TypeScript 前提で、移植すると仕様との対応がずれる)。外側の実行係・Claude の起動・Teams 投稿・CAバンドルは既存の shell / Python の部品を呼ぶ
- 記事サイトは Next.js の静的エクスポートを維持し、`file://` で直接開く方式は採らない(静的エクスポートの成果物は `/_next/static/...` の絶対パスとディレクトリ URL を前提にしており、直接開くと CSS・JS・リンクが解決されない)
- 置き場所は study リポジトリの `apps/digest-platform/`(共通基盤)と `apps/<アプリ名>/`(5本)。記事JSONと情報源の設定ファイルは git で管理し、実行状態ファイル・読者データ・観測ログは `~/Library/Application Support/digest/` に置く
- 実行時刻は起床後の朝に寄せる(深夜に置くと Mac が閉じていて復帰時にまとめて動く)。土曜・日曜の配信は、定時の Teams 投稿を土日祝に止める共通ルールの例外にする(編の分け方が曜日に紐づいているため)

## 検討した選択肢

| 選択肢 | 利点 | 欠点・リスク | 結果 |
|---|---|---|---|
| 元の構成のまま外部サービスを使う | 改修が最小 | この Mac では Supabase・Cloudflare・LINE・Google OIDC が使えず、そもそも成立しない | 棄却 |
| GitHub Actions だけ残し、配信・保存・通知をローカルにする | 定期実行の仕組みを作らなくてよい | Actions の上で `claude -p` を動かせない(Anthropic の認証を Secrets に置けない)。記事づくりの本体が動かないので残す意味がない | 棄却 |
| 全部 Python に書き直す | この Mac の既存の自動化と言語が揃う | 元の純粋関数(5アプリで約1万行)の移植と、TypeScript 前提の仕様書・タスク一覧との対応のずれが重い。テストも作り直しになる | 棄却 |
| 記事サイトを Python 生成の単純な HTML にする | 配信サーバーが静的ファイルだけになり Node が要らない | 元の画面(約100本の React 部品: 図解・付箋欄・ページ送り)を捨てることになる | 棄却 |
| 付箋・フィードバックをブラウザの localStorage に置く | 保存APIが要らない | 配信元ごとに別のデータになり、月次見直しのバッチが読めない。書き出しの手間が要る | 棄却 |
| 付箋機能そのものを廃止する | 保存の仕組みが丸ごと不要 | 読み返しとフィードバックが月次見直しの材料になっている | 棄却 |
| 新着通知を既存の投稿先(夜間バッチ・監視通知)に相乗りさせる | フローの追加が不要 | 5アプリの記事と障害の通知が1か所に混ざって追えない | 棄却 |
| 新設の Digestチャネルに配信スレッド5本と監視スレッド1本(採用) | アプリごとに記事を追え、障害も分かれる | 投稿先6つ(サブフォルダ6つ・フロー6本)の手元作業。スレッドのメッセージIDを控えて固定する | 採用 |

## 影響

- 読者は運営者本人1人になる。ログイン画面・運営者判定・RLS に相当する分岐はすべて無くなり、配信サーバーは 127.0.0.1 だけで待ち受ける
- 投稿先6つの設定(サブフォルダ・Power Automate フロー・スレッドのメッセージID)は運営者の手元作業。プライベートチャネルへの返信投稿は「読み上げ」投稿先で稼働実績がある
- `claude -p` は運営者のサブスクの枠を使う。5アプリ合計の呼び出し回数と利用枠の枯渇時の打ち切りを、各アプリの非機能要件と実行係の仕様で決める
- Claude Code のサンドボックスからは配信の確認・launchd の登録ができないため、環境スモークは手元ターミナルへ渡す
- 元の仕様書(5アプリ分)は、このADRの置き換え表に従って requirements.md / design.md を書き直す。元の構成への言及は仕様書に残さず、このADRだけが経緯を持つ
- 将来この判断を見直す場合の再検討先は次の2つ。**同じ調査を繰り返さないこと**
  - 会社の GitHub で Anthropic の認証を Secrets に置けるようになるか(定期実行だけを Actions に戻せる)
  - Teams から `http://127.0.0.1:...` のリンクが開けるか(開けないなら通知本文のローカルパスの併記が要る)
