# Teams録画トランスクリプトの自動取得 — 設計

対応する要件: [requirements.md](requirements.md)

## 作業フォルダの構成

Power Automateとバッチが受け渡しに使う場所。OneDriveの同期フォルダ配下、`00_root/auto/transcript/` に置く(`00_root/auto/` 直下に置かない理由は [requirements.md#実行環境](requirements.md#実行環境) [6])。

```
00_root/auto/transcript/
├── ledger/     # PAが作成、バッチが削除・退避
├── request/    # バッチが作成、PAが削除(滞留したものはバッチが退避)
├── url/        # PAが作成、バッチが削除
├── vtt/        # バッチが作成(最終成果物)
├── invalid/    # バッチが退避先として使用(不正な台帳・滞留した要求)
└── _status.md  # バッチが追記(処理結果と失敗の記録)
```

**同じファイルをPower Automateとバッチが同時に更新することはない。** 各フォルダについて「作成する側」と「通常時に削除する側」が上表のとおり固定されているため、OneDriveの同期競合ファイルが生まれない。

**`request/` だけは削除する側が2つある。** 通常はフロー②が処理後に削除するが、滞留しきい値を超えたものはバッチが退避する([台帳と要求のライフサイクル](#台帳と要求のライフサイクル))。この二重化が問題にならない理由は次のとおり。

- **同時に触れる可能性がある唯一のケースは「フロー②の処理が滞留しきい値を超えて遅延・リトライしている最中にバッチが退避する」場合。** このときフロー②の削除は対象が存在せず失敗するが、それはフロー実行の失敗記録に留まる(削除はループの後であり、URLファイルは既に作られている)
- バッチが退避したことで対象録画が解放され、重複して要求が出る可能性はある。**その結果、遅延したフロー②の書き込みが後発のフロー②の書き込みを上書きし、URLファイルの一覧が古い(件数の少ない)ものに戻ることがありうる。** これに対しては[使用するURLの一覧の決定](#台帳の読み取りと使用するurlの一覧の決定バッチ) 手順6が既知件数を単調非減少に保つため、全件保存済みと誤判定して台帳を消すことはない
- しきい値(30分)はフロー②の想定実行時間(1件あたり数秒、ポーリング遅延を含めて数分)より十分に長いため、このケース自体が稀である

取得済み記録・ロック・ログはこのツリーには置かず、同期対象外のローカル専用パスに置く([状態管理](#状態管理)参照)。

## 識別子とファイル名の規則(唯一の定義)

**この節がPower Automateフロー①・フロー②・バッチの3者が共有する唯一の取り決めである。** 規則を変更する場合は3箇所を同時に変更する必要がある([architecture.md#設計方針](../architecture.md#設計方針) 3が警告する「静かに壊れる」経路であるため、ここに集約する)。

| 対象 | 名前の規則 | 作る側 |
|---|---|---|
| 録画の識別子 | 録画のファイル識別子(トリガーが提供する値)を**加工せずそのまま**使う | — |
| 台帳のファイル名 | 「録画の識別子」+ 台帳の拡張子 | PAフロー① |
| URLファイルの名前 | 「録画の識別子」+ URLファイルの拡張子 | PAフロー② |
| 要求ファイルの名前 | 作成時刻をもとにした一意な名前(3者間で一致させる必要はない) | バッチ |
| 出力ファイル名 | 会議名 + 時刻 + 連番(規則は[出力ファイル名の組み立て](#出力ファイル名の組み立て)) | バッチ |

**URLファイルは録画1件につき1ファイルとし、その中に一覧全件分のダウンロードURLと並び順をまとめて格納する。** トランスクリプト単位でファイルを分けない理由は、分けると「並び順をファイル名にどう埋め込むか」という第2の規則が3者間に必要になり、規則の共有点が増えるため。録画の識別子だけを共有点にすることで、ずれる余地を最小にする。

### 発行時刻の取り決め

発行時刻は台帳とURLファイルの両方に入る共有フィールドであり、4つの役割を担う。書式が揺れると静かに壊れるため、ここで固定する。

| 項目 | 取り決め |
|---|---|
| 入れる値 | **フローが台帳またはURLファイルを書き出した時点の、フローの実行時刻。** トランスクリプト一覧の応答に含まれる時刻フィールドは転記しない |
| 書式 | ISO 8601 拡張形式、**UTC**、**ミリ秒まで** |
| 用途 | ①死んだURLの同定 ②処理順序 ③期限しきい値の判定 ④台帳とURLファイルの新旧比較 |

**応答内の時刻を転記しない理由**: 応答にどの項目が含まれるかが未確認である(検証項目2)。また応答内の値はトランスクリプトの生成時刻など「発行」とは別の意味を持つ可能性があり、再発行しても同じ値になりうるため、①④の用途に使えない。

**UTC固定にする理由**: クラウド側(Power Automate)が書いた値と、ローカル(Mac)の時計との差分で経過時間を計算する。ローカル時刻やオフセットなしの表記が混ざると、期限しきい値と滞留しきい値の判定が時差分ずれる。

**ミリ秒まで含める理由**: 再発行のたびに必ず異なる値になるようにする。秒精度だと、同一録画について短時間に再発行した場合に前回と同じ値になり、「恒久的失敗と判定した発行時刻」と誤って一致して、有効な新しいURLを使わなくなる。

## 処理フロー

### 録画の検知と台帳の作成(Power Automate フロー①)

**対象**: 監視対象フォルダに作成された録画ファイル

**手順**:

1. 監視対象フォルダにファイルが作成されたことを、1分間隔のポーリングで検知する
2. ファイル名が録画の拡張子で終わり、かつパスが録画フォルダ配下である場合のみ以降を実行する。そうでない場合は何もせず終了する
3. **トリガーが提供する録画の格納先とファイル識別子**を用いて、トランスクリプト一覧を取得する
4. 次の内容を持つ台帳を1件作成する。ファイル名は[識別子とファイル名の規則](#識別子とファイル名の規則唯一の定義)に従う
   - 会議名(録画のファイル名)
   - 録画の格納先とファイル識別子(URLを発行するために必要)
   - 録画の作成日時
   - 由来(チャネル会議 / 通常会議)
   - 手順3で得られた一覧の全件分のダウンロードURLと並び順、および発行時刻。**一覧が空の場合はURLを持たない台帳とする**
5. 手順3が失敗した場合も、URLを持たない台帳を作成する

**関連するビジネスルール**: [requirements.md#台帳の作成power-automate側](requirements.md#台帳の作成power-automate側)

**台帳を「トランスクリプト単位」ではなく「録画単位」にしている理由**: 録画が作成された時点でPower Automateが確実に知っているのは録画1件の存在だけであり、トランスクリプトの件数は後から増えうる。トランスクリプト単位にすると、件数が増えたときに2件目以降の台帳を作る経路が必要になり、フロー①は録画作成時にしか動かないためその経路が作れない。録画単位にすることで、件数と並び順の確定を「URLを発行する時点」に一元化できる([requirements.md#トランスクリプトの列挙](requirements.md#トランスクリプトの列挙) [1])。

**現行フローからの変更点**:

1. 一覧の先頭1件のみを取り出している箇所を、一覧全体の反復に変える
2. 保存先をSharePointからOneDriveの台帳置き場に変える(コネクタは変更しない)
3. 保存内容をURL単体から上記の台帳に変える
4. 一覧が空でも、また一覧の取得に失敗しても台帳を作るようにする
5. **通常会議用フローの、格納先の識別子をハードコードしている呼び出し2件を削除し、トリガーが提供する値を使う。** チャネル会議用フローは既にこの方式であり、揃えることで環境固有の値がフロー定義から消える

### 台帳の読み取りと使用するURLの一覧の決定(バッチ)

**対象**: 台帳置き場のすべての台帳

**この処理を未取得の判定より先に行う。** 「その録画に何件のトランスクリプトが存在するか」の正は台帳ではなく**直近の発行時点の一覧**であるため([requirements.md#トランスクリプトの列挙](requirements.md#トランスクリプトの列挙) [1])、先に使用する一覧を確定させないと件数を誤る。台帳の件数を正にすると、フロー②が2件発行しても台帳が1件なら1件保存した時点で完了と判定してしまう。

**手順**:

1. 台帳置き場のファイルを列挙する。列挙できない場合(同期フォルダが見つからない等)は、対象ごとの処理に入らず全体を中断する
2. 台帳を1件ずつ読み、必須項目が欠けているものやJSONとして解析できないものは不正として退避する([台帳と要求のライフサイクル](#台帳と要求のライフサイクル)参照)
3. その録画について、使用するURLの一覧を次の分岐で決める
   1. **台帳にURLがなく、URL置き場に同じ録画の識別子のURLファイルがある場合**は、そのファイルの一覧を使う
   2. **台帳にURLがあり、URLファイルもある場合**は、発行時刻が新しい方の一覧を使う
   3. **台帳にURLがあり、URLファイルがない場合**は、台帳内の一覧を使う
   4. **どちらにもURLがない場合**は「要発行」とし、以降の判定を行わない
4. 選んだ一覧の発行時刻が、その録画について記録された「恒久的失敗と判定した発行時刻」の**いずれかと一致する場合**は「要発行」として扱う(同じURLを再試行しないため)
5. 選んだ一覧の発行時刻からの経過時間が期限しきい値を超えている場合も「要発行」として扱い、**そのURLファイルを削除する**(古いままでは次サイクルでも同じ判定になるため)
6. **選んだ一覧の件数と、その録画についてこれまでに観測した既知件数の最大値を比べ、大きい方を「既知のトランスクリプト件数」とする。** 最大値は状態に保持し、更新する
7. 手順6の結果として、選んだ一覧のURLの数が既知件数に足りない場合は、足りない分を「要発行」として扱う。**この状態(一覧が実際に減った場合に起こる)が解消しないまま発行要求が既定回数続いたときの打ち切りは、[エラーハンドリング](#エラーハンドリング) 4を参照する**
8. **選んだURLの出所と、発行時刻からの経過時間をログに記録する**(検証項目1の観測用)
9. **既知のトランスクリプト件数と、選んだ一覧のURLの数をログに記録する**(検証項目2・8の観測用。両者の差が件数不足の観測になる)

**関連するビジネスルール**: [requirements.md#トランスクリプトの列挙](requirements.md#トランスクリプトの列挙) / [requirements.md#エラー時の挙動](requirements.md#エラー時の挙動) [1]

**手順3-1が独立した分岐である理由**: **フェーズ2の主経路は「URLを持たない台帳」+「フロー②が作ったURLファイル」の組み合わせである。** この状態では台帳側に比較対象の発行時刻が存在しないため、新旧比較(手順3-2)の条件に含めてはならない。含めると条件が成立せず、発行されたURLを永久に消費しないまま「要発行」を繰り返す。

**手順4が必要な理由**: フェーズ1ではURLが台帳の中にあり、台帳は書き換えられない([requirements.md#未取得の判定バッチ](requirements.md#未取得の判定バッチ) [3])。そのため「そのURLは死んでいる」という事実を状態側に持たないと、期限しきい値に達するまで同じURLへ5分ごとにアクセスし続けることになり、[requirements.md#エラー時の挙動](requirements.md#エラー時の挙動) [1] に反する。記録するのはURLそのものではなく**発行時刻**とし、URLを状態ファイルに残さない([セキュリティ](#セキュリティ))。

**発行時刻を単一値ではなく集合で保持する理由**: 台帳内のURL(発行時刻t1)が恒久的失敗になり、再発行されたURL(t2)も恒久的失敗になった場合、単一値だとt1がt2に上書きされる。次サイクルでは手順3-3により台帳内のt1が再び選ばれ、t1が死んだ事実が失われているため同じURLへアクセスし続けることになる。集合で持てばt1・t2の双方を除外できる。

**手順6で既知件数を単調非減少に保つ理由**([requirements.md#トランスクリプトの列挙](requirements.md#トランスクリプトの列挙) [5]): URLファイルは無条件に採用される(手順3-1)ため、**その件数が減るとその録画は「全件保存済み」と誤判定され、台帳が削除されて残りを永久に取りこぼす**。件数が減って見えるのは、遅延したフロー②の書き込みが後発のフロー②の書き込みを上書きした場合などに起こりうる。一覧からトランスクリプトが消えることはない前提([requirements.md#状態管理](requirements.md#状態管理) [5])なので、観測した最大値を下限として扱えばこの誤判定を防げる。

**その副作用と終端**(手順7): 前提が崩れて一覧が実際に減った場合、既知件数分のURLが永久に揃わず、フェーズ2では「要求 → 発行 → やはり不足 → 要求」を無制限に繰り返す。恒久的失敗ではないため上限3回([エラーハンドリング](#エラーハンドリング) 3の前半)が届かない。そのため**発行要求を出しても保存が進まない回数**に別の上限を設けて打ち切る([requirements.md#エラー時の挙動](requirements.md#エラー時の挙動) [7])。

**発行時刻の書式**: [発行時刻の取り決め](#発行時刻の取り決め)に従う。

**期限しきい値の考え方**: 実測した寿命より短い安全側の値を設定値として持つ。試行せずに要発行へ回すことで、確実に失敗する通信を省ける。ただし**しきい値内でも期限切れは起こりうる**ため、実際のアクセス結果による判定([エラーハンドリング](#エラーハンドリング))が最終的な判断になる。

### 未取得の判定(バッチ)

**対象**: 使用するURLの一覧が決まった録画それぞれ

**手順**:

1. 前の処理で確定した「既知のトランスクリプト件数」と取得済み記録を突き合わせ、まだ保存していないトランスクリプトを列挙する
2. 出力置き場に同名のトランスクリプトファイルが既に存在するものは、取得済みとして記録して対象から外す
3. 未保存のトランスクリプトが1件も残っていない録画は、台帳と使用済みURLファイルを削除して完了とする
4. 台帳の内容は書き換えない(行うのは削除と退避のみ)

**関連するビジネスルール**: [requirements.md#未取得の判定バッチ](requirements.md#未取得の判定バッチ)

**手順3で完了と判定した後にトランスクリプトが増えた場合は検知しない。** これは意図的なスコープ外である([requirements.md#トランスクリプトの列挙](requirements.md#トランスクリプトの列挙) [4])。

**「要発行」となった録画の扱い**: フェーズ2では[発行要求](#ダウンロードurlの発行要求バッチフェーズ2)へ回す。フェーズ1では発行する手段がないため、記録に残すことが終端となる([requirements.md#エラー時の挙動](requirements.md#エラー時の挙動) [3])。

### ダウンロードURLの発行要求(バッチ・フェーズ2)

**対象**: 「要発行」と判定された録画

**手順**:

1. 要求置き場に未処理の要求ファイルが残っている場合、そこに含まれる録画は今回の要求から除外する(重複要求を避ける)
2. 「要手動確認」となっている録画は要求の対象から除外する
3. 除外後に対象が1件以上あれば、それらの録画の識別情報(格納先・ファイル識別子)をまとめた要求ファイルを1つ作成する。**ダウンロードURLは含めない**
4. 要求を出した録画は今回のサイクルでは取得を試みず、次回サイクルに委ねる
5. 未処理の要求が滞留しきい値(既定30分)を超えて残っている場合は、**その要求ファイルを `invalid/` へ退避し**、フロー②が動いていない可能性があることを記録に残す。退避によって対象録画が手順1の除外から外れ、次サイクルで再要求される

**関連するビジネスルール**: [requirements.md#ダウンロードurlの発行要求](requirements.md#ダウンロードurlの発行要求)

**要求に台帳の参照を含めない理由**: 要求だけで発行に必要な情報が揃うようにする。Power Automate側が台帳を読みに行く必要がなくなり、フロー②が「解析して繰り返して呼ぶだけ」の単純な構造で済む。

### ダウンロードURLの発行(Power Automate フロー②・フェーズ2)

**対象**: 要求置き場に作成された要求ファイル

**手順**:

1. 要求置き場にファイルが作成されたことをポーリングで検知する
2. 要求の内容を解析する。解析できない場合は要求ファイルを削除せずに終了する(バッチ側が未処理の滞留として検知する)
3. 含まれる録画それぞれについて、格納先とファイル識別子を用いてトランスクリプト一覧を取得する
4. **一覧に含まれる全件**のダウンロードURLと並び順、および発行時刻を1つのURLファイルにまとめ、URL置き場に作成する。同名がある場合は上書きする
5. 一覧が空だった録画についてはURLファイルを作成しない(台帳が残り、次回また要求される)
6. すべての録画を処理し終えたら、要求ファイルを削除する
7. 個別の録画の取得に失敗しても、他の録画の処理は続行する

**関連するビジネスルール**: [requirements.md#ダウンロードurlの発行要求](requirements.md#ダウンロードurlの発行要求) [4]

**手順4で全件を書く理由**: URLと並び順を同じ応答から同時に取り出すため、両者がずれない。台帳作成時と件数が変わっていても、この時点の一覧が正になる([requirements.md#トランスクリプトの列挙](requirements.md#トランスクリプトの列挙) [1])。

### トランスクリプトの取得と保存(バッチ)

**対象**: 使用するURLが決まった未保存のトランスクリプトそれぞれ

**手順**:

1. 処理対象を**発行時刻の新しい順**([発行時刻の取り決め](#発行時刻の取り決め))に並べ、「要手動確認」の録画を除外したうえで、上限件数(既定20件)まで処理する
2. 決定したURLへ、認証情報を付けずにアクセスする
3. 応答が成功以外の場合は、[エラーハンドリング](#エラーハンドリング)の方針に従って分類し、次の対象へ進む
4. 応答本文がWEBVTTとして妥当か(所定の識別行で始まるか)を確認する。妥当でない場合は保存せず失敗として扱う
5. 出力ファイル名を組み立てる([出力ファイル名の組み立て](#出力ファイル名の組み立て))
6. 出力置き場に同名ファイルが既にある場合は上書きせず、取得済みとして記録して次へ進む
7. 一時ファイルに書き出したうえで所定の名前へ移動する。文字コードはUTF-8、BOMなし、改行は元の応答のまま保持する
8. 取得済み記録に識別子と取得日時を追加する
9. その録画のすべてのトランスクリプトを保存し終えた場合、台帳と使用済みのURLファイルを削除する

**関連するビジネスルール**: [requirements.md#トランスクリプトの取得と保存](requirements.md#トランスクリプトの取得と保存) / [requirements.md#処理の順序と上限](requirements.md#処理の順序と上限)

**手順1で発行時刻の新しい順にする理由**: URLの寿命が短いため、古い対象から処理すると、寿命内に消費できる新しい対象が上限件数に阻まれて後回しになりうる。滞留した対象が枠を占めて正常な対象を追い出すことを防ぐ。

**手順7で一時ファイルを経由する理由**: 同期フォルダに直接書くと、書き込み途中の不完全なファイルがOneDriveにアップロードされうる。所定の名前への移動を最後に行うことで、同期対象になるのは完成したファイルだけになる。

### 出力ファイル名の組み立て

**対象**: 保存するトランスクリプトファイル

**手順**:

1. 会議名から録画由来の拡張子を除去する
2. ファイル名に使えない文字と絵文字を代替文字に置き換える
3. 先頭と末尾の空白、および末尾のピリオドを除去する
4. 置換の結果が空文字列になった場合は、既定の名前を用いる
5. 時刻を決める。台帳に録画の作成日時があればそれを使い、なければ台帳ファイルの更新時刻を使う。時刻は分までの固定書式で表す
6. 会議名・時刻・一覧内の並び順を示す連番を区切り記号で連結し、トランスクリプトの拡張子を付ける
7. 全体の長さが上限(120文字)を超える場合は、会議名側を末尾から切り詰める(時刻と連番は落とさない)
8. 組み立て結果にパス区切り文字と親ディレクトリ参照が含まれないことを確認する

**関連するビジネスルール**: [requirements.md#ファイル名](requirements.md#ファイル名)

### 処理結果の記録

**対象**: 1回の実行

**手順**:

1. 実行の終わりに、処理件数・成功件数・失敗件数・スキップ件数を集計する
2. 失敗があった対象のうち、**まだ記録していない失敗**について、実行日時・会議名・時刻・失敗の種類を記録ファイルに追記する
3. 同じ対象の同じ失敗種別を記録したことを取得済み記録側に保持し、2回目以降は追記しない(ログには残す)
4. 「要手動確認」に到達した対象は、到達時に1回だけ追記する。**追記には原因を区別するラベルを付ける**([requirements.md#処理結果の記録](requirements.md#処理結果の記録) [5])
   - `トランスクリプト0件` — その録画のトランスクリプトが一度も見つかっていない(日常的に発生する想定)
   - `件数不足` — 既知件数分のURLが揃わない(調査が必要)
   - `取得失敗` — 恒久的失敗が上限回数に達した(調査が必要)
5. 台帳が長期滞留しきい値(既定7日)を超えて残っている対象は、1回だけその旨を追記する
6. 記録ファイルは追記のみとし、既存の内容を書き換えない
7. 追記すべき内容が1件もない場合は記録ファイルに触れない(不要な同期を発生させない)

**関連するビジネスルール**: [requirements.md#処理結果の記録](requirements.md#処理結果の記録)

## 台帳と要求のライフサイクル

作業フォルダに置かれるファイルがいつ消えるかを1箇所で定義する。ここで終端が定まっていない状態が残ると、永久に滞留するファイルと、5分ごとに同じ内容が追記される記録ファイルが生まれる。

### 台帳

| 状態 | 台帳 | URLファイル | 記録への追記 | 人手による終端 |
|---|---|---|---|---|
| その録画の全トランスクリプトを保存し終えた | **削除** | 削除 | なし | 不要 |
| 一部だけ保存できた | 保持(残りを次回) | 保持 | なし | 不要(自動で進む) |
| 出力置き場に既に同名ファイルがあり全件済みと判定 | **削除** | 削除 | なし | 不要 |
| 必須項目が欠けている・解析できない | **`invalid/` へ退避** | — | 1回のみ | `invalid/` を確認し、原因を直したうえで削除する |
| 有効なURLがない / 期限切れ(フェーズ2) | 保持(次回要求) | 削除 | なし | 不要(自動で解消する) |
| ★ 有効なURLがない / 期限切れ(フェーズ1) | 保持 | 削除 | 1回のみ | フェーズ2の導入で解消する。それまでは手動で録画からトランスクリプトを取得する |
| ★ 恒久的失敗が上限回数に到達(要手動確認) | 保持(処理対象からは除外) | 削除 | 到達時に1回のみ | **記録ファイルを見て原因を確認し、手動で取得するか、台帳を `invalid/` へ移す**(復旧手順はREADMEに記載) |
| ★ 発行要求を出しても保存が進まない回数が上限に到達(要手動確認・フェーズ2) | 保持(処理対象からは除外) | 期限切れ時に削除 | 到達時に1回のみ | 同上。**原因の大半は「その録画のトランスクリプトが永久に0件」(文字起こしが有効でなかった等)** |
| ★ 長期滞留しきい値を超えて残っている | 保持 | — | 1回のみ | 同上 |

**★の4状態だけはバッチが自動で終端させない。** いずれも原因が外部にあり(発行手段がない・URLが恒久的に取れない・トランスクリプトが永久に0件または一覧の件数が想定に反して減った・Power Automateが動いていない)、自動削除すると取得できたはずのトランスクリプトを黙って捨てることになる。したがって**人が判断して終端させる状態**として扱い、その手順をREADMEに書く。

★の付いていない「保持」2行(一部だけ保存できた / 期限切れフェーズ2)は、次サイクル以降に自動で解消するため人手を必要としない。

### 要求(フェーズ2)

| 状態 | 要求ファイル | 対象録画 | 人手による終端 |
|---|---|---|---|
| フロー②が全件を処理し終えた | **フロー②が削除** | URLファイルが作られる | 不要 |
| フロー②が解析できなかった | 滞留しきい値を超えたら**バッチが `invalid/` へ退避** | 退避後の次サイクルで再要求される | `invalid/` を確認して削除する |
| フロー②が動いていない(滞留) | 滞留しきい値を超えたら同上 | 同上 | Power Automateフローの稼働を確認する |

**要求ファイルもバッチが退避する理由**: 解析できない要求をフロー②は削除しない(削除すると要求が失われる)。一方バッチは「未処理の要求に含まれる録画を重複要求しない」ため、放置すると**その録画が恒久的に要求され直さなくなる**。滞留しきい値を超えた要求をバッチが退避することで、対象録画が解放され次サイクルで再要求される。

なお `request/` は通常フロー②が削除する側だが、フロー②が処理できなかった要求は削除されないため、しきい値超過後にバッチが触っても競合しない。

**不正なファイルを削除せず `invalid/` へ退避する理由**: 削除すると原因調査の材料が失われ、放置すると毎サイクル読み直されて記録が埋まる。バッチが所有するフォルダへ移すことで、終端を作りつつ内容を残す。

**「1回のみ」を実現する仕組み**: 記録済みかどうかを取得済み記録側に保持する(同期フォルダに置かないため、記録ファイル自体を読み返して判定する必要がない)。

## バリデーション

| 対象 | 検証する条件 | NGの場合 |
|---|---|---|
| 台帳 | ファイルがJSONとして解析できること | `invalid/` へ退避し1回だけ記録する |
| 台帳 | 会議名・録画の格納先・録画のファイル識別子が存在すること | 同上 |
| ダウンロードURL | HTTPSであること、および想定するホストの範囲内であること | アクセスせず恒久的失敗として扱う |
| 応答本文 | WEBVTTの識別行で始まること | 保存せず恒久的失敗として扱う |
| 出力ファイル名 | パス区切り文字・親ディレクトリ参照を含まないこと | 組み立て処理で除去する([セキュリティ](#セキュリティ)参照) |
| 書き出し先 | 出力置き場の配下であること | 書き出さず失敗として扱う |

**応答本文の検証を必須にする理由**: 期限切れのURLがエラーページ(HTML)を本文として返し、HTTPステータスは成功になる場合がある。ステータスコードだけを見ていると、HTMLをVTTとして保存し、しかも取得済みとして記録してしまう。この状態は台帳が削除されるため復旧できない。

## エラーハンドリング

機能全体を通じた方針。

**1. 対象ごとに独立させる**

1件の失敗が他の対象の処理を止めない。対象ごとに例外を捕捉し、記録して次へ進む。想定外の例外も同様に扱い、プロセス全体は異常終了させない。

**2. 恒久的失敗と一時的失敗に二分する**

| 分類 | 該当 | 扱い |
|---|---|---|
| 恒久的失敗 | 401 / 403 / 404、本文がWEBVTTでない、URLの検証NG | 同じURLでのリトライを行わない。**その一覧の発行時刻を「恒久的失敗と判定した発行時刻」として状態に記録し**、URLファイルを削除して台帳を残す。フェーズ2では次回の発行要求に回す |
| 一時的失敗 | 5xx、接続エラー、タイムアウト | 何も変更せず、次回の定期実行で自然にリトライされる |

**発行時刻を記録する理由**: URLファイルを削除しても、フェーズ1ではURLが台帳の中に残り、台帳は書き換えられない。発行時刻を記録しておかないと次サイクルで同じURLを選び直してしまう([台帳の読み取りと使用するURLの一覧の決定](#台帳の読み取りと使用するurlの一覧の決定バッチ) 手順4)。URLそのものは記録しない。発行時刻の書式は[発行時刻の取り決め](#発行時刻の取り決め)に従う。

**3. 恒久的失敗の繰り返しに上限を設ける**

同じ対象が恒久的失敗を既定回数(3回)繰り返した場合、それ以上の取得も発行要求も行わず、「要手動確認」として1回だけ記録する。上限に達した対象は処理対象から除外し、上限件数の枠も消費しない。無限に要求を出し続けてPower Automateの実行回数を消費することを防ぐ。

**数え方は「録画単位・1サイクルにつき最大1回」とする**([requirements.md#エラー時の挙動](requirements.md#エラー時の挙動) [5] [6])。1つの録画に3件のトランスクリプトがあり、そのURLがまとめて期限切れになった場合、トランスクリプトごとに数えると**1サイクルで即座に上限へ到達**し、フェーズ2の再発行で回復できるケースを人手案件に落としてしまう。同一サイクル内の複数の失敗は「URLの期限切れ」という1つの原因によるものなので1回と数える。これにより上限到達には最低3サイクル(約15分)を要し、その間に再発行のチャンスが確保される。

**この上限に到達するのはフェーズ2からである。** フェーズ1では、1回目の恒久的失敗で発行時刻が記録され、2回目以降は[使用するURLの一覧の決定](#台帳の読み取りと使用するurlの一覧の決定バッチ) 手順4によりアクセスされず「要発行」と判定されるため、回数が2以上に増える経路がない。フェーズ1におけるこの状態の終端は、[台帳と要求のライフサイクル](#台帳と要求のライフサイクル)の★「有効なURLがない/期限切れ(フェーズ1)」である。累積回数と上限の実装自体はフェーズ1から行うが、実際に発火するのはフェーズ2からになる。

**4. 進捗のない発行要求にも別の上限を設ける(フェーズ2)**

恒久的失敗にならないまま要求と発行を繰り返す経路がある(既知件数分のURLが揃わない場合など。[台帳の読み取りと使用するURLの一覧の決定](#台帳の読み取りと使用するurlの一覧の決定バッチ) 手順7)。この状態は方針3の上限が届かないため、別の打ち切りが必要になる。

**数え方は「バッチの実行1回につき最大1回」とする**(方針3と同じ換算)。発行要求を出した録画について、以降の実行で保存が1件も進まなかったらその実行で1加算する。**既定10回は実行間隔5分との積で約50分に相当する。** 上限に達したら「要手動確認」として1回だけ記録し、以降の取得と発行要求を行わない([requirements.md#エラー時の挙動](requirements.md#エラー時の挙動) [7] [8])。

**「保存が進んだ」の判定**: その録画のトランスクリプトを1件以上新たに出力置き場へ書き出した場合に加えて、[未取得の判定](#未取得の判定バッチ) 手順2で「出力置き場に同名ファイルがあり取得済みとして記録した」場合も進捗とみなす。どちらも完了に近づいているため。進捗があった時点でカウントを0に戻す。

**方針3の上限(3回・約15分)より緩い値にする理由**: こちらは「まだ生成されていないだけ」という正常な待ち状態を含む。**実運用でこの状態に最も多く至るのは、その録画のトランスクリプトが永久に0件のままのケース(会議で文字起こしが有効でなかった場合など)**だが、生成が遅れているだけの録画も同じ経路を通るため、生成待ちを人手案件に落とさないゆとりを取る。生成の遅れが約50分を超えると観測された場合([requirements.md#前提検証項目](requirements.md#前提検証項目) #7)は既定値を引き上げる。

**5. 全体を中断する条件**

同期フォルダにアクセスできない場合(パスが存在しない、権限がない)は、対象ごとの処理に入らず全体を中断して記録する。部分的に処理された中途半端な状態を作らないため。

**6. 書き込みは原子的に行う**

出力ファイル・取得済み記録のいずれも、一時ファイルへ書いてから所定の名前へ移動する。処理が途中で中断しても、壊れたファイルが残らないようにする。

**7. 二重起動を防ぐ**

前回の実行が長引いて次の起動時刻に達した場合、同時に2つの実行が走ると取得済み記録が壊れる。ロックファイルによって後発の実行を即座に終了させる。

### 外部ライブラリの方針

**外部ライブラリを一切追加しない。** 実行用・開発用ともに依存はゼロを維持する。

| 用途 | 採用 | 理由 |
|---|---|---|
| テスト | 標準ライブラリの `unittest` | pytestも検討したが、このサンドボックスからPyPIへ到達できずインストールも実行もできないため、TDDのRed/Greenを確認できない。`unittest` なら追加作業なしで `python3 -m unittest` が動く |
| HTTPアクセス | 標準ライブラリの `urllib.request` | 必要なのはGET1種類と、ステータスコード・本文・タイムアウトの扱いだけ。`requests` の利点(セッション管理・リトライ・認証方式の抽象化)をどれも使わない。定期実行される常駐バッチの実行時依存は少ないほど壊れにくい |

## 状態管理

| 保持するもの | 置き場所 | 内容 |
|---|---|---|
| 取得済み記録 | 同期対象外のローカル専用パス | 取得済みトランスクリプトの識別子と取得日時、録画ごとの恒久的失敗の累積回数、**録画ごとの「進捗のない発行要求の連続回数」**、録画ごとの「恒久的失敗と判定した発行時刻の集合」、録画ごとの「観測した既知件数の最大値」、記録ファイルへ追記済みの失敗種別、台帳を最初に観測した日時(長期滞留の判定用) |
| ロック | 同上 | 実行中であることを示すファイル |
| ログ | 同上 | 実行ログ |

**同期フォルダに置かない理由**: OneDriveが競合ファイルを作ると、状態が二重化して取得済み判定が壊れる。またローカル固有の情報をクラウドに置く必要がない。

**URLそのものは保持しない。** 死んだURLの識別には発行時刻を使う([エラーハンドリング](#エラーハンドリング) 2)。状態ファイルにベアラトークン相当の文字列を残さないため。

**取得済み記録が失われた場合**: 出力置き場の同名ファイルの存在チェック([未取得の判定](#未取得の判定バッチ) 手順2)が二重取得を防ぐ。記録は高速化とエラー回数の保持のためのもので、唯一の真実の源ではない。

**録画に紐づく状態の掃除**: 台帳が削除または退避された時点で、その録画に紐づく「恒久的失敗の累積回数」「**進捗のない発行要求の連続回数**」「恒久的失敗と判定した発行時刻の集合」「観測した既知件数の最大値」「最初に観測した日時」「追記済みの失敗種別」を削除する。台帳が消えた録画についてこれらを持ち続ける意味はなく、発行時刻の集合は際限なく増えうるため。**取得済みトランスクリプトの識別子と取得日時は削除しない**(重複保存を防ぐ用途であり、台帳の有無とは独立している)。

**識別方式を切り替えた場合**([requirements.md#状態管理](requirements.md#状態管理) [4]・検証項目8): 「録画の識別子 + 並び順」から一覧の一意な識別子へ切り替えると、既存の取得済み記録は識別子体系が変わって一致しなくなる。この場合も出力置き場の同名ファイルの存在チェックが二重取得を防ぐため、記録を移行する必要はない(切り替え直後の1サイクルだけ、既に保存済みのトランスクリプトを取得済みとして再登録する動きになる)。

## セキュリティ

- **ダウンロードURLをログと記録ファイルに出力しない。** 事前認証済みURLは実質ベアラトークンであり、そのURLを知れば会議音声由来の内容を第三者が取得できる。出力する場合はホスト名までに留める
- **要求ファイルにダウンロードURLを含めない**([requirements.md#ダウンロードurlの発行要求](requirements.md#ダウンロードurlの発行要求) [3])
- **フェーズ1では台帳にURLが含まれる。** 会議終了から取得までの間、URLがOneDrive上に存在し、PCが停止していれば数時間〜数日に及ぶ。これは[architecture.md#設計方針](../architecture.md#設計方針) 4が目指す状態からの意図的な逸脱であり、フェーズ2で解消される。フェーズ1の期間中は作業フォルダを共有せず、個人利用の範囲に留める
- **トランスクリプトは会議の発話内容そのものであり、機微情報を含みうる。** 出力置き場を他者と共有する場合は共有範囲を意識的に決める
- **出力ファイル名は会議名由来のため、パストラバーサルの経路になりうる。** ファイル名の組み立てでパス区切り文字と親ディレクトリ参照を除去し、書き出し前に出力先が出力置き場の配下であることを確認する
- **アクセス先URLを検証する。** 台帳やURLファイルの内容は外部から与えられた文字列として扱い、HTTPSかつ想定するホストの範囲内であることを確認してからアクセスする
- **資格情報を一切保持しない。** 設定ファイル・コード・リポジトリのいずれにも認証情報を置かない。M365への認証はOneDrive同期クライアントに委ねる
- **フロー定義に含まれるテナント識別子・接続識別子・ドライブ識別子をリポジトリのドキュメントへ転記しない。** フロー定義ファイル自体を管理する場合は、これらを含むことを前提に置き場所を決める

## ログ

ローカルのログファイルに出力する(同期フォルダには置かない)。**URLとトランスクリプト本文はログに出力しない。**

**既定のログレベルは DEBUG とする。** 検証項目の観測に使う項目を含めてすべて記録されている必要があり、1日あたり数件〜十数件という規模では出力量が問題にならないため。運用が安定して観測が不要になった時点で INFO へ上げる。

| タイミング | 内容 | レベル |
|---|---|---|
| 実行開始 | 開始時刻、台帳の件数 | INFO |
| 二重起動の検知 | 先行実行が動作中であること | INFO |
| スキップ | 識別子、理由(取得済み/出力済み/要手動確認) | DEBUG |
| 台帳の退避 | ファイル名、欠けている項目 | WARNING |
| **台帳の項目** | **台帳に含まれていた項目名の一覧(値は出さない)、その録画の既知のトランスクリプト件数、選んだ一覧のURLの数** | DEBUG |
| **URLの鮮度** | **選んだURLの出所(台帳 / URL置き場 / なし)と、発行時刻からの経過時間** | INFO |
| 発行要求 | 要求した件数、要発行と判定した理由の内訳 | INFO |
| 未処理要求の滞留 | 滞留時間 | WARNING |
| 取得成功 | 識別子、出力ファイル名、本文のバイト数、**URL発行からの経過時間** | INFO |
| 恒久的失敗 | 識別子、ステータスコードまたは理由、累積失敗回数、**URL発行からの経過時間** | WARNING |
| 上限到達 | 識別子、要手動確認であること | ERROR |
| 長期滞留 | 識別子、滞留日数 | WARNING |
| 一時的失敗 | 識別子、エラーの種類 | INFO |
| 全体の中断 | 中断理由 | ERROR |
| 実行終了 | 処理件数の内訳、所要時間 | INFO |

**太字の3項目は、[requirements.md#前提検証項目](requirements.md#前提検証項目) の #1(URLの寿命)・#2(一覧の応答項目)・#8②(件数が減らないか)を実機で観測するためのものである。** 事前実測をしない代わりに、これらのログが揃っていることを実装の完了条件に含める。**#8①は直接観測できないため完了条件に含めない**(下記)。

- 検証項目1は「取得成功」と「恒久的失敗」の経過時間を並べれば、成功する最大経過時間と失敗する最小経過時間が挟み込める
- 検証項目2は「台帳の項目」から、一意な識別子や作成日時が実際に得られているかが分かる
- 検証項目8②(件数が減らないか)は、「台帳の項目」の**「選んだ一覧のURLの数」**を同一録画について時系列で並べて確認する。「既知のトランスクリプト件数」は定義上単調非減少なので、そちらでは観測できない
- **検証項目8'(既存の並び順が保たれるか)はログから直接観測できず、間接検知にも限界がある。** 保存済みのトランスクリプトを再取得しないため、同一性を比較する材料が残らない。破れ方は2通りある
  - **件数が増える形で現れた場合**: 「一覧の件数は増えているのに保存が進まない」という症状になり、[エラーハンドリング](#エラーハンドリング) 方針4の要手動確認(ラベル `件数不足`)で検知できる
  - **件数が変わらないまま並び順だけ入れ替わった場合**: 全インデックスが取得済みと一致するため全件保存済みと判定され、台帳が削除される。**この破れ方は検知できず、前提として受容する**([requirements.md#前提検証項目](requirements.md#前提検証項目) #8')
  - 検証項目2で一覧の応答に一意な識別子が含まれると分かった場合は、その値をログに追加して直接検知できるようにし、識別方式もその識別子へ切り替える(値そのものがURLではないため出力してよい)

ログファイルは無制限に増えないよう世代でローテーションする。

## パフォーマンス

想定件数は1日あたり数件〜十数件のため特別な考慮は不要。ただし次の3点は設ける。

- 1回の実行で取得を試みる上限件数(既定20件)。1回の実行が起動間隔(5分)を超えないようにする
- 上限件数は「要手動確認」の対象を除外したうえで、発行時刻の新しい順に適用する([requirements.md#処理の順序と上限](requirements.md#処理の順序と上限))
- ダウンロードのタイムアウト(接続・読み取りともに既定30秒)。応答しないURLで実行が滞留しないようにする
